## 3. 오답노트 — 1과목 리눅스 실무의 이해

### 3-1. 운영체제(커널)의 역할과 응용 도구의 경계

> 1번 오답 — ③(메모리 관리)을 골랐으나 정답은 ②(소스 코드 컴파일)

"가장 거리가 먼 것"을 묻는 문제였는데 커널이 **하는 일**을 골라버림. 운영체제의 4대 역할은 다음과 같음.

| 역할        | 내용                       | 관련 명령·개념                  |
| --------- | ------------------------ | ------------------------- |
| 프로세스 관리   | 생성(fork)·스케줄링·종료·시그널 전달  | `ps`, `top`, `kill`, nice |
| 메모리 관리    | 물리/가상 메모리 할당·회수, 페이징·스와핑 | `free`, `vmstat`, swap    |
| 파일시스템 관리  | 파일·디렉터리 추상화, inode, 마운트  | `mount`, `df`             |
| 장치·입출력 관리 | 디바이스 드라이버, 인터럽트 처리       | `/dev`, 커널 모듈             |

**컴파일(gcc)은 응용 프로그램(툴체인)의 일**임. 커널은 컴파일된 결과물을 "실행"시켜 줄 뿐 컴파일 자체를 하지 않음. 같은 맥락으로 셸(bash)·라이브러리(glibc)도 커널이 아니라 사용자 영역(user space)임.

```
┌──────────────────────────────────────┐
│ 사용자 영역  응용프로그램 (gcc, vim, httpd) │
│              셸 (bash)                 │
│              라이브러리 (glibc)          │
├──────────── 시스템 콜 ─────────────────┤
│ 커널 영역    프로세스·메모리·파일시스템·장치  │
├──────────────────────────────────────┤
│ 하드웨어     CPU · RAM · Disk · NIC     │
└──────────────────────────────────────┘
```

### 3-2. 오픈소스 라이선스 5종 비교

> 3번 오답(③ 선택, 정답 ①) · 4번 무응답(정답 ④ MPL)

카피레프트(copyleft)란 "이 소프트웨어를 가져다 쓴 결과물도 같은 자유를 유지해야 한다"는 강제 조항임. 강제 범위에 따라 등급이 나뉨.

| 라이선스       | 원어                             | 카피레프트 강도      | 파생물 소스 공개                             | 대표 사례                       |
| ---------- | ------------------------------ | ------------- | ------------------------------------- | --------------------------- |
| GPL        | GNU General Public License     | **강함**        | 링크한 프로그램 **전체** 공개                    | 리눅스 커널, GCC                 |
| LGPL       | Lesser GPL                     | 중간            | **라이브러리 자체**의 수정분만 공개 (링크한 앱은 비공개 가능) | glibc                       |
| MPL        | Mozilla Public License         | **약함(파일 단위)** | **수정한 파일만** 공개, 새로 만든 파일은 비공개 가능      | Firefox                     |
| BSD        | Berkeley Software Distribution | 없음(허용적)       | 공개 의무 없음, 저작권 고지만                     | FreeBSD                     |
| Apache 2.0 | Apache License                 | 없음(허용적)       | 공개 의무 없음 + **특허 라이선스 명시**             | Apache HTTP Server, Android |

**시험 포인트** — "파일 단위 약한 카피레프트 + Firefox" 조합이 나오면 무조건 MPL임. "전체 공개 + 카피레프트"는 GPL, "라이브러리만"은 LGPL, "공개 의무 없음"은 BSD/Apache임. Apache가 BSD와 다른 유일한 지점은 **특허 조항**이라는 것도 자주 나옴.

### 3-3. 배포판 계열 — RPM 계열과 데비안 계열

> 5번 오답 — ④(openSUSE)를 골랐으나 정답은 ②(Linux Mint)

문제는 "데비안 **계열**"을 물었음. openSUSE는 RPM 패키지를 쓰지만 SUSE 계열이지 데비안 계열이 아님.

| 계열           | 패키지 형식 | 패키지 도구             | 배포판                                                       |
| ------------ | ------ | ------------------ | --------------------------------------------------------- |
| 레드햇(RHEL) 계열 | `.rpm` | `rpm`, `yum`/`dnf` | RHEL, CentOS, **Rocky Linux**, AlmaLinux, Fedora          |
| 데비안 계열       | `.deb` | `dpkg`, `apt`      | Debian, **Ubuntu**, **Linux Mint**, Kali, Raspberry Pi OS |
| 슬랙웨어 계열      | `.tgz` | `pkgtool`          | Slackware                                                 |
| SUSE 계열      | `.rpm` | `rpm`, `zypper`    | SUSE Linux Enterprise, **openSUSE**                       |

**함정** — "RPM을 쓰면 레드햇 계열"이 아님. SUSE도 RPM을 씀. **계열은 패키지 형식이 아니라 조상 배포판으로 갈림.**

### 3-4. 부팅 순서·런레벨·타겟

> 7번 무응답 — 정답 ③ multi-user.target

부팅 순서(6번은 맞혔지만 함께 정리):

```
전원 → BIOS/UEFI (펌웨어, POST 하드웨어 점검)
     → MBR/GPT 의 부트로더 (GRUB2) 적재
     → 커널(vmlinuz) + 초기 램디스크(initramfs) 메모리 적재
     → 커널이 하드웨어 초기화 후 루트 파일시스템 마운트
     → PID 1 로 systemd 실행
     → default.target 이 요구하는 유닛들 병렬 기동
     → 로그인 프롬프트
```

- **BIOS** = Basic Input/Output System, **UEFI** = Unified Extensible Firmware Interface
- **GRUB** = GRand Unified Bootloader
- **initramfs** = initial RAM file system — 루트 파일시스템을 마운트하는 데 필요한 드라이버(LVM·RAID·암호화 등)를 임시로 담은 램디스크

런레벨 ↔ 타겟 대응표 — **시험에 거의 매회 나옴**:

| 런레벨   | systemd 타겟              | 의미                          |
| ----- | ----------------------- | --------------------------- |
| 0     | `poweroff.target`       | 시스템 종료                      |
| 1     | `rescue.target`         | 단일 사용자 모드(복구용)              |
| 2     | `multi-user.target`     | 다중 사용자, 네트워크 없음(전통 SysV 기준) |
| **3** | **`multi-user.target`** | **다중 사용자 + 네트워크, 텍스트 콘솔**   |
| 4     | `multi-user.target`     | 미사용(사용자 정의)                 |
| **5** | **`graphical.target`**  | **다중 사용자 + 그래픽(GUI) 로그인**   |
| 6     | `reboot.target`         | 재부팅                         |

```bash
systemctl get-default              # 현재 기본 타겟 확인
systemctl set-default multi-user.target   # 부팅 시 텍스트 모드로 고정
systemctl isolate graphical.target        # 재부팅 없이 지금 타겟 전환
runlevel                           # 이전·현재 런레벨 (호환용)
```

> 타겟·런레벨의 상세 의미는 [[../../QA#J-2. 타겟(target)과 런레벨(runlevel)이란 정확히 무엇인가]] 참조.

### 3-5. GRUB2 — 부트로더란 무엇인가

> 8번 무응답 — "GRUB이 뭔지 모르겠음". 정답 ②(grub.cfg 직접 편집이 권장 — 틀린 설명)

**부트로더(boot loader)** 는 펌웨어(BIOS/UEFI)와 커널 사이를 잇는 아주 작은 프로그램임. 펌웨어는 파일시스템을 이해하지 못하므로 커널 파일을 직접 읽어올 수 없음. 부트로더가 그 역할을 대신함.

1. 펌웨어가 디스크 첫 섹터(MBR) 또는 EFI 시스템 파티션에서 부트로더를 읽어 메모리에 올림
2. 부트로더가 부팅 메뉴를 띄우고(멀티부팅 선택), 사용자가 고른 커널 이미지와 initramfs를 메모리에 적재
3. 커널에 부팅 파라미터(root 장치, `quiet`, `selinux=0` 등)를 넘기고 제어권 이양

**GRUB2 파일 구조 — 여기가 시험 포인트:**

| 파일                                                                     | 역할                              | 직접 편집?       |
| ---------------------------------------------------------------------- | ------------------------------- | ------------ |
| `/etc/default/grub`                                                    | 타임아웃·기본 메뉴·커널 파라미터 등 **사용자 설정** | **여기를 편집**   |
| `/etc/grub.d/`                                                         | 메뉴 항목 생성 스크립트 조각                | 필요 시 편집      |
| `/boot/grub2/grub.cfg` (BIOS)<br>`/boot/efi/EFI/<배포판>/grub.cfg` (UEFI) | 위 둘을 재료로 **자동 생성된 결과물**         | **직접 편집 금지** |

```bash
# 설정 변경 절차 — 반드시 이 순서
vi /etc/default/grub                        # 예: GRUB_TIMEOUT=5
grub2-mkconfig -o /boot/grub2/grub.cfg      # -o = output, 결과 파일 경로 지정
```

`grub.cfg`를 직접 고치면 다음번 커널 업데이트가 `grub2-mkconfig`를 자동 실행하면서 수정분이 **전부 날아감**. 이것이 ②가 틀린 이유임.

부팅 메뉴에서 `e` 키를 누르면 **그 회차 부팅에만** 적용되는 일시 편집이 가능함(디스크에 저장되지 않음). 루트 패스워드 복구 시 커널 라인 끝에 `rd.break` 또는 `init=/bin/bash`를 붙이는 것이 이 방식임.

### 3-6. FHS — 디렉터리 계층 표준 전수 정리

> 9번 정답(④) — "FHS 설명 필요" 요청

**FHS** = Filesystem Hierarchy Standard. 리눅스/유닉스에서 어떤 디렉터리에 무엇을 두는지 정한 표준. 배포판이 달라도 이 구조가 같기 때문에 스크립트와 패키지가 호환됨.

| 디렉터리             | 원어·의미                     | 담기는 것                                                               |
| ---------------- | ------------------------- | ------------------------------------------------------------------- |
| `/`              | root                      | 최상위. 모든 경로의 시작                                                      |
| `/bin`           | binaries                  | 모든 사용자용 필수 실행 파일 (`ls`, `cp`, `bash`)                               |
| `/sbin`          | system binaries           | **관리자용** 실행 파일 (`fdisk`, `ip`, `shutdown`)                          |
| `/etc`           | et cetera (편집 가능한 텍스트 설정) | **시스템 전역 설정 파일** — 4-9 절 참조                                         |
| `/home`          | —                         | **일반 사용자 홈 디렉터리** (`/home/kim`)                                     |
| `/root`          | —                         | **root 계정의 홈 디렉터리** (`/`와 다름)                                       |
| `/var`           | variable                  | 크기가 **변하는** 데이터 — 로그(`/var/log`), 메일 스풀, 프린트 큐, DB                  |
| `/tmp`           | temporary                 | 임시 파일. 재부팅 시 비워짐. 스티키 비트 설정됨                                        |
| `/usr`           | Unix System Resources     | 응용 프로그램·라이브러리·문서 (`/usr/bin`, `/usr/lib`, `/usr/share`)             |
| `/usr/local`     | —                         | **관리자가 직접 설치**한 소프트웨어 (소스 컴파일 기본 설치 경로)                             |
| `/opt`           | optional                  | 서드파티 패키지(단일 디렉터리 통째 설치형)                                            |
| `/boot`          | —                         | 커널(`vmlinuz`)·initramfs·GRUB 파일                                     |
| `/dev`           | devices                   | 장치 파일 (`/dev/sda`, `/dev/null`, `/dev/tty`)                         |
| `/proc`          | processes                 | **가상 파일시스템** — 커널·프로세스 정보를 파일처럼 노출 (`/proc/cpuinfo`, `/proc/1234/`) |
| `/sys`           | system                    | **가상 파일시스템** — 커널이 본 장치·드라이버 정보 (sysfs)                             |
| `/lib`, `/lib64` | libraries                 | 부팅·`/bin`·`/sbin` 실행에 필요한 공유 라이브러리, 커널 모듈                           |
| `/media`         | —                         | 이동식 매체 자동 마운트 지점 (USB, CD)                                          |
| `/mnt`           | mount                     | 관리자가 임시로 수동 마운트하는 지점                                                |
| `/srv`           | service                   | 서비스가 제공하는 데이터(웹·FTP 자료)                                             |
| `/run`           | —                         | 부팅 이후의 런타임 데이터(PID 파일, 소켓). 메모리 기반                                  |

**시험 단골 함정**
- `/proc`은 홈 디렉터리가 **아님** (9번의 정답 근거). 홈은 `/home`, root의 홈은 `/root`
- `/bin`은 일반 사용자용, `/sbin`은 **관리자용**
- `/var`는 "변하는 것", `/usr`는 "설치된 것" — 백업 전략이 완전히 다름
- `/proc`, `/sys`, `/run`은 디스크에 없는 **가상 파일시스템**이라 크기가 0으로 나옴

### 3-7. inode·하드 링크·심볼릭 링크와 "동일 파일시스템"

> 10번·11번 정답 — "동일한 파일시스템이 정확히 뭘 지칭하는지?" 요청

**inode(index node)** 는 파일의 **메타데이터를 담은 자료구조**임. 파일시스템을 만들 때(`mkfs`) 개수가 고정되고, 각 inode는 그 파일시스템 안에서만 유효한 번호를 가짐.

| inode에 **있는** 것                             | inode에 **없는** 것      |
| ------------------------------------------- | -------------------- |
| 파일 유형(일반/디렉터리/링크…)                          | **파일 이름** ← 10번 정답   |
| 소유자 UID·그룹 GID                              | 파일 내용 자체(데이터 블록에 있음) |
| 접근 권한(퍼미션)                                  |                      |
| 파일 크기                                       |                      |
| 시각 3종 — atime(접근)·mtime(수정)·ctime(inode 변경) |                      |
| 하드 링크 수                                     |                      |
| 데이터 블록 위치 포인터                               |                      |

**파일 이름은 디렉터리 안에 있음.** 디렉터리는 `이름 → inode 번호` 쌍의 목록일 뿐임. 그래서 한 inode에 이름을 여러 개 붙일 수 있고, 그것이 하드 링크임.

```bash
ls -li file.txt        # -i = inode 번호 함께 출력
# 1310724 -rw-r--r--. 2 kim dev 12 Sep 6 10:00 file.txt
#  ^inode번호           ^하드 링크 수
```

**"동일한 파일시스템"이란?** — 같은 `mkfs`로 포맷된 하나의 파티션/논리 볼륨을 뜻함. `df` 출력에서 한 줄이 하나의 파일시스템임.

```bash
$ df -h
Filesystem            Size  Used Avail Use% Mounted on
/dev/mapper/rl-root    70G   12G   58G  18% /          ← 파일시스템 A
/dev/sda1             1014M  350M  665M  35% /boot     ← 파일시스템 B
/dev/sdb1              50G   40G   10G  80% /data      ← 파일시스템 C
```

`/home/kim/a.txt`와 `/tmp/b.txt`는 둘 다 A에 있으므로 같은 파일시스템이지만, `/data/c.txt`는 C라서 다름. **inode 번호는 파일시스템별로 독립**이라 A의 inode 1234와 C의 inode 1234는 완전히 다른 파일임. 하드 링크는 "이 inode를 가리켜라"라는 뜻이므로 파일시스템 경계를 넘을 수 없음.

| 항목         | 하드 링크                      | 심볼릭(소프트) 링크                     |
| ---------- | -------------------------- | ------------------------------- |
| 생성         | `ln 원본 링크`                 | `ln -s 원본 링크`                   |
| inode      | 원본과 **동일**                 | **별도** inode를 가진 새 파일           |
| 저장 내용      | (없음, 이름만 추가)               | 원본의 **경로 문자열**                  |
| 파일시스템 경계   | **넘을 수 없음**                | 넘을 수 있음                         |
| 디렉터리 대상    | **불가**(일반 사용자)             | 가능                              |
| 원본 삭제 시    | 링크로 **계속 접근 가능**(링크 수만 감소) | **깨진 링크**(dangling)가 됨 ← 11번 정답 |
| `ls -l` 표시 | 일반 파일과 동일                  | `l`로 시작, `링크 -> 원본` 표시          |

### 3-8. 셸 변수·환경변수·export·source

> 13번 정답(② HISTSIZE) — "변수와 export, source 설명 필요" 요청

**셸 변수 vs 환경변수**

| 구분    | 셸 변수(shell variable)       | 환경변수(environment variable)    |
| ----- | -------------------------- | ----------------------------- |
| 정의    | `NAME=value` (등호 앞뒤 공백 없음) | `export NAME=value`           |
| 유효 범위 | **현재 셸에서만**                | 현재 셸 **+ 여기서 실행된 자식 프로세스 전부** |
| 확인    | `set` (셸 변수 + 함수 전부)       | `env` 또는 `printenv`           |
| 관례    | 소문자 자주 사용                  | **대문자**                       |

```bash
myvar="hello"          # 셸 변수
export myvar           # 환경변수로 승격 (자식에게 상속)
export PATH=$PATH:/opt/bin   # 정의와 동시에 export
unset myvar            # 삭제
echo $myvar            # 값 참조
```

**핵심 개념 — 상속은 아래로만 흐름.** 자식 프로세스는 부모의 환경변수 **복사본**을 받음. 자식이 값을 바꿔도 부모에게 반영되지 않음.

**주요 환경변수 — 시험 빈출:**

| 변수                | 의미                                |
| ----------------- | --------------------------------- |
| `PATH`            | 명령 실행 파일 **검색 경로** (`:`로 구분)      |
| `HOME`            | 현재 사용자의 홈 디렉터리                    |
| `PWD` / `OLDPWD`  | 현재 / 직전 작업 디렉터리                   |
| `SHELL`           | 로그인 셸 경로 (`/bin/bash`)            |
| `USER`, `LOGNAME` | 로그인 사용자명                          |
| `PS1`             | **1차 프롬프트** 문자열 (`[\u@\h \W]\$ `) |
| `PS2`             | 2차 프롬프트(명령이 다음 줄로 이어질 때, 기본 `>`)  |
| `HISTSIZE`        | **메모리에 유지할** 히스토리 명령 개수 ← 13번     |
| `HISTFILE`        | 히스토리 저장 파일 (`~/.bash_history`)    |
| `HISTFILESIZE`    | **파일에 저장할** 히스토리 개수               |
| `TERM`            | 터미널 유형 (`xterm-256color`)         |
| `LANG`            | 로케일 (`ko_KR.UTF-8`)               |
| `EDITOR`          | 기본 편집기                            |
| `UID`, `EUID`     | 사용자 ID, 유효 사용자 ID                 |
| `?`               | 직전 명령의 종료 상태 (`echo $?`, 0이면 성공)  |
| `$`               | 현재 셸의 PID                         |

**`source`(= `.`)가 필요한 이유**

`bash script.sh`로 스크립트를 실행하면 **자식 셸**이 새로 뜨고 그 안에서 변수가 설정됨. 자식이 끝나면 변수도 함께 사라짐. 부모(현재 셸)에는 아무 일도 일어나지 않음.

```bash
bash   ~/.bashrc      # 자식 셸에서 실행 → 현재 셸에 반영 안 됨 (무의미)
source ~/.bashrc      # 현재 셸에서 직접 실행 → 반영됨
.      ~/.bashrc      # source 의 축약형 (POSIX 표기)
```

`.bashrc`를 고친 뒤 `source ~/.bashrc`를 치는 이유가 이것임. 로그아웃/로그인해도 같은 효과지만 `source`가 즉시임.

**셸 초기화 파일 읽는 순서:**

| 파일                    | 범위     | 읽히는 시점                                               |
| --------------------- | ------ | ---------------------------------------------------- |
| `/etc/profile`        | 전체 사용자 | **로그인 셸** 시작 시                                       |
| `/etc/profile.d/*.sh` | 전체 사용자 | `/etc/profile`이 불러들임                                 |
| `~/.bash_profile`     | 개인     | **로그인 셸** 시작 시 (없으면 `~/.bash_login` → `~/.profile`)  |
| `~/.bashrc`           | 개인     | **비로그인 셸**(새 터미널 창) 시작 시. 보통 `.bash_profile`이 이걸 불러줌 |
| `/etc/bashrc`         | 전체 사용자 | `~/.bashrc`가 불러들임                                    |
| `~/.bash_logout`      | 개인     | 로그인 셸 종료 시                                           |

> 로그인 셸/비로그인 셸의 차이와 `su -`가 환경을 초기화하는 이유는 [[../../QA#F-1. 환경변수·셸·tty 와 `su -` 가 환경을 초기화하는 이유]], [[../../QA#F-2. 로그인 셸과 비로그인 셸의 차이]] 참조.

### 3-9. 시그널 체계 총정리

> 16번 오답 — ④(SIGINT)를 골랐으나 정답은 ③(SIGKILL). "시그널 체계 총체적 정리 필요" 요청

**시그널(signal)** 은 커널이 프로세스에게 보내는 **비동기 알림**임. 프로세스는 각 시그널에 대해 셋 중 하나로 대응함.

1. **기본 동작 수행** (대개 종료)
2. **무시**(ignore)
3. **핸들러로 가로채기**(catch) — 자기 코드로 처리

**이 셋 중 어느 것도 불가능한 시그널이 딱 둘 있음 — 여기가 문제의 핵심임.**

| 번호  | 이름          | 기본 동작        | 무시/가로채기          | 발생 상황                              |
| --- | ----------- | ------------ | ---------------- | ---------------------------------- |
| 1   | **SIGHUP**  | 종료           | 가능               | 터미널 연결 끊김. **데몬은 관례적으로 설정 재적재**로 씀 |
| 2   | **SIGINT**  | 종료           | 가능               | **Ctrl+C** (interrupt)             |
| 3   | SIGQUIT     | 종료 + 코어 덤프   | 가능               | Ctrl+\                             |
| 9   | **SIGKILL** | **즉시 강제 종료** | **불가능** ← 16번 정답 | `kill -9`                          |
| 11  | SIGSEGV     | 종료 + 코어 덤프   | 가능               | 잘못된 메모리 접근(segmentation fault)     |
| 15  | **SIGTERM** | 종료           | 가능               | `kill`의 **기본값**. 정상 종료 요청          |
| 17  | SIGCHLD     | 무시           | 가능               | 자식 프로세스 종료 알림                      |
| 18  | SIGCONT     | 재개           | 가능               | 정지된 프로세스 계속 실행 (`fg`/`bg`)         |
| 19  | **SIGSTOP** | **일시 정지**    | **불가능**          | `kill -STOP`                       |
| 20  | SIGTSTP     | 일시 정지        | 가능               | **Ctrl+Z** (terminal stop)         |

> 번호는 아키텍처마다 다를 수 있음. 위 표는 x86/ARM 리눅스 기준이며 시험도 이 값을 씀. `kill -l`로 전체 목록 확인 가능.

**왜 SIGKILL과 SIGSTOP만 가로챌 수 없는가** — 이 둘까지 프로그램이 막아버리면 관리자가 폭주한 프로세스를 멈출 방법이 사라짐. 커널이 최후 수단으로 남겨둔 것임.

**실무 감각** — `kill -9`를 습관적으로 쓰면 안 됨. SIGKILL은 프로세스에 전달조차 되지 않고 커널이 바로 죽이므로, 임시 파일 정리·버퍼 flush·소켓 정상 종료가 전부 생략됨. **먼저 SIGTERM(기본), 안 되면 SIGKILL** 순서가 원칙임.

```bash
kill 1234              # SIGTERM(15) — 기본. 정상 종료 요청
kill -HUP 1234         # = kill -1  설정 재적재
kill -9 1234           # SIGKILL   최후 수단
killall httpd          # 이름으로 모두에게 전송
pkill -u kim           # 조건(사용자)으로 전송
kill -l                # 시그널 목록 전체 출력
```

### 3-10. X 윈도 시스템 구조

> 17번 정답(①) — "X 윈도 내용 정리 필요" 요청 · 18번 오답(③ GNOME 선택, 정답 ② GDM)

**X 윈도의 서버/클라이언트는 직관과 반대임 — 이게 시험 함정의 전부임.**

| 구성 요소       | 담당                                       | 위치 감각              |
| ----------- | ---------------------------------------- | ------------------ |
| **X 서버**    | **디스플레이 하드웨어 제어** — 화면 출력, 키보드·마우스 입력 수집 | 사용자가 **앉아 있는** 컴퓨터 |
| **X 클라이언트** | **응용 프로그램** — 그려달라고 요청하는 쪽               | 어디서 실행되든 상관없음      |

즉 "내 노트북이 X 서버, 원격 서버에서 돌아가는 프로그램이 X 클라이언트"임. 화면(자원)을 **제공**하는 쪽이 서버이기 때문임. 이 구조 덕분에 **네트워크 투명성**(network transparency)이 성립함 — 원격에서 실행한 프로그램의 창이 내 화면에 뜸.

```bash
ssh -X user@server     # X11 포워딩. 원격 GUI 앱을 로컬 화면에 표시
echo $DISPLAY          # :0.0  — 호스트:디스플레이번호.화면번호
```

**계층 구조 — 18번의 정답 근거:**

| 계층                  | 역할                             | 예시                                        |
| ------------------- | ------------------------------ | ----------------------------------------- |
| **X 서버 / 디스플레이 서버** | 하드웨어 추상화, 프로토콜 처리              | X.Org(X11), **Wayland**                   |
| **디스플레이 매니저(DM)**   | **그래픽 로그인 화면** 제공, 인증 후 세션 시작  | **GDM**(GNOME), SDDM(KDE), LightDM, XDM   |
| **윈도 매니저(WM)**      | 창 테두리·이동·크기 조절·최소화             | **Mutter**(GNOME), KWin(KDE), i3, Openbox |
| **데스크톱 환경(DE)**     | WM + 파일관리자 + 패널 + 기본 앱의 **묶음** | **GNOME**, KDE Plasma, **Xfce**, LXDE     |

18번은 "그래픽 로그인 화면 + 인증 후 세션 시작" = **디스플레이 매니저**를 물었음. GNOME은 데스크톱 환경(묶음)이지 로그인 화면 자체가 아님. **G**NOME의 DM이 **GDM**(GNOME Display Manager)이라는 이름 관계로 기억하면 됨.

**Wayland는 X11의 상위 버전이 아니라 대체 프로토콜**임(17번 ③ 오답 근거). X11의 누적된 복잡성을 버리고 새로 설계했으며, 서버/클라이언트 분리 대신 컴포지터가 통합 담당함. Rocky 9·Ubuntu 최신 버전은 기본이 Wayland이고 X11은 호환 모드(XWayland)로 남아 있음.

### 3-11. 서브넷 마스크와 호스트 개수 계산

> 20번 정답(④ 62) — "서브넷 마스크 표현 방식?" 요청

**서브넷 마스크**는 IP 주소 32비트 중 **어디까지가 네트워크 부분이고 어디부터가 호스트 부분인지** 구분하는 비트 마스크임. 1이 연속된 부분이 네트워크, 0이 연속된 부분이 호스트임.

두 가지 표기 방식이 있고 **같은 것을 다르게 쓴 것뿐임**:

```
점 십진 표기(dotted decimal) : 255.255.255.192
CIDR 표기(prefix length)     : /26          ← 1 비트의 개수

255.255.255.192 을 2진수로 펼치면
11111111.11111111.11111111.11000000
└────────── 26개의 1 ──────┘└ 6개의 0 ┘
   네트워크 부분(26비트)      호스트 부분(6비트)
```

**호스트 개수 공식 — `2^(호스트 비트 수) - 2`**

`-2`를 하는 이유:
- 호스트 비트가 **전부 0**인 주소 = **네트워크 주소**(그 서브넷 자체를 가리킴)
- 호스트 비트가 **전부 1**인 주소 = **브로드캐스트 주소**(서브넷 전체에 방송)

20번 계산: 호스트 비트 6개 → `2^6 - 2 = 64 - 2 = **62**`

**자주 나오는 마스크 값 — 외워두면 계산이 없어짐:**

| CIDR | 점 십진            | 마지막 옥텟 2진수 | 총 주소 | 할당 가능 호스트         |
| ---- | --------------- | ---------- | ---- | ----------------- |
| /24  | 255.255.255.0   | 00000000   | 256  | **254**           |
| /25  | 255.255.255.128 | 10000000   | 128  | **126**           |
| /26  | 255.255.255.192 | 11000000   | 64   | **62**            |
| /27  | 255.255.255.224 | 11100000   | 32   | **30**            |
| /28  | 255.255.255.240 | 11110000   | 16   | **14**            |
| /29  | 255.255.255.248 | 11111000   | 8    | **6**             |
| /30  | 255.255.255.252 | 11111100   | 4    | **2** (라우터 간 링크용) |

마지막 옥텟 값이 `128 / 192 / 224 / 240 / 248 / 252`로 이어지는 것만 기억하면 됨(앞 값에 다음 비트를 더해가는 수열).

**192.168.10.100 / 255.255.255.192 의 소속 서브넷 구하기** — 블록 크기 64 단위로 끊음:

```
0~63 · 64~127 · 128~191 · 192~255
100 은 64~127 구간에 속함
  네트워크 주소   : 192.168.10.64
  사용 가능 범위  : 192.168.10.65 ~ 192.168.10.126   (62개)
  브로드캐스트    : 192.168.10.127
```

### 3-11-1. IP 주소 클래스 — 구분 기준과 목적

#### 무엇을 기준으로 나눴는가 — 첫 옥텟의 **선두 비트**

클래스는 10진수 범위로 나눈 것이 아니라 **첫 옥텟 맨 앞의 비트 패턴**으로 나눈 것임. 10진수 범위는 그 결과일 뿐임.

| 클래스 | 선두 비트 | 첫 옥텟 2진수 범위 | 첫 옥텟 10진수 | 전체 주소 공간 비중 |
| --- | --- | --- | --- | --- |
| **A** | **`0`** | `0`0000000 ~ `0`1111111 | 0 ~ 127 | **50%** (2^31개) |
| **B** | **`10`** | `10`000000 ~ `10`111111 | 128 ~ 191 | 25% |
| **C** | **`110`** | `110`00000 ~ `110`11111 | 192 ~ 223 | 12.5% |
| **D** | **`1110`** | `1110`0000 ~ `1110`1111 | 224 ~ 239 | 6.25% |
| **E** | **`1111`** | `1111`0000 ~ `1111`1111 | 240 ~ 255 | 6.25% |

**경계값을 2진수로 펼치면 규칙이 그대로 드러남** (VM 실측):

```
 10 = 00001010     ← 0 으로 시작 → A
126 = 01111110     ← 0 으로 시작 → A
127 = 01111111     ← 0 으로 시작 (A 범위이나 루프백으로 예약)
128 = 10000000     ← 10 으로 시작 → B 시작점
191 = 10111111     ← 10 으로 시작 → B 끝점
192 = 11000000     ← 110 으로 시작 → C 시작점
223 = 11011111     ← 110 으로 시작 → C 끝점
224 = 11100000     ← 1110 으로 시작 → D 시작점
239 = 11101111     ← 1110 으로 시작 → D 끝점
240 = 11110000     ← 1111 으로 시작 → E 시작점
```

- **127/128, 191/192, 223/224, 239/240 이 경계인 이유** = 그 지점에서 선두 비트가 하나 늘어나기 때문
- 외울 때는 10진수 8개를 암기하는 대신 **`0` → `10` → `110` → `1110` → `1111`** 순서만 기억
	- 각 단계에서 남은 공간이 절반씩 줄어듦 → 50% · 25% · 12.5% · 6.25% · 6.25%
- 이 방식은 **접두 부호(prefix code)** 구조여서, 앞에서부터 비트를 읽다가 처음 `0` 을 만나는 위치로 클래스가 즉시 확정됨

#### 왜 나눴는가 — 목적 두 가지

**목적 1. 서브넷 마스크 없이 주소만으로 네트워크·호스트 경계를 판별**

1981년 IPv4 설계(RFC 791) 당시에는 서브넷 마스크라는 개념 자체가 없었음. 라우터가 주소를 보고 **"어디까지가 네트워크 부분인가"** 를 스스로 알아내야 했고, 그 판단 근거로 선두 비트를 쓴 것임.

| 클래스 | 네트워크 부 | 호스트 부 | 기본 마스크 |
| --- | --- | --- | --- |
| A | **첫 1옥텟** (8비트) | 나머지 3옥텟 (24비트) | `/8` = 255.0.0.0 |
| B | **첫 2옥텟** (16비트) | 나머지 2옥텟 (16비트) | `/16` = 255.255.0.0 |
| C | **첫 3옥텟** (24비트) | 나머지 1옥텟 (8비트) | `/24` = 255.255.255.0 |

- 주소 `10.1.2.3` → 선두 비트 `0` → A 클래스 → **네트워크는 `10.0.0.0`, 호스트는 `1.2.3`** 으로 즉시 확정
- 라우팅 테이블에 마스크를 함께 저장할 필요가 없어짐 → 이 방식을 **클래스풀(classful) 라우팅**이라 부름

**목적 2. 조직 규모별 주소 배분**

네트워크 부의 길이가 다르므로 **"네트워크를 몇 개 만들 수 있는가"** 와 **"한 네트워크에 호스트를 몇 대 둘 수 있는가"** 가 정반대로 움직임.

| 클래스 | 네트워크 개수 | 네트워크당 호스트 수 | 배분 대상 |
| --- | --- | --- | --- |
| **A** | **126개** (2^7 − 2) | **16,777,214대** (2^24 − 2) | 초대형 조직·국가 기관 |
| **B** | **16,384개** (2^14) | **65,534대** (2^16 − 2) | 대학·대기업 |
| **C** | **2,097,152개** (2^21) | **254대** (2^8 − 2) | 소규모 조직 |

- 네트워크 개수 계산 — **선두 고정 비트를 뺀 나머지**가 네트워크 식별에 쓰임
	- A: 8비트 중 선두 `0` 1개 고정 → 2^7 = 128개, 여기서 **`0`(예약)과 `127`(루프백)을 제외해 126개**
	- B: 16비트 중 선두 `10` 2개 고정 → 2^14 = 16,384개
	- C: 24비트 중 선두 `110` 3개 고정 → 2^21 = 2,097,152개
- 호스트 수에서 **−2** 는 네트워크 주소·브로드캐스트 주소 제외분 (3-11 본절 참조)

#### 왜 지금은 쓰지 않는가 — CIDR 로의 전환

클래스 방식은 **주소 낭비가 구조적**이었음.

| 상황 | 클래스 방식의 결과 |
| --- | --- |
| 호스트 500대가 필요한 조직 | C(254대)로는 부족 → **B(65,534대)를 통째로 할당** → 65,000여 개 사장 |
| 호스트 2대만 필요한 라우터 간 링크 | 최소 단위가 C(254대) → 252개 사장 |

- 1993년 **CIDR**(Classless Inter-Domain Routing, RFC 1519) 도입으로 클래스 개념 폐기
	- 마스크를 주소와 **함께 명시**하는 `/26` 방식으로 전환 → 8비트 단위 제약 소멸
	- 필요한 크기만큼 잘라 쓰는 **VLSM**(가변 길이 서브넷 마스크) 가능
	- 여러 네트워크를 하나로 합쳐 라우팅 테이블을 줄이는 **슈퍼네팅** 가능
- **현재 라우터·OS 는 전부 클래스리스** → 클래스는 시험·교재에만 남은 역사적 개념
	- 20번 문제의 `255.255.255.192`(/26)도 클래스로는 표현 불가능한 마스크임
	- 즉 **"클래스로 나눈 뒤 서브네팅한다"가 아니라, 처음부터 마스크로 경계를 정하는 것**이 실제 동작

#### 특수 목적 대역 — 클래스와 별개로 예약

| 대역 | 용도 | 비고 |
| --- | --- | --- |
| `0.0.0.0/8` | 「이 네트워크」 | `0.0.0.0` 단독은 「모든 주소」 의미로도 사용 |
| **`127.0.0.0/8`** | **루프백**(자기 자신) | **A 클래스 범위이나 통신용에서 제외** → A 가 126개인 이유 |
| `169.254.0.0/16` | 링크 로컬 (APIPA) | DHCP 실패 시 자동 할당 |
| `100.64.0.0/10` | 통신사 CGNAT | RFC 6598 |
| `224.0.0.0/4` | **멀티캐스트** (D 클래스 전체) | 특정 그룹에 동시 전송 |
| `240.0.0.0/4` | **예약** (E 클래스 전체) | 미사용. `255.255.255.255` 는 제한 브로드캐스트 |

**루프백이 `/8` 전체를 차지함** — `127.0.0.1` 한 주소가 아니라 `127.0.0.0 ~ 127.255.255.255` 1,677만 개가 전부 루프백임 (VM 실측):

```bash
$ ip route show table local
local 127.0.0.0/8 dev lo proto kernel scope host src 127.0.0.1
local 127.0.0.1   dev lo proto kernel scope host src 127.0.0.1
broadcast 127.255.255.255 dev lo proto kernel scope link src 127.0.0.1
```

- `ping 127.1.2.3` 도 자기 자신에게 도달함 → 루프백 대역 전체가 `lo` 로 라우팅되기 때문

#### 사설 IP(RFC 1918) — 클래스별로 하나씩 배정

인터넷에 라우팅되지 않는 내부 전용 대역임. **클래스마다 하나씩** 떼어둔 구조라 표가 클래스와 나란히 놓임.

| 클래스 | 사설 대역 | CIDR | 포함 네트워크 수 | 주소 개수 |
| --- | --- | --- | --- | --- |
| A | `10.0.0.0` ~ `10.255.255.255` | **`10.0.0.0/8`** | A 네트워크 1개 | 약 1,677만 |
| B | `172.16.0.0` ~ `172.31.255.255` | **`172.16.0.0/12`** | B 네트워크 **16개** | 약 104만 |
| C | `192.168.0.0` ~ `192.168.255.255` | **`192.168.0.0/16`** | C 네트워크 **256개** | 65,536 |

- **`172.16.0.0/12` 의 범위가 헷갈리는 지점** — `/12` 이므로 `172.16` ~ `172.31` 까지 16개 블록임
	- `172.32.x.x` 는 사설이 아님 → 시험 함정으로 출제됨
- 사설 IP 는 NAT 를 거쳐야 외부와 통신 가능
- 실습 VM 도 사설 대역 사용 (VM 실측)

```bash
$ ip -br addr
lo       UNKNOWN  127.0.0.1/8            # 루프백
enp0s1   UP       192.168.64.3/24        # C 클래스 사설 대역, /24 마스크
```

#### 시험 대비 정리

| 묻는 방식 | 답하는 근거 |
| --- | --- |
| "첫 옥텟이 172인 주소의 클래스는?" | 172 = `10`101100 → 선두 `10` → **B** |
| "A 클래스 네트워크 개수는?" | 2^7 = 128, `0`·`127` 제외 → **126** |
| "C 클래스 호스트 개수는?" | 2^8 − 2 = **254** |
| "127.0.0.1 의 클래스는?" | 범위상 A 이나 **루프백 예약** → 통신용 A 에서 제외 |
| "192.168.5.0 은 사설인가?" | `192.168.0.0/16` 범위 → **사설** |
| "172.32.1.1 은 사설인가?" | `172.16~172.31` 밖 → **공인** |
| "224.0.0.5 의 용도는?" | D 클래스 → **멀티캐스트** |

## 4. 오답노트 — 2과목 리눅스 시스템 관리

### 4-1. 계정 생성·수정 명령과 옵션

> 21번 오답 — ④(`-c`)를 골랐으나 정답은 ①(`-s`). "직접 실행해 볼 명령어·옵션 총정리 필요" 요청

**`useradd` 주요 옵션** — 대부분 **영어 단어의 첫 글자**임. 그 연결을 잡으면 외울 것이 없음.

| 옵션 | 원어 | 의미 | 예시 |
| --- | --- | --- | --- |
| `-u` | **u**id | UID 지정 | `useradd -u 1500 kim` |
| `-g` | **g**roup | **1차(기본) 그룹** 지정 | `useradd -g dev kim` |
| `-G` | **G**roups | **보조 그룹** 지정(쉼표 구분) | `useradd -G wheel,docker kim` |
| `-d` | **d**irectory | 홈 디렉터리 경로 지정 | `useradd -d /data/kim kim` |
| `-s` | **s**hell | **로그인 셸 지정** ← 21번 정답 | `useradd -s /bin/bash kim` |
| `-c` | **c**omment | 설명(GECOS 필드, 보통 실명) | `useradd -c "Kim Dev" kim` |
| `-m` | **m**ake home | 홈 디렉터리 생성(데비안 계열에서 필수) | `useradd -m kim` |
| `-M` | no **M**ake home | 홈 디렉터리 생성 안 함 | |
| `-e` | **e**xpire | 계정 만료일 (YYYY-MM-DD) | `useradd -e 2026-12-31 kim` |
| `-f` | **f**inactive | 패스워드 만료 후 계정 비활성까지 유예 일수 | |
| `-D` | **D**efault | 기본값 조회·변경 (`/etc/default/useradd`) | `useradd -D` |
| `-r` | **r**system | 시스템 계정 생성(UID를 시스템 범위에서 할당) | |

**`usermod`** — 기존 계정 수정. 옵션은 `useradd`와 거의 같고 **`-a` 하나가 결정적임**.

```bash
usermod -aG devops kim     # -a = append. 기존 보조 그룹 유지하며 devops 추가  ← 25번 정답
usermod  -G devops kim     # ⚠ 위험. 기존 보조 그룹을 전부 버리고 devops 로 "교체"
usermod  -g devops kim     # 1차 그룹 자체를 devops 로 변경
usermod  -L kim            # Lock   — 패스워드 앞에 ! 를 붙여 잠금
usermod  -U kim            # Unlock — 잠금 해제
usermod  -s /sbin/nologin kim   # 로그인 셸 박탈(서비스 계정화)
usermod  -d /data/kim -m kim    # 홈 이동 + -m 으로 기존 내용까지 이사
```

`-a`는 **반드시 `-G`와 함께**만 쓰임. `usermod -aG`는 통째로 하나의 숙어로 외우는 것이 안전함.

**`userdel`**

```bash
userdel kim        # 계정만 삭제. 홈 디렉터리와 메일 스풀은 남음
userdel -r kim     # -r = remove. 홈 디렉터리·메일 스풀까지 삭제
userdel -f kim     # 로그인 중이어도 강제 삭제
```

**확인 명령 — 실습 시 반드시 이 세트로 검증할 것:**

```bash
id kim                     # UID, GID, 소속 그룹 전부
groups kim                 # 소속 그룹 이름만
getent passwd kim          # /etc/passwd 항목 (NIS/LDAP 포함 조회)
grep '^kim:' /etc/passwd /etc/shadow /etc/group
finger kim / chfn kim      # GECOS 필드 조회·수정
```

### 4-2. 계정 관련 /etc 파일 4종 전수 해부

> 22번 정답(③) — "/etc/passwd 총정리 필요, 1차 그룹이 뭔지?" 요청 · 23번·24번 무응답

#### `/etc/passwd` — 계정 기본 정보 (모든 사용자 읽기 가능)

```
kim:x:1001:1001:Kim Dev:/home/kim:/bin/bash
 1   2   3    4     5        6        7
```

| # | 필드 | 값 | 설명 |
| --- | --- | --- | --- |
| 1 | 로그인명 | `kim` | 사용자 계정 이름 |
| 2 | 패스워드 | `x` | **`x`는 "실제 해시는 `/etc/shadow`에 있음"이라는 표시.** 예전엔 여기 해시가 직접 들어갔음 |
| 3 | **UID** | `1001` | User ID. 0=root, 1~999=시스템 계정, 1000~=일반 사용자(RHEL 계열) |
| 4 | **GID** | `1001` | **1차(기본) 그룹의 GID** ← 22번 정답 |
| 5 | GECOS | `Kim Dev` | 설명/실명. `useradd -c`, `chfn`으로 설정 |
| 6 | 홈 디렉터리 | `/home/kim` | 로그인 직후의 작업 디렉터리 |
| 7 | 로그인 셸 | `/bin/bash` | **`/sbin/nologin`·`/bin/false`면 로그인 불가**(서비스 계정) |

**1차 그룹(primary group)이란?** — 사용자가 **파일을 새로 만들 때 자동으로 붙는 그룹**임. 사용자는 그룹에 여러 개 속할 수 있지만 1차 그룹은 **정확히 하나**임.

| 구분 | 1차(기본) 그룹 | 보조(2차) 그룹 |
| --- | --- | --- |
| 개수 | **딱 1개** | 0개 이상 여러 개 |
| 저장 위치 | **`/etc/passwd` 4번째 필드** | **`/etc/group`의 멤버 목록** |
| 역할 | 새로 만든 파일의 소유 그룹이 됨 | 그 그룹에 부여된 권한을 추가로 획득 |
| 변경 | `usermod -g` | `usermod -aG`, `gpasswd -a` |
| 세션 중 전환 | `newgrp 그룹명` | — |

```bash
$ id kim
uid=1001(kim) gid=1001(kim) groups=1001(kim),10(wheel),1002(dev)
              ^^^^^^^^^^^^ 1차 그룹        ^^^^^^^^^^^^^^^^^ 보조 그룹
$ touch newfile && ls -l newfile
-rw-r--r--. 1 kim kim 0 Sep 6 10:00 newfile
                  ^^^ 1차 그룹이 자동으로 붙음
```

RHEL 계열은 **UPG**(User Private Group) 정책을 씀 — 사용자를 만들면 같은 이름의 그룹을 함께 만들어 1차 그룹으로 지정함. 위에서 `kim`의 1차 그룹이 `kim`인 이유임. umask 002를 안전하게 쓰기 위한 설계임.

#### `/etc/shadow` — 패스워드 해시와 만료 정책 (**root만 읽기 가능**, 권한 000 또는 640)

```
kim:$6$xyz...$abc...:19600:0:90:7:14:20000:
 1        2            3   4  5 6  7   8   9
```

| # | 필드 | 설명 |
| --- | --- | --- |
| 1 | 로그인명 | |
| 2 | **암호화된 패스워드** | **`$6$` = SHA-512**, `$5$`=SHA-256, `$1$`=MD5, `$y$`=yescrypt.<br>**`!` 또는 `!!` = 잠김(locked)**, **`*` = 로그인 불가(서비스 계정)**, **빈 값 = 패스워드 없이 로그인** ← 23번 정답 |
| 3 | 마지막 변경일 | **1970-01-01부터의 일수** |
| 4 | 최소 사용 기간 | 이 일수 안에는 재변경 불가 (0=제한 없음) |
| 5 | **최대 사용 기간** | 이 일수가 지나면 변경 강제 (`PASS_MAX_DAYS`) |
| 6 | 경고 기간 | 만료 며칠 전부터 경고 표시 |
| 7 | 비활성 유예 | 만료 후 이 일수가 더 지나면 계정 잠금 |
| 8 | 계정 만료일 | 1970-01-01부터의 일수. 이 날 이후 로그인 불가 |
| 9 | 예약 | 미사용 |

**함정** — 2번 필드가 해시, **3번 필드가 마지막 변경일**임. 이 둘을 바꿔 묻는 선지가 23번에 그대로 나왔음.

```bash
chage -l kim         # 위 만료 정보를 사람이 읽는 형태로 출력  ← 64번 정답
passwd -S kim        # Status. 한 줄 요약 (PS=정상, LK=잠김, NP=패스워드 없음)
```

#### `/etc/group` — 그룹 정보

```
dev:x:1002:kim,lee,park
 1  2  3        4
```

| # | 필드 | 설명 |
| --- | --- | --- |
| 1 | 그룹명 | |
| 2 | 패스워드 | `x` (해시는 `/etc/gshadow`) |
| 3 | **GID** | Group ID |
| 4 | **멤버 목록** | **보조 그룹으로 속한 사용자만** 쉼표로 나열. **1차 그룹으로 속한 사용자는 여기 안 나옴** |

마지막 문장이 중요함. `kim`의 1차 그룹이 `kim`이라면 `/etc/group`의 `kim` 줄 멤버 목록은 **비어 있음**. 1차 소속은 `/etc/passwd`가 관리하기 때문임.

#### `/etc/login.defs` — 계정 정책 **기본값** (24번 정답 ④)

`useradd`가 옵션 없이 실행될 때 참조하는 시스템 전역 기본값임.

| 항목 | 의미 |
| --- | --- |
| `UID_MIN` / `UID_MAX` | 일반 사용자 UID 자동 할당 범위 (보통 1000 / 60000) |
| `GID_MIN` / `GID_MAX` | 일반 그룹 GID 범위 |
| `SYS_UID_MIN` / `SYS_UID_MAX` | 시스템 계정 UID 범위 (201~999) |
| `PASS_MAX_DAYS` | 패스워드 최대 사용 일수 (기본 99999) |
| `PASS_MIN_DAYS` | 최소 사용 일수 |
| `PASS_WARN_AGE` | 만료 경고 시작일 |
| `CREATE_HOME` | 홈 디렉터리 자동 생성 여부 |
| `UMASK` | 신규 계정의 기본 umask |
| `ENCRYPT_METHOD` | 패스워드 해시 알고리즘 (SHA512 등) |

관련 파일과 헷갈리지 말 것:

| 파일 | 역할 |
| --- | --- |
| `/etc/login.defs` | 계정 정책 **기본값** |
| `/etc/default/useradd` | `useradd`의 기본 셸·홈 베이스·스켈레톤 경로 (`useradd -D`로 조회) |
| `/etc/skel/` | **s**keleton. 홈 디렉터리 생성 시 **복사되는 원본 파일들**(`.bashrc`, `.bash_profile`) |
| `/etc/securetty` | root가 콘솔 로그인할 수 있는 tty 목록 |

### 4-3. 그룹 관리 명령

> 26번 무응답 — 정답 ②(`groupdel`이 소속 사용자까지 삭제 — 틀린 설명)

```bash
groupadd dev                 # 그룹 생성
groupadd -g 2000 dev         # GID 지정 생성
groupmod -n newdev dev       # -n = new name. 그룹 이름 변경
groupmod -g 2500 dev         # GID 변경
groupdel dev                 # 그룹만 삭제. 사용자 계정은 건드리지 않음 ← 26번 정답 근거
gpasswd -a kim dev           # -a = add.    kim 을 dev 에 추가
gpasswd -d kim dev           # -d = delete. kim 을 dev 에서 제거
gpasswd -A kim dev           # -A = Admin.  kim 을 dev 의 그룹 관리자로 지정
newgrp dev                   # 현재 세션의 1차 그룹을 dev 로 전환(새 서브셸이 뜸)
```

**`groupdel`의 정확한 동작** — 그룹 자체만 지움. 사용자 계정은 그대로 남음. 단, **그 그룹을 1차 그룹으로 쓰는 사용자가 있으면 삭제가 거부됨**(`cannot remove the primary group of user 'kim'`). 이 경우 먼저 `usermod -g`로 사용자의 1차 그룹을 옮겨야 함.

### 4-4. 퍼미션 8진수 표기법

> 27번 정답(④ 651) — "각 권한 8진수 표기 필요: 124?" 요청. **124로 오해했으므로 계산법을 다시 잡아야 함**

각 권한에 **고정된 가중치**가 있고, 그것을 **더하면** 자릿수 하나가 됨.

```
r (read,  읽기)  = 4
w (write, 쓰기)  = 2
x (execute,실행) = 1
- (없음)         = 0
```

`124`로 답한 것은 `r=1, w=2, x=4`로 순서를 거꾸로 잡은 결과로 보임. **r이 가장 큰 4**임. 2진수 자리값(`rwx` = `100 010 001`)이라고 생각하면 r이 최상위 비트라 4가 되는 것이 자연스러움.

**27번 계산 — `-rw-r-x--x`:**

```
-   rw-      r-x      --x
↑    ↑        ↑        ↑
유형 소유자   그룹     기타(others)
     4+2+0=6  4+0+1=5  0+0+1=1
                          → 651
```

맨 앞 한 글자는 **권한이 아니라 파일 유형**임. 8진수 계산에서 제외해야 함.

| 기호 | 파일 유형 |
| --- | --- |
| `-` | 일반 파일 |
| `d` | 디렉터리(**d**irectory) |
| `l` | 심볼릭 링크(**l**ink) |
| `b` | 블록 장치(**b**lock, 디스크) |
| `c` | 문자 장치(**c**haracter, 터미널·`/dev/null`) |
| `p` | 명명된 파이프(**p**ipe, FIFO) |
| `s` | 소켓(**s**ocket) |

**8진수 ↔ 기호 대응표 — 통째로 외울 것:**

| 8진수 | 기호 | 8진수 | 기호 |
| --- | --- | --- | --- |
| 0 | `---` | 4 | `r--` |
| 1 | `--x` | 5 | `r-x` |
| 2 | `-w-` | 6 | `rw-` |
| 3 | `-wx` | 7 | `rwx` |

**자주 쓰는 조합:**

| 값 | 기호 | 용도 |
| --- | --- | --- |
| 644 | `rw-r--r--` | 일반 파일 기본값 |
| 755 | `rwxr-xr-x` | 실행 파일·디렉터리 기본값 |
| 600 | `rw-------` | 개인 설정 파일(`~/.ssh/config`) |
| 700 | `rwx------` | 개인 전용 디렉터리(`~/.ssh`) |
| 400 | `r--------` | SSH 개인키(`~/.ssh/id_rsa`, 600도 가능) |
| 777 | `rwxrwxrwx` | **절대 쓰지 말 것** |
| 000 | `---------` | `/etc/shadow` |

**`chmod` 두 가지 표기법:**

```bash
chmod 755 script.sh              # 8진수(절대) — 기존 권한을 전부 덮어씀
chmod u+x script.sh              # 기호(상대) — u=user g=group o=others a=all
chmod go-w file.txt              # + 부여 / - 회수 / = 지정
chmod u=rw,go=r file.txt         # = 는 해당 대상의 권한을 통째로 설정
chmod -R 755 /var/www            # -R = recursive. 하위 전체
chmod --reference=a.txt b.txt    # a.txt 와 동일한 권한으로 맞춤
```

**디렉터리에서 권한의 의미가 달라짐 — 시험 빈출:**

| 권한 | 파일에서 | **디렉터리에서** |
| --- | --- | --- |
| `r` | 내용 읽기 | **목록 조회**(`ls`) |
| `w` | 내용 수정 | **내부 파일 생성·삭제·이름변경** |
| `x` | 실행 | **진입**(`cd`) 및 내부 파일 접근 |

디렉터리에 `x`가 없으면 `r`이 있어도 그 안의 파일에 접근할 수 없음. 반대로 `x`만 있으면 `ls`는 안 되지만 정확한 이름을 알면 접근은 됨. **파일 삭제 권한은 파일이 아니라 그 파일이 든 디렉터리의 `w`가 결정함** — 이것이 스티키 비트가 필요한 이유임.

`chown`/`chgrp`도 함께:

```bash
chown kim file.txt           # 소유자 변경
chown kim:dev file.txt       # 소유자:그룹 동시 변경
chown :dev file.txt          # 그룹만 변경
chgrp dev file.txt           # 그룹만 변경(전용 명령)
chown -R kim:dev /data       # 재귀
```

소유자 변경은 **root만** 가능함(일반 사용자가 자기 파일을 남에게 넘길 수 없음). 그룹 변경은 자기가 속한 그룹으로는 소유자도 가능함.

### 4-5. 특수 권한 — Set-UID·Set-GID·스티키 비트

> 28번 무응답("Set-UID란?") · 29번 무응답("777 앞 비트 의미 모름")

8진수 권한은 사실 **네 자리**임. 평소 생략하던 맨 앞자리가 특수 권한임.

```
chmod 1777 /dir
       ↑└┴┴─ 일반 권한 (소유자/그룹/기타)
       └──── 특수 권한  ← 29번이 묻던 "777 앞 비트"
```

| 값 | 이름 | 대상 | 동작 | 표시 위치 |
| --- | --- | --- | --- | --- |
| **4000** | **Set-UID** (SUID) | 실행 파일 | 실행하는 동안 **파일 소유자의 권한**으로 동작 | 소유자 `x` 자리가 **`s`** |
| **2000** | **Set-GID** (SGID) | 실행 파일 | 실행하는 동안 **파일 그룹의 권한**으로 동작 | 그룹 `x` 자리가 **`s`** |
| 2000 | Set-GID | **디렉터리** | 그 안에 만든 파일이 **디렉터리의 그룹**을 상속 (협업 폴더) | 그룹 `x` 자리가 **`s`** |
| **1000** | **스티키 비트** | 디렉터리 | **자기가 만든 파일만 삭제 가능** | 기타 `x` 자리가 **`t`** |

#### Set-UID를 왜 쓰는가 — `passwd`가 정답 그 자체

일반 사용자가 자기 패스워드를 바꾸려면 `/etc/shadow`를 써야 함. 그런데 `/etc/shadow`는 권한이 `000`이고 소유자가 root임. 일반 사용자는 읽을 수조차 없음.

```bash
$ ls -l /usr/bin/passwd
-rwsr-xr-x. 1 root root 32656 ... /usr/bin/passwd
   ↑
   여기가 x 가 아니라 s  → Set-UID 설정됨

$ ls -l /etc/shadow
----------. 1 root root 1234 ... /etc/shadow
```

`passwd` 실행 파일에 Set-UID가 걸려 있어서, kim이 실행해도 **프로세스의 EUID(Effective UID)가 root가 됨.** 그래서 `/etc/shadow`를 갱신할 수 있음. 실행이 끝나면 권한도 사라짐. **딱 필요한 순간에만 권한을 빌려주는 장치**임.

| 구분 | 원어 | 의미 |
| --- | --- | --- |
| **RUID** | Real UID | 실제로 실행한 사용자 (kim = 1001) |
| **EUID** | Effective UID | **권한 판정에 실제로 쓰이는 ID** (Set-UID로 0=root가 됨) |

**Set-UID는 보안 위험이기도 함.** 그 프로그램에 취약점이 있으면 공격자가 root 권한을 얻음(권한 상승). 그래서 보안 점검 시 SUID 파일 전수 조사를 함:

```bash
find / -perm -4000 -type f 2>/dev/null     # Set-UID 파일 전부 찾기
find / -perm -2000 -type f 2>/dev/null     # Set-GID 파일
find / -perm -1000 -type d 2>/dev/null     # 스티키 비트 디렉터리
```

`-perm -4000`에서 앞의 `-`는 "**이 비트를 포함하는**"이라는 뜻임(정확히 일치가 아님).

대표적인 SUID 프로그램: `passwd`, `su`, `sudo`, `mount`, `umount`, `ping`(구버전), `chsh`, `chfn`, `crontab`

#### 스티키 비트를 왜 쓰는가 — `/tmp`가 정답 그 자체

`/tmp`는 모든 사용자가 파일을 만들 수 있어야 하므로 `w` 권한이 열려 있어야 함. 그런데 앞서 본 것처럼 **파일 삭제 권한은 그 파일이 든 디렉터리의 `w`가 결정함.** 즉 `/tmp`가 777이면 kim이 lee의 임시 파일을 지울 수 있음.

스티키 비트는 이 규칙에 **예외**를 만듦 — 이 디렉터리 안에서는 **파일 소유자와 디렉터리 소유자, root만** 삭제·이름변경 가능.

```bash
$ ls -ld /tmp
drwxrwxrwt. 20 root root 4096 Sep 6 10:00 /tmp
         ↑
         기타의 x 자리가 t  → 스티키 비트

$ chmod 1777 /share       # 29번 정답 ①
$ chmod +t   /share       # 기호 표기
```

#### 표시 문자 대문자/소문자 구분 — 함정 문제

| 표시 | 의미 |
| --- | --- |
| `s` (소문자) | 특수 권한 + **실행 권한 있음** (정상) |
| `S` (대문자) | 특수 권한 + **실행 권한 없음** (사실상 무의미, 설정 실수) |
| `t` (소문자) | 스티키 + 기타 실행 권한 있음 |
| `T` (대문자) | 스티키 + 기타 실행 권한 없음 |

```bash
chmod 4755 f  → -rwsr-xr-x   (소문자 s : x 가 살아 있음)
chmod 4655 f  → -rwSr-xr-x   (대문자 S : x 가 없음)
```

#### 정리 — 시험에 나오는 조합

| 명령 | 결과 |
| --- | --- |
| `chmod 4755 file` | Set-UID |
| `chmod 2755 dir` | Set-GID (그룹 상속 협업 디렉터리) |
| `chmod 1777 dir` | 스티키 비트 (`/tmp` 방식) ← 29번 |
| `chmod 6755 file` | Set-UID + Set-GID (4+2) |
| `chmod 0777 dir` | 특수 권한 **없음** |

### 4-6. umask — 기본 권한 계산

> 30번 무응답("umask란?") — 정답 ②(640)

**umask**(user file creation mask)는 새로 만드는 파일·디렉터리에서 **제외할 권한을 지정하는 마스크**임. 부여하는 값이 아니라 **빼는 값**이라는 것이 핵심임.

**기본 최대 권한(base permission)이 파일과 디렉터리가 다름:**

| 대상 | 기본 최대 권한 | 이유 |
| --- | --- | --- |
| **일반 파일** | **666** (`rw-rw-rw-`) | 새 파일에 실행 권한을 자동으로 주면 위험하므로 `x` 제외 |
| **디렉터리** | **777** (`rwxrwxrwx`) | 디렉터리는 `x`(진입 권한)가 없으면 쓸 수 없으므로 포함 |

**30번 계산:**

```
파일     : 666 - 027 = 640  →  rw-r-----   ← 정답 ②
디렉터리 : 777 - 027 = 750  →  rwxr-x---
```

`0027`의 맨 앞 `0`은 특수 권한 자리라 무시하면 됨.

**주의 — 정확히는 뺄셈이 아니라 비트 AND NOT 연산임.** 자릿수마다 빌려오기가 일어나지 않음. 대부분의 시험 문제는 뺄셈으로 풀려도 답이 같지만, `umask 023` 같은 값에서 차이가 남:

```
파일 666, umask 023
  뺄셈으로:  666 - 023 = 643   ← 틀림
  비트연산:  rw-rw-rw- 에서 (---, -w-, -wx) 제거
             = rw- rw- r--  =  664   ← 맞음
```

`w`가 없는 자리에서 `w`를 빼봤자 그대로이기 때문임. **"이미 없는 권한은 더 빠지지 않는다"** 로 기억하면 됨.

```bash
umask              # 현재 값 확인 (0022)
umask -S           # -S = symbolic. u=rwx,g=rx,o=rx 형태로 출력
umask 027          # 현재 셸에서만 변경
```

영구 적용은 `~/.bashrc`(개인) 또는 `/etc/profile`·`/etc/bashrc`(전역)에 적음.

**일반적인 값:**

| umask | 파일 | 디렉터리 | 성격 |
| --- | --- | --- | --- |
| 022 | 644 | 755 | RHEL root 기본. 남이 읽기 가능 |
| 002 | 664 | 775 | RHEL 일반 사용자 기본(UPG 전제). 같은 그룹이 쓰기 가능 |
| 027 | 640 | 750 | 보안 강화. 그룹은 읽기, 타인은 차단 |
| 077 | 600 | 700 | 최고 보안. 본인만 |

### 4-7. ACL — 세밀한 접근 제어

> 31번 오답 — ④(`setfacl -x`)를 골랐으나 정답은 ③(`setfacl -m`). "ACL이란?" 요청

**ACL** = Access Control List(접근 제어 목록). 전통 퍼미션은 **소유자·그룹·기타 딱 셋**에만 권한을 줄 수 있음. "kim은 rw, lee는 r만, park은 접근 금지"처럼 **개인별로 다르게** 주려면 그룹을 계속 만들어야 함. ACL은 파일에 추가 권한 목록을 직접 붙여 이 한계를 해결함.

```bash
getfacl data.txt                   # 조회 (get)
setfacl -m u:lee:rw  data.txt      # -m = modify.  사용자 lee 에게 rw 부여  ← 31번 정답
setfacl -m g:dev:r   data.txt      # 그룹 dev 에게 r 부여
setfacl -m o::---    data.txt      # 기타 사용자 권한 제거
setfacl -x u:lee     data.txt      # -x = remove.  lee 항목 삭제
setfacl -b           data.txt      # -b = remove all. ACL 전부 제거
setfacl -R -m u:lee:rx /data       # -R = recursive
setfacl -d -m u:lee:rw /data       # -d = default. 디렉터리에 기본 ACL(신규 파일 상속)
setfacl -m m::r      data.txt      # mask 설정
```

문법은 **`대상유형:이름:권한`** — `u`=user, `g`=group, `o`=other, `m`=mask.

**31번 선지가 틀린 이유:**
- ① `getfacl -m` — `getfacl`은 **조회 전용**이라 `-m` 옵션이 없음
- ② `chmod u:lee:rw` — **`chmod`는 ACL 문법을 지원하지 않음**
- ④ `setfacl -x` — 명령은 맞지만 `-x`는 **제거**라 "부여"와 반대

**ACL이 걸린 파일은 `ls -l`에 `+`가 붙음** — 시험에 자주 나옴:

```bash
$ ls -l data.txt
-rw-rw----+ 1 kim dev 1024 Sep 6 10:00 data.txt
          ↑
          이 + 가 ACL 존재 표시

$ getfacl data.txt
# file: data.txt
# owner: kim
# group: dev
user::rw-
user:lee:rw-          ← ACL 항목
group::r--
mask::rw-             ← 유효 권한 상한
other::---
```

**mask** 는 소유자와 other를 제외한 모든 항목(명명된 사용자·그룹)의 **권한 상한선**임. mask가 `r--`이면 `user:lee:rw-`라고 적혀 있어도 실제로는 `r--`만 적용됨. `chmod g+w` 등을 하면 mask가 바뀌므로, ACL을 쓰는 파일에 `chmod`를 함부로 쓰면 안 됨.

ACL을 쓰려면 파일시스템에 `acl` 마운트 옵션이 필요하나, ext4·XFS는 요즘 **기본 활성**임.

### 4-8. 파일시스템 종류와 생성·검사 명령

> 32번 정답(④ `mkfs.xfs`) — "XFS란?" 요청

**파일시스템**은 디스크의 빈 공간에 "어디에 무엇을 어떻게 저장할지"의 규칙을 부여한 구조임. 파티션을 나눈 것만으로는 쓸 수 없고 `mkfs`(make filesystem)로 포맷해야 함.

| 파일시스템 | 특징 | 최대 파일/볼륨 크기 | 사용처 |
| --- | --- | --- | --- |
| **ext4** | fourth extended fs. 저널링, 안정성 검증됨, **축소 가능** | 16TB / 1EB | Ubuntu·Debian 기본 |
| **XFS** | SGI가 개발한 **고성능 저널링** fs. 대용량·병렬 I/O에 강함. **확장만 가능, 축소 불가** | 8EB / 8EB | **RHEL·Rocky 9 기본** |
| ext3 | ext2 + 저널링 | 2TB / 32TB | 레거시 |
| ext2 | 저널링 **없음** | | USB 등 소형 매체 |
| Btrfs | 스냅샷·체크섬·내장 RAID | | SUSE 기본 |
| swap | 스왑 영역 전용 | | 가상 메모리 |
| ISO 9660 | CD/DVD 표준 | | 광학 매체 |
| VFAT / NTFS | 윈도 호환 | | USB, 듀얼부팅 |
| tmpfs | 메모리 기반 | | `/dev/shm`, `/run` |
| procfs / sysfs | 가상 fs (디스크 없음) | | `/proc`, `/sys` |

**저널링(journaling)** — 파일을 쓰기 전에 "무엇을 할 것인지"를 저널 영역에 먼저 기록하고 실제 작업을 수행하는 방식임. 정전 등으로 중간에 끊겨도 저널을 보고 복구할 수 있어 `fsck` 시간이 극적으로 짧아짐. ext2에는 없고 ext3부터 도입됨.

**XFS가 RHEL 기본인 이유** — 대용량 파일과 병렬 I/O 성능이 뛰어나고 온라인 확장(`xfs_growfs`)이 가능함. 대신 **축소가 불가능**하다는 제약이 있어 LVM 설계 시 여유 있게 잡지 말고 필요한 만큼만 할당한 뒤 늘려 가는 방식을 씀. 시험에 "축소 불가"가 자주 나옴.

**명령 — 목적별로 확실히 구분할 것(32번 선지가 이걸 물었음):**

| 목적 | ext4 | XFS |
| --- | --- | --- |
| **생성(포맷)** | `mkfs.ext4 /dev/sdb1`<br>`mkfs -t ext4 /dev/sdb1` | **`mkfs.xfs /dev/sdb1`** ← 32번 정답 |
| **검사·복구** | `fsck.ext4 -f /dev/sdb1`<br>`e2fsck -f /dev/sdb1` | **`xfs_repair /dev/sdb1`**<br>(`fsck.xfs`는 아무 일도 안 하는 더미) |
| **레이블 설정** | `e2label /dev/sdb1 DATA` | `xfs_admin -L DATA /dev/sdb1` |
| **확장** | `resize2fs /dev/sdb1` | `xfs_growfs /mount/point` |
| **축소** | `resize2fs /dev/sdb1 10G` | **불가능** |
| **정보 조회** | `dumpe2fs /dev/sdb1` | `xfs_info /mount/point` |
| **튜닝** | `tune2fs -l /dev/sdb1` | `xfs_admin` |

```bash
mount /dev/sdb1 /data              # 연결(마운트)
mount -t xfs -o noatime /dev/sdb1 /data
umount /data                       # 해제  (un**mount**, n 하나임에 주의)
mount -a                           # /etc/fstab 의 모든 항목 마운트
blkid                              # 장치의 UUID·파일시스템 유형 조회
lsblk -f                           # 블록 장치 트리 + 파일시스템 정보
findmnt                            # 마운트 트리 조회
```

**`fsck`는 반드시 언마운트 상태에서** 실행해야 함. 마운트된 채로 검사하면 파일시스템이 손상됨.

> 마운트의 개념은 [[../../QA#B-2. 마운트란 무엇인가]], `lsblk -f` 출력 해설은 [[../../QA#B-1. `lsblk -f` 출력 전체 해설]] 참조.

### 4-9. /etc/fstab 6개 필드와 /etc 주요 설정 파일

> 33번 무응답 — "/etc/fstab? /etc 아래 것들 전부 모르겠음". 정답 ②(fsck 검사 순서)

#### `/etc/fstab` — file systems table

부팅할 때 **자동으로 마운트할 파일시스템 목록**임. `mount -a`가 이 파일을 읽음.

```
UUID=abcd-1234   /data   ext4   defaults   1 2
      1            2      3        4       5 6
```

| # | 필드 | 설명 |
| --- | --- | --- |
| 1 | **장치** | `/dev/sdb1` 또는 **`UUID=...`**(권장) 또는 `LABEL=...`.<br>장치명은 디스크를 추가하면 순서가 바뀔 수 있어 UUID를 씀 |
| 2 | **마운트 지점** | `/data`. swap이면 `swap` |
| 3 | **파일시스템 유형** | `ext4`, `xfs`, `swap`, `nfs`, `iso9660`, `auto` |
| 4 | **마운트 옵션** | 아래 표 참조. `defaults`는 `rw,suid,dev,exec,auto,nouser,async` |
| 5 | **dump 여부** | `dump` 백업 대상인지. `0`=제외, `1`=대상. 요즘은 거의 `0` |
| 6 | **fsck 검사 순서** | **`0`=검사 안 함, `1`=루트(`/`), `2`=그 외.** 부팅 시 검사 순서 ← **33번 정답** |

**5번(dump)과 6번(fsck)을 뒤바꿔 묻는 것이 고정 패턴임.** "다섯 번째=dump, 여섯 번째=fsck 순서"로 외울 것.

주요 마운트 옵션:

| 옵션 | 의미 |
| --- | --- |
| `defaults` | 표준 기본값 묶음 |
| `ro` / `rw` | 읽기 전용 / 읽기·쓰기 |
| `noatime` | 접근 시각(atime) 기록 생략 → **성능 향상** |
| `noexec` | 실행 파일 실행 금지 (`/tmp` 보안 강화) |
| `nosuid` | Set-UID 무시 (보안 강화) |
| `nodev` | 장치 파일 인식 안 함 |
| `auto` / `noauto` | `mount -a` 대상 포함 / 제외 |
| `user` / `nouser` | 일반 사용자 마운트 허용 / 금지 |
| `usrquota`, `grpquota` | 사용자·그룹 쿼터 활성화 |
| `_netdev` | 네트워크가 올라온 뒤 마운트(NFS·iSCSI 필수) |
| `nofail` | 장치가 없어도 부팅 실패시키지 않음 |

**`fstab`을 잘못 쓰면 부팅이 안 됨.** 편집 후 반드시 `mount -a`로 검증해야 함(오류 없으면 안전).

#### `/etc` 주요 설정 파일 — 전수 정리

| 파일 | 역할 |
| --- | --- |

### 4-10. top 화면 전수 해설

> 36번 정답(④) — "전체 옵션과 top 화면 자체 분석 정리 필요" 요청

```
top - 14:32:07 up 3 days,  2:11,  2 users,  load average: 0.15, 0.09, 0.05
Tasks: 142 total,   1 running, 141 sleeping,   0 stopped,   0 zombie
%Cpu(s):  2.3 us,  0.7 sy,  0.0 ni, 96.8 id,  0.2 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :   3823.5 total,   1902.1 free,    721.3 used,   1200.1 buff/cache
MiB Swap:   2048.0 total,   2048.0 free,      0.0 used.   2841.9 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   1234 apache    20   0  412340  22156   8340 S   1.3   0.6   0:03.21 httpd
      1 root      20   0  173880  16920  10520 S   0.0   0.4   0:12.45 systemd
```

**1행 — 시스템 요약** (`uptime` 명령과 동일)

| 항목 | 의미 |
| --- | --- |
| `14:32:07` | 현재 시각 |
| `up 3 days, 2:11` | 부팅 후 경과 시간 |
| `2 users` | 로그인 중인 사용자 수 |
| **`load average: 0.15, 0.09, 0.05`** | **최근 1분·5분·15분 평균 부하.** 실행 가능(runnable) + 디스크 I/O 대기 상태 프로세스의 평균 개수.<br>**CPU 코어 수와 비교해서 해석함** — 4코어에서 4.0이면 포화, 8.0이면 과부하 |

**2행 — 프로세스 상태별 개수**

| 상태 | 기호 | 의미 |
| --- | --- | --- |
| running | `R` | 실행 중 또는 실행 대기 |
| sleeping | `S` | 이벤트를 기다리는 중(대부분이 여기). `D`는 인터럽트 불가 대기(디스크 I/O) |
| stopped | `T` | 정지됨 (Ctrl+Z, SIGSTOP) |
| **zombie** | `Z` | **종료됐지만 부모가 아직 종료 상태를 회수(wait)하지 않은 프로세스.** 메모리는 반납했고 프로세스 테이블 항목만 남음. 많으면 부모 프로그램의 버그 |

**3행 — CPU 사용률 (%Cpu(s))** — 각 약어가 시험에 그대로 나옴

| 약어 | 원어 | 의미 |
| --- | --- | --- |
| `us` | **us**er | 사용자 영역 프로세스가 쓴 시간 |
| `sy` | **sy**stem | 커널 영역(시스템 콜)이 쓴 시간 |
| `ni` | **ni**ce | nice 값이 조정된 사용자 프로세스 |
| **`id`** | **id**le | **유휴**. 이 값이 크면 여유 있음 |
| **`wa`** | **wa**it (I/O wait) | **디스크·네트워크 I/O 대기.** 이 값이 높으면 CPU가 아니라 **디스크가 병목** |
| `hi` | **h**ardware **i**nterrupt | 하드웨어 인터럽트 처리 |
| `si` | **s**oftware **i**nterrupt | 소프트웨어 인터럽트 처리 |
| `st` | **st**eal | **가상 머신**에서 하이퍼바이저가 가져간 시간. 클라우드에서 높으면 호스트 과밀 |

**4~5행 — 메모리**

| 항목 | 의미 |
| --- | --- |
| `total` | 전체 물리 메모리 |
| `free` | 완전히 비어 있는 메모리 |
| `used` | 사용 중 |
| **`buff/cache`** | **버퍼·페이지 캐시.** 디스크 내용을 담아둔 것으로, **필요하면 즉시 회수됨** |
| **`avail Mem`** | **실제로 새 프로세스에 줄 수 있는 양** = free + 회수 가능한 buff/cache.<br>**메모리 여유를 볼 때는 `free`가 아니라 이 값을 봐야 함** |

리눅스는 남는 메모리를 전부 캐시로 씀. `free`가 작다고 메모리가 부족한 것이 아님. **`avail`이 작고 swap `used`가 계속 증가하면** 그때가 진짜 부족임.

**프로세스 목록 열**

| 열 | 의미 |
| --- | --- |
| `PID` | 프로세스 ID |
| `USER` | 실행 사용자 |
| **`PR`** | Priority. 커널 내부 우선순위(보통 `NI + 20`, `rt`는 실시간) |
| **`NI`** | **Nice 값. -20(최우선) ~ 19(최후순위), 기본 0** |
| **`VIRT`** | Virtual. 가상 메모리 총량(실제 안 쓰는 것도 포함, 크게 나오는 게 정상) |
| **`RES`** | Resident. **실제 물리 메모리 점유량 — 실질 사용량은 이것** |
| `SHR` | Shared. 다른 프로세스와 공유하는 메모리 |
| `S` | 상태 (R/S/D/T/Z) |
| `%CPU` | CPU 사용률 |
| `%MEM` | 물리 메모리 사용률 (= RES / total) |
| `TIME+` | 누적 CPU 사용 시간 (1/100초 단위) |
| `COMMAND` | 명령 이름 |

**대화형 키 — 36번이 물은 부분. 대소문자를 구분함**

| 키 | 동작 |
| --- | --- |
| **`k`** | **kill. PID를 입력받아 시그널 전송** ← 36번 정답 ④ |
| `q` | quit. **종료** (①이 "갱신 주기 변경"이라 했으므로 오답) |
| **`M`** | **Memory. 메모리 사용률 정렬** (②가 "CPU 정렬"이라 했으므로 오답) |
| **`P`** | **Processor. CPU 사용률 정렬** (③이 "메모리 정렬"이라 했으므로 오답) |
| `T` | Time. 누적 실행 시간 정렬 |
| `N` | Number(PID) 정렬 |
| `d` 또는 `s` | delay/set. **화면 갱신 주기 변경** |
| `r` | renice. 우선순위 변경 |
| `u` | 특정 사용자만 필터 |
| `c` | 명령의 전체 경로 표시 토글 |
| `1` | **CPU 코어별로 분리 표시** |
| `H` | 스레드 단위 표시 토글 |

### 4-11. cron·at 스케줄링

> 40번 정답(③) — "크론탭 구조 정리 필요" 요청 · 41번 오답(② 선택, 정답 ①)

#### crontab 필드 구조

```
분  시  일  월  요일   실행할 명령
*   *   *   *   *
│   │   │   │   └── 요일 (0~7, 0과 7 모두 일요일, 1=월 … 5=금)
│   │   │   └────── 월   (1~12)
│   │   └────────── 일   (1~31)
│   └────────────── 시   (0~23)
└────────────────── 분   (0~59)
```

**40번 해석 — `30 2 * * 5`:**

```
30  2  *  *  5
분=30, 시=2, 일=매일, 월=매월, 요일=5(금요일)
→ 매주 금요일 02시 30분   ← 정답 ③
```

선지 ①(매월 5일)이 되려면 **세 번째 필드**가 5여야 함(`30 2 5 * *`). **일 필드와 요일 필드의 위치를 헷갈리게 하는 것이 이 유형의 고정 함정임.**

**특수 문자:**

| 기호 | 의미 | 예시 |
| --- | --- | --- |
| `*` | 모든 값 | `* * * * *` = 매분 |
| `,` | 열거 | `0 9,18 * * *` = 매일 09시·18시 |
| `-` | 범위 | `0 9-18 * * *` = 매일 09~18시 정각 |
| `/` | 간격(step) | `*/10 * * * *` = 10분마다 |
| | | `0 */6 * * *` = 6시간마다 |

**주의** — `일`과 `요일`을 **둘 다** 지정하면 **OR 조건**임(둘 중 하나만 맞아도 실행). 나머지 필드는 AND임.

**특수 문자열:**

| 문자열 | 대응 |
| --- | --- |
| `@reboot` | 부팅 시 1회 |
| `@yearly` / `@annually` | `0 0 1 1 *` |
| `@monthly` | `0 0 1 * *` |
| `@weekly` | `0 0 * * 0` |
| `@daily` / `@midnight` | `0 0 * * *` |
| `@hourly` | `0 * * * *` |

#### crontab 명령과 파일

```bash
crontab -e          # edit.   내 crontab 편집 (반드시 이 명령으로. 직접 파일 편집 금지)
crontab -l          # list.   내 crontab 조회
crontab -r          # remove. 내 crontab 전체 삭제 (⚠ 확인 없이 지움)
crontab -u kim -l   # user.   특정 사용자의 crontab (root만)
crontab -i -r       # interactive. 삭제 전 확인
```

| 위치 | 성격 |
| --- | --- |
| `/var/spool/cron/<사용자명>` | **사용자별 crontab 실체** (`crontab -e`가 여기 씀). **5필드** |
| `/etc/crontab` | 시스템 crontab. **사용자 필드가 추가된 6필드** |
| `/etc/cron.d/` | 패키지가 넣는 시스템 cron 조각. 6필드 |
| `/etc/cron.hourly/`, `.daily/`, `.weekly/`, `.monthly/` | **스크립트를 넣기만 하면 주기 실행** |
| `/etc/cron.allow`, `/etc/cron.deny` | 사용 허가·금지 목록.<br>**`allow`가 있으면 거기 적힌 사람만**, 없으면 `deny`에 없는 사람 전원 |
| `/etc/anacrontab` | anacron. **시스템이 꺼져 있어 놓친 작업을 켜진 뒤 보충 실행** (노트북·데스크톱용) |

```
# /etc/crontab 은 사용자 필드가 하나 더 있음
30 2 * * 5 root /usr/local/bin/backup.sh
           ^^^^ 실행 사용자
```

**cron 실행 환경의 함정 — 실무에서 반드시 물림:**
- cron은 **최소한의 환경변수만** 가지고 실행됨. `PATH`가 `/usr/bin:/bin` 정도라 **명령을 절대경로로 써야 함**
- 홈 디렉터리·로케일도 로그인 셸과 다름
- **출력(stdout/stderr)은 계정 메일로 발송됨.** 원치 않으면 `>/dev/null 2>&1`을 붙임
- `%`는 개행으로 해석되므로 `date +\%Y` 처럼 이스케이프해야 함

```bash
30 2 * * 5 /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
```

#### at — 일회성 예약 (41번)

**cron은 반복, at은 단 한 번**이 결정적 차이임.

```bash
at 14:30                    # 대화형 입력 → Ctrl+D 로 종료
at now + 2 hours
at 10:00 tomorrow
at 2026-09-10
at -f script.sh 14:30       # -f = file. 파일로 지정
atq                         # at queue.  대기 목록 조회  ← 41번 정답 근거
at -l                       # atq 와 동일
atrm 3                      # at remove. 작업 번호 3 삭제
at -d 3                     # atrm 과 동일
at -c 3                     # 작업 3의 내용 확인
```

41번 선지가 틀린 이유:
- ② "지정 주기로 반복 실행" — **cron의 설명**임. at은 1회성
- ③ "삭제할 수 없다" — `atrm`으로 삭제 가능
- ④ "표준 출력이 터미널에 즉시 표시" — **메일로 전달됨**(cron과 동일)

`at`이 동작하려면 `atd` 데몬이 떠 있어야 함(`systemctl status atd`). 허가는 `/etc/at.allow`·`/etc/at.deny`가 관리함.

| 구분 | cron | at |
| --- | --- | --- |
| 실행 횟수 | **반복** | **1회** |
| 데몬 | `crond` | `atd` |
| 등록 | `crontab -e` | `at 시각` |
| 조회 | `crontab -l` | `atq` |
| 삭제 | `crontab -r` | `atrm 번호` |
| 저장 위치 | `/var/spool/cron/` | `/var/spool/at/` |
| 허가 파일 | `/etc/cron.allow/deny` | `/etc/at.allow/deny` |

### 4-12. 패키지 관리 명령 총정리

> 42번 오답(④ 선택, 정답 ②) · 43번 오답(④ 선택, 정답 ③) · 44번 정답(④). "옵션 정리 필요", "uninstall?" 요청

#### rpm — RPM Package Manager (레드햇 계열, 저수준)

**의존성을 자동 해결하지 않음.** 단일 패키지 파일을 직접 다룸.

| 옵션 | 원어 | 용도 |
| --- | --- | --- |
| `-i` | **i**nstall | 설치 |
| `-U` | **U**pgrade | 업그레이드 (없으면 설치) |
| `-F` | **F**reshen | 이미 설치된 것만 업그레이드 |
| `-e` | **e**rase | **삭제** ← "uninstall"에 해당하는 것이 이것 |
| `-v` | **v**erbose | 상세 출력 |
| `-h` | **h**ash | 진행 막대(`#`) 표시 |
| `-q` | **q**uery | **조회 모드** (아래 옵션과 조합) |
| `-V` | **V**erify | 설치 후 변조 검증 |

**조회(`-q`) 조합 — 42번의 핵심:**

| 조합 | 의미 |
| --- | --- |
| `rpm -q vim` | 패키지 **이름**으로 설치 여부·버전 조회 |
| `rpm -qa` | **a**ll. 설치된 전체 패키지 목록 |
| `rpm -ql vim` | **l**ist. 그 패키지가 설치한 **파일 목록** |
| **`rpm -qf /usr/bin/vim`** | **f**ile. **그 파일을 제공한 패키지 역조회** ← **42번 정답 ②** |
| `rpm -qi vim` | **i**nfo. 패키지 상세 정보(버전·요약·라이선스) |
| `rpm -qR vim` | **R**equires. **의존성 목록** (42번 선지 ①이 이것) |
| `rpm -qc vim` | **c**onfig. 설정 파일만 |
| `rpm -qd vim` | **d**oc. 문서 파일만 |
| `rpm -qp pkg.rpm` | **p**ackage. **설치 전 `.rpm` 파일**을 대상으로 조회 |
| `rpm -q --changelog vim` | 변경 이력 |

```bash
rpm -ivh pkg.rpm        # 설치 + 상세 + 진행바  (가장 흔한 조합)
rpm -Uvh pkg.rpm        # 업그레이드
rpm -e vim              # 삭제
rpm -e --nodeps vim     # 의존성 무시 삭제 (⚠ 시스템 파손 위험)
rpm -V vim              # 변조 검증. 출력의 S=크기 M=권한 5=MD5 T=시간
rpm --import KEY        # GPG 키 등록
```

**42번 오답 분석** — ④(이름으로 설치 여부 조회)는 `-q`만 쓴 경우임. `-qf`의 **`f`가 file**이라는 것만 잡으면 됨. `-ql`(패키지→파일)과 `-qf`(파일→패키지)가 **방향이 반대**라는 것이 시험 포인트임.

#### dnf / yum — 저장소 기반 (의존성 자동 해결)

**dnf** = Dandified YUM. **yum** = Yellowdog Updater Modified. RHEL 8부터 dnf가 표준이고 `yum`은 dnf의 심볼릭 링크임.

| 명령 | 용도 |
| --- | --- |
| `dnf install httpd` | 설치(의존성 자동 해결) |
| `dnf remove httpd` | 삭제 |
| `dnf update` / `dnf upgrade` | 전체 업데이트 |
| `dnf update httpd` | 특정 패키지만 |
| `dnf search 문자열` | 이름·요약에서 검색 |
| `dnf info httpd` | 상세 정보 |
| **`dnf list installed`** | **이미 설치된 패키지 목록** ← **43번 정답 근거** |
| **`dnf list available`** | **저장소에서 설치 가능한 패키지 목록** |
| `dnf list all` | 둘 다 |
| `dnf provides /usr/bin/vim` | **파일을 제공하는 패키지 검색**(rpm -qf의 저장소 버전) |
| `dnf repolist` | 등록된 저장소 목록 |
| `dnf clean all` | 캐시 삭제 |

| `dnf -y install httpd` | `-y` = 모든 질문에 yes |

**43번 오답 분석** — ④(`dnf remove`가 패키지를 제거한다)는 **맞는 설명**이라 "틀린 것"이 아님. 틀린 것은 ③으로, `list installed`(설치됨)를 `list available`(설치 가능)의 설명으로 바꿔놓은 것임. **`installed` / `available`의 뜻만 알면 즉답 가능함.**

저장소 설정은 `/etc/yum.repos.d/*.repo`에 있음.

**apt** = Advanced Package Tool. dnf에 대응하는 고수준 도구.

### 4-13. 소스 컴파일 3단계

> 45번 오답 — ③을 골랐으나 정답은 ②

```bash
tar xvzf app-1.0.tar.gz && cd app-1.0
./configure --prefix=/usr/local    # 1. 환경 검사 + Makefile 생성
make                               # 2. 컴파일 (소스 → 실행 파일)
make install                       # 3. 설치 (결과물을 시스템 경로로 복사)
```

**순서를 외우는 논리** — Makefile이 있어야 `make`가 돌고(1→2), 컴파일 결과물이 있어야 설치할 수 있음(2→3). 뒤집힐 수 없는 순서임.

| 단계 | 하는 일 |
| --- | --- |
| `./configure` | 컴파일러·라이브러리·헤더 존재 여부 점검, 설치 경로(`--prefix`) 결정, **`Makefile` 생성** |
| `make` | `Makefile`을 읽어 gcc를 호출, 소스를 오브젝트·실행 파일로 **컴파일·링크** |
| `make install` | 결과물을 `--prefix` 경로(`/usr/local/bin` 등)로 **복사**. 보통 root 권한 필요 |

부가 타깃:

```bash
make clean       # 컴파일 산출물 삭제
make uninstall   # 설치 제거 (Makefile이 지원할 때만)
make -j4         # 4개 병렬 컴파일
```

**패키지 관리자와의 차이** — 소스 설치는 `rpm -qa`·`dpkg -l`에 잡히지 않음. 그래서 **관리자가 직접 설치한 것은 `/usr/local`에 몰아넣어** 패키지가 관리하는 `/usr`와 구분하는 관례가 있음.

### 4-14. 파티션 도구 — fdisk와 parted

> 46번 정답(③) · 47번 무응답 — 정답 ①(GPT 지원)

#### fdisk 내부 명령 (46번)

`fdisk /dev/sdb`로 진입한 뒤 대화형으로 입력함.

| 키 | 원어 | 동작 |
| --- | --- | --- |
| **`n`** | **n**ew | **새 파티션 추가** ← 46번 정답 |
| `d` | **d**elete | 파티션 삭제 |
| **`p`** | **p**rint | **파티션 테이블 출력** |
| `t` | **t**ype | 파티션 유형(시스템 ID) 변경 (83=Linux, 82=swap, 8e=LVM, fd=RAID) |
| `l` | **l**ist | 지원하는 파티션 유형 목록 |
| **`w`** | **w**rite | **변경 사항을 디스크에 저장하고 종료** |
| **`q`** | **q**uit | **저장하지 않고 종료** |
| `m` | **m**enu | 도움말 |
| `g` / `o` | — | GPT / DOS(MBR) 라벨 새로 생성 |

**`w`를 누르기 전까지는 아무것도 디스크에 반영되지 않음.** 실수하면 `q`로 빠져나오면 됨 — 이것이 fdisk의 안전장치임.

```bash
fdisk -l                # 전체 디스크·파티션 목록(비대화형)
fdisk /dev/sdb          # 대화형 진입
partprobe /dev/sdb      # 커널에 파티션 테이블 재읽기 요청
```

#### MBR vs GPT — 47번의 배경

| 항목 | **MBR** (Master Boot Record) | **GPT** (GUID Partition Table) |
| --- | --- | --- |
| 위치 | 디스크 **첫 512바이트** | 디스크 앞·뒤(백업본 포함) |
| **최대 디스크 크기** | **2TB** | 9.4ZB (사실상 무제한) |
| 최대 파티션 수 | 주 4개 (또는 주 3 + 확장 1 안에 논리 다수) | **128개**(기본) |
| 파티션 테이블 백업 | **없음** | **디스크 끝에 백업본** |
| 무결성 검사 | 없음 | CRC32 |
| 펌웨어 | BIOS | **UEFI** |

#### parted (47번)

| 항목 | fdisk | parted |
| --- | --- | --- |
| GPT 지원 | 최신 버전은 지원 | **완전 지원** ← 47번 정답 ① |
| 2TB 초과 | 구버전 불가 | **가능** |
| 반영 시점 | **`w` 입력 시** | **명령 즉시 반영**(취소 불가) ← 47번 ③이 틀린 이유 |
| 크기 조절 | 불가 | 가능(`resizepart`) |
| 스크립트 | 어려움 | `-s` 옵션으로 쉬움 |

```bash
parted /dev/sdb
(parted) mklabel gpt                     # GPT 라벨 생성
(parted) mkpart primary xfs 0% 50GB      # 파티션 생성
(parted) print                           # 조회
(parted) rm 1                            # 삭제
(parted) quit

parted -s /dev/sdb mklabel gpt           # -s = script. 비대화형
parted -l                                # 전체 조회
gdisk /dev/sdb                           # GPT 전용 fdisk 계열 도구
```

**parted는 `w`가 없음 — 입력하는 순간 디스크에 쓰임.** 실무에서 가장 조심해야 할 지점이고, 47번 ③이 이걸 노린 선지임.

### 4-15. LVM 구조와 명령 순서

> 48번 오답(③ 선택, 정답 ④) · 49번 오답(③ LV 선택, 정답 ② VG)

**LVM** = Logical Volume Manager. 물리 디스크를 직접 쓰지 않고 한 겹 추상화를 두어, **여러 디스크를 하나로 묶고 나중에 크기를 자유롭게 조절**할 수 있게 하는 구조임.

```
물리 디스크        /dev/sdb        /dev/sdc
                      │               │
   pvcreate           ▼               ▼
PV (Physical Volume)  PV              PV      ← LVM 이 쓸 수 있게 표식을 붙인 디스크
                      └───────┬───────┘
   vgcreate                   ▼
VG (Volume Group)         [  VG "vgdata"  ]   ← PV 들을 합친 저장 공간 풀  ← 49번 정답
                       ┌──────┴──────┐         내부는 PE 라는 균일한 조각으로 나뉨
   lvcreate            ▼             ▼
LV (Logical Volume)  lv_web       lv_db        ← VG 에서 잘라낸 논리 파티션
                       │             │
   mkfs                ▼             ▼
파일시스템            xfs           ext4
                       │             │
   mount               ▼             ▼
                    /var/www       /var/lib/mysql
```

| 용어 | 원어 | 의미 |
| --- | --- | --- |
| **PV** | Physical Volume | LVM용으로 초기화한 **물리 디스크/파티션** |
| **VG** | Volume Group | **PV 들을 묶은 저장 공간 풀** ← **49번 정답 ②** |
| **LV** | Logical Volume | VG에서 할당받은 **논리 파티션**. 여기에 파일시스템을 만듦 |
| **PE** | Physical Extent | **VG를 나눈 균일한 최소 할당 단위**(기본 4MB) |
| **LE** | Logical Extent | LV 쪽에서 본 PE. 1:1 대응 |

**명령 순서 — 48번 정답 ④. 아래에서 위로 쌓아 올린다고 생각하면 뒤집히지 않음:**

```bash
pvcreate /dev/sdb /dev/sdc          # 1. PV 초기화
vgcreate vgdata /dev/sdb /dev/sdc   # 2. VG 생성 (PV 들을 묶음)
lvcreate -L 50G -n lv_web vgdata    # 3. LV 생성 (-L 크기, -n 이름)
mkfs.xfs /dev/vgdata/lv_web         # 4. 파일시스템 생성
mount /dev/vgdata/lv_web /var/www   # 5. 마운트
```

LV의 장치 경로는 `/dev/<VG명>/<LV명>` 또는 `/dev/mapper/<VG명>-<LV명>` 두 가지로 나타남.

**명령 체계 — 접두사가 대상, 접미사가 동작임. 조합으로 외우면 30개를 안 외워도 됨:**

| | `pv*` (PV 대상) | `vg*` (VG 대상) | `lv*` (LV 대상) |
| --- | --- | --- | --- |
| `*create` | `pvcreate` | `vgcreate` | `lvcreate` |
| `*display` | `pvdisplay` | `vgdisplay` | `lvdisplay` |
| `*s` (요약) | `pvs` | `vgs` | `lvs` |
| `*scan` | `pvscan` | `vgscan` | `lvscan` |
| `*remove` | `pvremove` | `vgremove` | `lvremove` |
| `*extend` | — | `vgextend`(PV 추가) | `lvextend`(용량 증가) |
| `*reduce` | — | `vgreduce`(PV 제거) | `lvreduce`(용량 감소) |

**용량 확장 — 실무 빈출 시나리오:**

```bash
pvcreate /dev/sdd                        # 새 디스크 준비
vgextend vgdata /dev/sdd                 # VG 에 편입
lvextend -L +20G /dev/vgdata/lv_web      # LV 를 20G 증가
lvextend -l +100%FREE /dev/vgdata/lv_web # 남은 공간 전부
xfs_growfs /var/www                      # XFS 는 마운트 지점 지정
resize2fs /dev/vgdata/lv_web             # ext4 는 장치 지정
lvextend -r -L +20G /dev/vgdata/lv_web   # -r = resizefs. 파일시스템까지 한 번에
```

**LV를 늘린 것만으로는 끝이 아님 — 파일시스템도 늘려야 실제 용량이 보임.** 이 두 단계를 분리해 묻는 문제가 자주 나옴.

**LVM의 장점** — 여러 디스크를 하나로 묶음, 무중단 확장, 스냅샷(`lvcreate -s`), 디스크 교체 시 데이터 이동(`pvmove`).

### 4-16. RAID 레벨 전수 정리

> 50번·51번 모두 무응답 — "RAID 전략 정리 필요", "각 숫자가 가지는 특별한 이유가 있는지?"

**RAID** = Redundant Array of Independent(원래는 Inexpensive) Disks. 여러 디스크를 묶어 **성능** 또는 **가용성**(장애 허용)을 얻는 기술임.

**"숫자에 특별한 이유가 있는가?"** — **없음.** 초기 논문(1988, 버클리)에서 제안된 순서대로 붙인 **일련번호**일 뿐이고 크기·성능 순서가 아님. RAID 6이 5보다 좋고 5가 1보다 좋다는 의미가 전혀 아님. 다만 아래 세 가지 축의 조합으로 이해하면 전부 정리됨.

**세 가지 기본 기법:**

| 기법 | 원어 | 하는 일 | 얻는 것 |
| --- | --- | --- | --- |
| **스트라이핑** | striping | 데이터를 조각내 **여러 디스크에 나눠 씀** | **속도** (병렬 읽기/쓰기) |
| **미러링** | mirroring | **같은 데이터를 그대로 복제** | **안전성** (용량은 절반) |
| **패리티** | parity | XOR 계산값을 저장해 **잃은 조각을 역산** | **안전성 + 용량 효율** |

**패리티의 원리** — `A XOR B = P`를 저장해 두면, B를 잃어도 `A XOR P = B`로 복원됨. 디스크 하나를 통째로 복제하지 않고 **디스크 1개 분량의 공간**만으로 1개 장애를 견딜 수 있음.

| 레벨 | 기법 | 최소 디스크 | 가용 용량 | 장애 허용 | 특징 |
| --- | --- | --- | --- | --- | --- |
| **RAID 0** | 스트라이핑 | **2** | **100%** | **0개 (없음)** | 성능 최고, **디스크 1개만 죽어도 전부 소실**. 사실 Redundant가 아님 |
| **RAID 1** | 미러링 | **2** | **50%** | n-1개 | 완전 복제. 읽기 성능↑, 쓰기 성능 변화 없음. 가장 안전 |
| RAID 2 | 해밍 코드 | 3 | — | 1개 | **실사용 안 함** (역사적 존재) |
| RAID 3 | 스트라이핑(바이트) + **전용** 패리티 | 3 | (n-1)/n | 1개 | 패리티 디스크가 병목 |
| **RAID 4** | 스트라이핑(블록) + **전용 패리티 디스크** | 3 | (n-1)/n | 1개 | **패리티가 한 디스크에 집중** → 그 디스크가 병목 |
| **RAID 5** | 스트라이핑 + **분산 패리티** | **3** | **(n-1)/n** | **1개** | **패리티를 모든 디스크에 나눠 저장** → RAID 4의 병목 해소. 가장 널리 쓰임 |
| **RAID 6** | 스트라이핑 + **이중 분산 패리티** | **4** | (n-2)/n | **2개** | 복구 중 두 번째 장애까지 대비. 대용량 디스크 시대의 표준 |
| **RAID 10 (1+0)** | 미러링 후 스트라이핑 | **4** | 50% | 각 미러 쌍당 1개 | **성능 + 안전 둘 다.** DB 서버 표준 |
| RAID 01 (0+1) | 스트라이핑 후 미러링 | 4 | 50% | 1개 | 10보다 복구 취약. 잘 안 씀 |

**50번 정답 ① 분해** — "패리티를 각 디스크에 **분산** 저장 + 최소 **3**개 + **1개** 장애 허용" = RAID 5의 정의 그대로임.
- ② 미러링 50% → **RAID 1**
- ③ 패리티 없는 스트라이핑 → **RAID 0**
- ④ **전용** 패리티 디스크 → **RAID 4** (RAID 5와의 유일한 차이가 '전용이냐 분산이냐'임)

**51번 정답 ③ 분해** — RAID 0 = 성능↑·장애 허용 없음, RAID 1 = 가용 용량 절반. 나머지 선지는 0과 1의 설명을 서로 바꾸거나(①②) 최소 디스크 수를 틀리게(④, 둘 다 최소 2개) 만든 것임.

**용량 계산 연습 — 1TB 디스크 4개일 때:**

| 레벨 | 가용 용량 | 계산 |
| --- | --- | --- |
| RAID 0 | **4TB** | 전부 사용 |
| RAID 1 (2쌍) | **2TB** | 절반 |
| RAID 5 | **3TB** | (4-1)×1TB |
| RAID 6 | **2TB** | (4-2)×1TB |
| RAID 10 | **2TB** | 절반 |

**리눅스 소프트웨어 RAID 명령 — `mdadm`(multiple device admin):**

```bash
mdadm --create /dev/md0 --level=5 --raid-devices=3 /dev/sd{b,c,d}1
mdadm --detail /dev/md0            # 상세 상태
mdadm --stop /dev/md0              # 중지
mdadm --add /dev/md0 /dev/sde1     # 디스크 추가(교체)
mdadm --fail /dev/md0 /dev/sdb1    # 장애 표시
mdadm --remove /dev/md0 /dev/sdb1  # 제거
mdadm --detail --scan >> /etc/mdadm.conf   # 설정 영구화
cat /proc/mdstat                   # RAID 현황 (재동기화 진행률 포함)
```

**RAID ≠ 백업.** RAID는 **디스크 고장**을 견딜 뿐, 실수로 삭제한 파일이나 랜섬웨어·논리적 손상은 모든 디스크에 즉시 반영됨. 백업은 별개로 필요함 — 시험에도 서술로 나옴.

### 4-17. 커널 모듈 관리

> 52번 오답 — ④(`depmod -r`)를 골랐으나 정답은 ②(`modprobe -r`)

**커널 모듈**은 커널에 **동적으로 붙였다 뗄 수 있는 코드 조각**임(주로 장치 드라이버, 파일시스템). 모든 드라이버를 커널에 내장하면 커널이 거대해지므로, 필요할 때만 적재하는 구조를 씀. 확장자는 `.ko`(kernel object)이고 `/lib/modules/$(uname -r)/`에 있음.

| 명령 | 원어 | 동작 | 의존성 처리 |
| --- | --- | --- | --- |
| `lsmod` | **l**i**s**t **mod**ules | **적재된 모듈 목록** (`/proc/modules`) | — |
| `insmod file.ko` | **ins**ert **mod**ule | 모듈 **1개**를 파일 경로로 적재 | **안 함** |
| `rmmod usb_storage` | **r**e**m**ove **mod**ule | 모듈 **1개** 제거 | **안 함** |
| **`modprobe usb_storage`** | **mod**ule **probe** | **이름으로 적재 + 의존 모듈 자동 적재** | **함** |
| **`modprobe -r usb_storage`** | remove | **제거 + 필요 없어진 의존 모듈까지 제거** ← **52번 정답** | **함** |
| `modinfo usb_storage` | **mod**ule **info** | 모듈 정보(설명·파라미터·의존성) | — |
| `depmod -a` | **dep**endency **mod**ules | **의존성 정보 파일 갱신**(`modules.dep` 생성) | — |

**핵심 대비 — `insmod`/`rmmod`는 단일 모듈만, `modprobe`는 의존성까지.** 52번 선지 ①③④는 존재하지 않는 옵션(`lsmod -r`, `insmod -r`)이거나 역할이 다른 명령(`depmod`)임.

```bash
lsmod | grep usb                    # 적재 여부 확인
modprobe -r usb_storage             # 안전한 제거
echo "blacklist usb_storage" > /etc/modprobe.d/blacklist.conf   # 부팅 시 적재 금지
echo "usb_storage" > /etc/modules-load.d/usb.conf               # 부팅 시 자동 적재
uname -r                            # 실행 중인 커널 버전
```

### 4-18. CUPS — 인쇄 시스템

> 53번 무응답 — "CUPS가 뭐지? 문제에 있는 모든 선지를 모르겠음". 정답 ④(`/etc/xinetd.conf` — 틀린 설명)

**CUPS** = Common UNIX Printing System. 애플이 개발해 오픈소스로 공개한, 리눅스/macOS의 **표준 인쇄 시스템**임. 예전의 LPD/LPRng를 대체함.

| 항목 | 내용 |
| --- | --- |
| 데몬 | `cupsd` |
| **주 설정 파일** | **`/etc/cups/cupsd.conf`** ← 53번 정답 근거 |
| 프린터 정의 | `/etc/cups/printers.conf` |
| **웹 관리 인터페이스** | **`http://localhost:631`** — 포트 **631** |
| **프로토콜** | **IPP** = Internet Printing Protocol (631/tcp). SMB·LPD·소켓도 지원 |
| 스풀 디렉터리 | `/var/spool/cups/` |
| 로그 | `/var/log/cups/` |

**`/etc/xinetd.conf`는 xinetd**(eXtended InterNET Daemon, 슈퍼 데몬)의 설정 파일로 CUPS와 무관함. 이것이 ④가 틀린 이유임. **"631 포트 = CUPS"** 하나만 확실히 잡아도 이 유형은 풀림.

**명령 두 계열 — 둘 다 시험에 나옴:**

| 작업 | System V 계열 | BSD 계열 |
| --- | --- | --- |
| 인쇄 요청 | `lp file.txt` | `lpr file.txt` |
| 큐 조회 | `lpstat -o` | `lpq` |
| 작업 취소 | `cancel 작업ID` | `lprm 작업ID` |
| 프린터 상태 | `lpstat -p` | `lpc status` |

```bash
lpstat -a              # 인쇄 수락 중인 프린터
lpstat -t              # total. 전체 상태 한 번에
lpstat -p -d           # 프린터 목록 + 기본 프린터
lpadmin -p hp -E -v ipp://... -m drv   # 프린터 등록
lpoptions -d hp        # 기본 프린터 지정
cupsenable hp / cupsdisable hp
accept hp / reject hp  # 작업 수락/거부
systemctl status cups
```

### 4-19. df·du·dd와 MBR

> 54번 정답(①) — "나머지 선지가 틀린 이유 확인 필요" · 55번 무응답 — "MBR 영역이 뭐지?"

#### df vs du — 54번 선지 분석

| 명령 | 원어 | 관점 | 대상 |
| --- | --- | --- | --- |
| **`df`** | **d**isk **f**ree | **파일시스템 단위** 사용량 | **마운트된** 파일시스템 |
| **`du`** | **d**isk **u**sage | **디렉터리·파일 단위** 사용량 | 지정한 경로를 재귀 합산 |

```bash
df -h                # -h = human-readable. K/M/G 단위  ← 54번 정답 ①
df -H                # 1000 단위(디스크 제조사 표기)
df -T                # -T = Type. 파일시스템 유형 함께 표시
df -i                # -i = inode. inode 사용률 (블록이 아님)
df -a                # 가상 파일시스템까지 전부

du -sh /var/log      # -s = summarize 합계만, -h 사람이 읽는 단위
du -h --max-depth=1 /var    # 1단계 하위까지만
du -ah /var/log | sort -rh | head -20   # 용량 큰 순 20개
```

**54번 나머지 선지가 틀린 이유:**
- ② "디렉터리별 재귀 합산" → **`du`의 동작**임. df는 파일시스템 단위임
- ③ "`Use%`가 inode 사용률" → `Use%`는 **블록(용량) 사용률**임. inode 사용률은 **`df -i`**로 따로 봄
- ④ "마운트되지 않은 파티션도 표시" → **df는 마운트된 것만** 보여줌. 마운트 안 된 것은 `lsblk`·`fdisk -l`로 봄

**실무 함정** — 용량이 남는데 "No space left on device"가 나면 **inode 고갈**임. 작은 파일이 수백만 개일 때 발생하며 `df -i`로 확인함. 또 `df`와 `du`의 결과가 다르면 **삭제됐지만 프로세스가 아직 열고 있는 파일** 때문임(`lsof | grep deleted`).

#### MBR과 dd — 55번

**MBR** = Master Boot Record. **디스크의 맨 앞 512바이트**로, 부팅에 반드시 필요한 정보가 들어 있음.

```
512 바이트 구조
┌──────────────────────────────────────┬──────────────────┬──────┐
│ 부트스트랩 코드 446 B                 │ 파티션 테이블 64B │ 55AA │
│ (부트로더 1단계, GRUB의 첫 조각)       │ (16B × 4개 항목)  │  2B  │
└──────────────────────────────────────┴──────────────────┴──────┘
                                          ↑                  ↑
                            주 파티션 최대 4개인 이유    시그니처(유효 표식)
```

MBR이 손상되면 **부팅 불가 + 파티션 정보 전부 소실**임. 백업본이 없기 때문에(GPT와의 차이) 파티션 작업 전에 백업해 두는 것이 관례임.

**`dd`** = data duplicator(또는 disk dump). **블록 단위로 저수준 복사**를 하는 명령임. 파일시스템을 이해하지 않고 원시 바이트를 그대로 옮기므로 장치 전체·부트섹터·ISO 복사에 씀.

| 옵션 | 원어 | 의미 |
| --- | --- | --- |
| `if=` | **i**nput **f**ile | **입력** 원본 |
| `of=` | **o**utput **f**ile | **출력** 대상 |
| `bs=` | **b**lock **s**ize | 한 번에 읽고 쓸 블록 크기 |
| `count=` | — | 복사할 **블록 개수** |
| `skip=` | — | 입력에서 건너뛸 블록 수 |
| `seek=` | — | 출력에서 건너뛸 블록 수 |
| `conv=` | convert | `noerror`(오류 무시), `sync`(패딩), `notrunc`(자르지 않음) |
| `status=progress` | — | 진행 상황 표시 |

**55번 정답 ③ 분해:**

```bash
dd if=/dev/sda of=mbr.img bs=512 count=1
   ^^^^^^^^^^^ 원본=디스크    ^^^^^^^^^^^^^ 512바이트 × 1블록 = 정확히 MBR
        ^^^^^^^^^^^^ 대상=파일  → 백업 방향
```

선지가 틀린 이유:
- ① `if=mbr.img of=/dev/sda` — **if/of가 반대**. 이건 **복원**임(백업이 아님)
- ② `count=2` — 1024바이트를 읽음. MBR은 512바이트이므로 초과
- ④ `cp /dev/sda mbr.img` — `cp`는 장치를 스트림으로 읽어 **디스크 전체**를 복사하려 함. 512바이트만 뽑을 수 없음

```bash
# 복원 (방향만 반대)
dd if=mbr.img of=/dev/sda bs=512 count=1

# 파티션 테이블은 살리고 부트 코드만 복원 (앞 446바이트)
dd if=mbr.img of=/dev/sda bs=446 count=1

# 자주 쓰는 응용
dd if=/dev/zero of=/swapfile bs=1M count=2048    # 2GB 스왑 파일 생성
dd if=/dev/urandom of=/dev/sdb bs=1M             # 디스크 완전 소거
dd if=rocky.iso of=/dev/sdb bs=4M status=progress # 부팅 USB 제작
```

**`dd`는 되돌릴 수 없음.** `of=`에 잘못된 장치를 적으면 그 디스크가 즉시 파괴됨(별명이 disk destroyer). `if`와 `of`를 두 번 확인하는 습관이 필요함.

스왑 관련도 함께:

```bash
mkswap /swapfile && chmod 600 /swapfile
swapon /swapfile        # 활성화
swapoff /swapfile       # 비활성화
swapon -s / free -h     # 스왑 현황
```

### 4-20. rsyslog — 로그 수집 체계

> 56번 무응답 — "rsyslog이 뭐지?". 정답 ②

**rsyslog** = rocket-fast system for log processing. 전통 `syslog`의 확장 구현으로, 커널과 각종 데몬이 보내는 로그 메시지를 받아 **규칙에 따라 파일·콘솔·원격 서버로 분배**하는 데몬임.

- 데몬: `rsyslogd`
- 설정: **`/etc/rsyslog.conf`**, `/etc/rsyslog.d/*.conf`

**규칙 문법 — `퍼실리티.우선순위    목적지`**

```
authpriv.*        /var/log/secure
    ↑       ↑          ↑
 퍼실리티  우선순위   목적지
 (어디서)  (얼마나심각) (어디에 기록)
```

**퍼실리티(facility)** — 메시지를 만든 **주체의 분류**:

| 퍼실리티 | 의미 |
| --- | --- |
| `kern` | 커널 |
| `user` | 사용자 프로세스 |
| `mail` | 메일 시스템 |
| `daemon` | 시스템 데몬 |
| **`auth`** | 인증(로그인) |
| **`authpriv`** | **보안·인증 (민감 정보 포함)** → 보통 `/var/log/secure` |
| `syslog` | rsyslog 자신 |
| `lpr` | 프린터 |
| `news`, `uucp` | 뉴스, UUCP |
| `cron` | cron |
| `local0` ~ `local7` | 사용자 정의용 |
| `*` | 모든 퍼실리티 |

**우선순위(priority/severity)** — 숫자가 **작을수록 심각**함:

| 값 | 이름 | 의미 |
| --- | --- | --- |
| 0 | **emerg** (panic) | 시스템 사용 불가 |
| 1 | **alert** | 즉시 조치 필요 |
| 2 | **crit** | 치명적 상황 |
| 3 | **err** (error) | 오류 |
| 4 | **warning** (warn) | 경고 |
| 5 | **notice** | 정상이지만 주목할 상황 |
| 6 | **info** | 정보 |
| 7 | **debug** | 디버깅 |
| — | `none` | 해당 퍼실리티 **제외** |
| — | `*` | **모든 우선순위** |

**중요 — 우선순위를 그냥 적으면 "그 이상(더 심각한) 전부"를 의미함.**

```
mail.err          → err, crit, alert, emerg 전부 기록 (err "이상")
mail.=err         → = 를 붙이면 err "만"
mail.!=err        → err 만 제외
*.info;mail.none;authpriv.none   /var/log/messages
   ↑ 모든 퍼실리티의 info 이상    ↑ 단 mail 과 authpriv 는 제외
```

**56번 정답 ② 분해** — `authpriv.*`에서 `*`는 **모든 우선순위**이므로 authpriv의 전 메시지가 `/var/log/secure`에 기록됨. ①은 `authpriv.=emerg`의 설명이고, ③은 `none`의 설명, ④는 목적지가 `@서버주소`일 때의 설명임.

**목적지 표기:**

| 표기 | 의미 |
| --- | --- |
| `/var/log/secure` | 파일에 기록 |
| `-/var/log/maillog` | `-` = 비동기 기록(성능↑, 정전 시 유실 가능) |
| `@192.168.1.10:514` | **UDP**로 원격 로그 서버 전송 |
| `@@192.168.1.10:514` | **TCP**로 전송(`@` 두 개) |
| `/dev/console` | 콘솔에 출력 |
| `*` | 로그인한 모든 사용자에게 |
| `kim` | 특정 사용자에게 |

**주요 로그 파일:**

| 파일 | 내용 |
| --- | --- |
| `/var/log/messages` | **일반 시스템 로그**(RHEL 계열) |
| `/var/log/syslog` | 같은 역할(데비안 계열) |
| **`/var/log/secure`** | **인증·보안**(RHEL). 데비안은 `/var/log/auth.log` |
| `/var/log/maillog` | 메일 |
| `/var/log/cron` | cron 실행 이력 |
| `/var/log/boot.log` | 부팅 |
| `/var/log/dmesg` | 커널 링 버퍼 |
| `/var/log/httpd/access_log`, `error_log` | Apache |

**logrotate** — 로그가 무한히 커지는 것을 막는 순환 도구. `/etc/logrotate.conf`와 `/etc/logrotate.d/*`에 정책을 두고 cron이 매일 실행함.

```
/var/log/httpd/*log {
    weekly              # 주 단위 순환
    rotate 4            # 4세대 보관
    compress            # gzip 압축
    missingok           # 파일 없어도 오류 아님
    notifempty          # 비어 있으면 순환 안 함
    create 0640 root adm
    postrotate ... endscript   # 순환 후 실행할 명령(데몬에 HUP 등)
}
```

**systemd-journald와의 관계** — systemd 시스템은 `journald`가 바이너리 저널에 먼저 기록하고, rsyslog가 그것을 받아 전통 텍스트 파일로도 남김. 둘은 **경쟁이 아니라 병행**임.

```bash
journalctl -u sshd -f      # -u 유닛 필터, -f follow 실시간  ← 57번 정답
journalctl -b              # 이번 부팅 로그
journalctl -b -1           # 직전 부팅 로그
journalctl -p err          # err 이상만
journalctl --since "1 hour ago" --until now
journalctl -k              # 커널 메시지만
journalctl --disk-usage    # 저널 용량
journalctl --vacuum-time=7d   # 7일 이전 삭제
```

> `journalctl`이 읽는 파일과 저장 위치는 [[../../QA#H-2. `journalctl` 은 어느 파일을 읽는가]] 참조.

### 4-21. 로그 파일과 조회 명령

> 58번 오답 — ④를 골랐으나 정답은 ①

**바이너리 로그 3종과 전용 조회 명령** — 텍스트가 아니라 `cat`으로 볼 수 없고 전용 명령이 필요함. **이 대응이 시험에 거의 그대로 나옴.**

| 파일 | 기록 내용 | **조회 명령** |
| --- | --- | --- |
| **`/var/log/wtmp`** | **로그인·로그아웃 이력**(누적) | **`last`** ← 58번 정답 ① |
| **`/var/log/btmp`** | **로그인 실패 이력** (**b** = bad) | **`lastb`** |
| **`/var/run/utmp`** | **현재 접속 중인 사용자** | **`who`**, **`w`**, `users` |
| **`/var/log/lastlog`** | 각 사용자의 **마지막 로그인 시각** | **`lastlog`** |

**외우는 요령** — `w`tmp→`last`(누적 이력), `b`tmp→`lastb`(**b**ad), `u`tmp→`who`(현재), lastlog→`lastlog`(이름 그대로).

58번 선지 ②③④는 이 짝을 전부 어긋나게 섞어놓은 것임.

```bash
last                 # 로그인 이력 전체
last -n 10           # 최근 10건
last kim             # 특정 사용자
last -f /var/log/wtmp.1   # 다른 파일 지정
lastb                # 로그인 실패(무차별 대입 공격 탐지에 사용)
lastlog              # 전 사용자의 마지막 로그인
lastlog -u kim
who                  # 현재 접속자
w                    # 현재 접속자 + 무엇을 하고 있는지
users                # 접속자 이름만
```

### 4-22. PAM — 인증 모듈 프레임워크

> 59번 무응답 — 정답 ③

**PAM** = Pluggable Authentication Modules(착탈식 인증 모듈). 각 프로그램(`login`, `sshd`, `su`, `sudo`, `passwd`)이 **자기 안에 인증 코드를 갖는 대신**, 인증을 표준 인터페이스로 외부 모듈에 위임하게 만든 프레임워크임.

**해결한 문제** — 예전에는 인증 방식을 바꾸려면(예: LDAP 도입, OTP 추가) 모든 프로그램을 다시 컴파일해야 했음. PAM은 **설정 파일만 고치면** 모든 프로그램의 인증 방식이 함께 바뀜.

- 설정: **`/etc/pam.d/<서비스명>`** (예: `/etc/pam.d/sshd`, `/etc/pam.d/login`)
- 모듈: `/lib64/security/*.so`

**설정 문법 — `타입  제어플래그  모듈  [인자]`**

```
auth     required     pam_unix.so
account  required     pam_unix.so
password requisite    pam_pwquality.so retry=3 minlen=8
session  optional     pam_lastlog.so
```

**타입(관리 그룹) 4종:**

| 타입 | 담당 |
| --- | --- |
| **auth** | **본인 확인** (패스워드·지문·OTP) |
| **account** | **계정 유효성** (만료·시간대·접속 허용 여부) |
| **password** | **패스워드 변경** 시의 규칙(복잡도 등) |
| **session** | 세션 시작·종료 시 처리(홈 마운트, 로그 기록, 자원 한도) |

**제어 플래그:**

| 플래그 | 의미 |
| --- | --- |
| **`required`** | 반드시 성공. 실패해도 **나머지 모듈은 계속 수행한 뒤** 최종 실패(공격자에게 어느 단계에서 실패했는지 숨김) |
| **`requisite`** | 반드시 성공. 실패하면 **즉시 중단**하고 실패 반환 |
| **`sufficient`** | 성공하면 **거기서 통과**(앞의 required가 실패하지 않았다면). 실패해도 계속 진행 |
| **`optional`** | 결과가 최종 판정에 영향 없음 |
| `include` | 다른 설정 파일을 불러옴 |

**자주 나오는 모듈:**

| 모듈 | 역할 |
| --- | --- |
| `pam_unix.so` | 전통 `/etc/passwd`·`/etc/shadow` 기반 인증 |
| `pam_pwquality.so` (구 `pam_cracklib`) | **패스워드 복잡도 강제**(길이·문자 종류·사전 단어) |
| `pam_faillock.so` (구 `pam_tally2`) | **로그인 실패 횟수 초과 시 계정 잠금** |
| `pam_wheel.so` | **`wheel` 그룹만 `su` 허용** |
| `pam_limits.so` | `/etc/security/limits.conf`의 자원 한도 적용 |
| `pam_time.so` | 시간대별 접속 제한 |
| `pam_nologin.so` | `/etc/nologin`이 있으면 일반 사용자 차단 |
| `pam_securetty.so` | root 콘솔 로그인 제한 |
| `pam_rootok.so` | root면 무조건 통과(`su`가 root일 때 암호를 안 묻는 이유) |

59번 선지 ①(커널 모듈), ②(패키지 의존성), ④(방화벽)는 전부 다른 개념임. **"인증을 모듈화 + `/etc/pam.d/`"** 조합만 잡으면 됨.

> `wheel` 그룹과 `su`·`sudo`의 관계는 [[../../QA#C-1. wheel 그룹이란 무엇이며 sudo 와 어떤 관계인가]] 참조.

### 4-23. tar·백업·rsync

> 60번 정답(④) — "tar 관련 설명 필요" 요청 · 61번·62번 무응답

#### tar — tape archive

여러 파일을 **하나로 묶는** 것이 본업이고, 압축은 외부 도구에 위임함(옵션으로 연동).

| 옵션 | 원어 | 의미 |
| --- | --- | --- |
| **`c`** | **c**reate | **아카이브 생성** |
| **`x`** | e**x**tract | **풀기** |
| **`t`** | **t**est/list | **내용 목록만 보기**(풀지 않음) |
| `r` | **r**append | 기존 아카이브에 추가 |
| `u` | **u**pdate | 더 새로운 파일만 갱신 |
| **`f`** | **f**ile | **아카이브 파일명 지정** (거의 항상 필요, **맨 뒤에 씀**) |
| **`v`** | **v**erbose | 처리 파일 목록 출력 |
| **`z`** | g**z**ip | **gzip 압축/해제** (`.tar.gz`, `.tgz`) ← **60번 정답 ④** |
| **`j`** | bzip2 | **bzip2** 압축 (`.tar.bz2`) |
| **`J`** | xz | **xz** 압축 (`.tar.xz`) — 대문자 |
| `p` | **p**ermission | 권한 보존 |
| `P` | **P**ath | 절대경로 유지 |
| `C 경로` | **C**hange dir | 지정 디렉터리로 이동해 작업 |
| `--exclude=패턴` | | 제외 |

```bash
tar cvzf backup.tar.gz /home/kim     # 생성 + 목록 + gzip + 파일명
tar xvzf backup.tar.gz               # 풀기
tar tvzf backup.tar.gz               # 내용만 확인 (푸는 것이 아님)
tar xvzf backup.tar.gz -C /restore   # 특정 위치에 풀기
tar cvJf backup.tar.xz /data         # xz 압축 (압축률 최고, 느림)
tar cvzf b.tar.gz --exclude='*.log' /data
```

**압축 도구 단독 사용:**

| 도구 | 확장자 | 압축률 | 속도 | tar 옵션 |
| --- | --- | --- | --- | --- |
| `gzip`/`gunzip` | `.gz` | 보통 | **빠름** | `z` |
| `bzip2`/`bunzip2` | `.bz2` | 높음 | 느림 | `j` |
| `xz`/`unxz` | `.xz` | **최고** | 가장 느림 | `J` |
| `compress` | `.Z` | 낮음 | 빠름 | `Z` |
| `zip`/`unzip` | `.zip` | 보통 | — | (별도 명령) |

`gzip`·`bzip2`·`xz`는 **원본을 대체**하는 것이 기본 동작임(`-k`로 원본 유지). `zip`만 여러 파일을 스스로 묶을 수 있고, 나머지는 파일 하나씩만 압축하므로 tar와 짝을 이룸.

#### dump / restore — 61번

**파일시스템 단위**의 전통 백업 도구임(ext 계열 전용, XFS는 `xfsdump`).

**백업 레벨 0~9의 의미 — 61번 정답 ②:**

| 레벨 | 의미 |
| --- | --- |
| **0** | **전체 백업**(full) |
| **1~9** | **자신보다 낮은 레벨의 가장 최근 백업 이후 변경분**만 저장하는 **증분 백업** |

```
월: dump 0  → 전체
화: dump 1  → 월요일(레벨0) 이후 변경분
수: dump 2  → 화요일(레벨1) 이후 변경분
목: dump 1  → 월요일(레벨0) 이후 전부 변경분   ← 레벨 1 이 다시 나오면 기준이 0 으로 돌아감
```

```bash
dump -0u -f /backup/full.dump /dev/sdb1   # -0 레벨, -u = /etc/dumpdates 갱신, -f 대상
dump -1u -f /backup/inc1.dump /dev/sdb1
restore -rf /backup/full.dump             # -r = rebuild. 전체 복원
restore -if /backup/full.dump             # -i = interactive. 원하는 파일만 골라 복원
restore -tf /backup/full.dump             # -t = table. 목록만
```

**백업 방식 3종 비교 — 개념 문제로 자주 나옴:**

| 방식 | 백업 대상 | 백업 시간 | 복원 시 필요한 것 |
| --- | --- | --- | --- |
| **전체(full)** | 전부 | 김 | 전체 백업 1개 |
| **증분(incremental)** | **직전 백업 이후** 변경분 | **가장 짧음** | 전체 + **모든 증분** (하나라도 빠지면 실패) |
| **차등(differential)** | **마지막 전체 백업 이후** 변경분 | 중간 | 전체 + **마지막 차등 1개** |

#### rsync — remote sync (62번)

변경된 **차이분만** 전송하는 동기화 도구임. 백업·미러링·배포에 표준으로 쓰임.

| 옵션 | 원어 | 의미 |
| --- | --- | --- |
| **`-a`** | **a**rchive | **재귀 + 권한·소유자·그룹·시간·심볼릭링크 보존** (= `-rlptgoD`). 가장 많이 씀 ← 62번 정답 ① |
| **`-z`** | **z**ip | **전송 중 압축** ← 62번 정답 ① |
| `-v` | **v**erbose | 상세 출력 |
| `-r` | **r**ecursive | 재귀 |
| `-l` | **l**inks | 심볼릭 링크 보존 |
| `-p` | **p**erms | 권한 보존 |
| `-t` | **t**imes | 시간 보존 |
| `-g` / `-o` | **g**roup / **o**wner | 그룹 / 소유자 보존 |
| **`--delete`** | | **원본에 없는 대상 파일 삭제**(완전 미러링) |
| `-n` / `--dry-run` | | **실제로 하지 않고 결과만 확인** (`--delete` 쓸 때 필수) |
| `-e ssh` | | SSH를 통해 전송 |
| `--bwlimit=1000` | bandwidth | 대역폭 제한(KB/s) |
| `--progress` | | 진행률 |
| `--exclude=` | | 제외 패턴 |

```bash
rsync -avz /data/ /backup/                        # 로컬 동기화
rsync -avz -e ssh /data/ user@host:/backup/       # 원격 전송
rsync -avz --delete /data/ /backup/               # 완전 미러링
rsync -avzn --delete /data/ /backup/              # 먼저 -n 으로 확인
```

**슬래시 하나가 동작을 바꿈 — 실무 최대 함정:**

```
rsync -a /data/ /backup/    → /data 의 "내용물"을 /backup 안으로   (/backup/file)
rsync -a /data  /backup/    → /data "디렉터리 자체"를 /backup 안으로 (/backup/data/file)
```

62번 선지가 틀린 이유 — ② `-v`는 상세 출력(삭제는 `--delete`), ③ `-z`는 압축(링크 무시 아님), ④ `--delete`는 삭제(대역폭 제한은 `--bwlimit`)임. **옵션의 역할을 서로 바꿔치기한 전형적 패턴임.**

### 4-24. sudo·sudoers·chage

> 63번 오답 — ②를 골랐으나 정답은 ③ · 64번 정답(②)

#### sudoers 문법 — 63번

```
kim    ALL=(ALL)    NOPASSWD: /usr/bin/systemctl
 ↑      ↑      ↑        ↑             ↑
사용자  호스트  실행할  태그        허용 명령
              사용자
```

| 위치 | 의미 |
| --- | --- |
| `kim` | 대상 사용자. `%dev`처럼 `%`를 붙이면 **그룹** |
| `ALL=` | 이 규칙이 적용되는 **호스트**(보통 ALL) |
| `(ALL)` | **어떤 사용자로 실행 가능한지**. `(root)`면 root로만 |
| `NOPASSWD:` | **암호 확인 생략** (기본은 `PASSWD:` — 자기 암호를 물음) |
| `/usr/bin/systemctl` | **허용되는 명령 목록**. `ALL`이면 모든 명령 |

**63번 정답 ③ 분해** — kim은 **암호 없이**(NOPASSWD) **`systemctl` 명령만**(ALL이 아님) sudo로 실행 가능함. ②를 고른 것은 `NOPASSWD:` 태그와 명령 제한을 둘 다 놓친 것임.

```
# 자주 보는 형태
root      ALL=(ALL)       ALL
%wheel    ALL=(ALL)       ALL              # wheel 그룹 전원, 암호 확인 있음
%wheel    ALL=(ALL)       NOPASSWD: ALL    # 암호 없이 전부 (RHEL 기본은 주석 처리)
kim       ALL=(ALL)       /usr/bin/systemctl, /usr/bin/journalctl
lee       ALL=(root)      NOPASSWD: /usr/sbin/reboot
```

**`visudo`로만 편집할 것** — 저장 시 문법 검사를 하고, 잘못된 문법으로 저장되면 **sudo 자체가 동작하지 않아 root 권한을 완전히 잃을 수 있음.** 추가 규칙은 `/etc/sudoers.d/` 아래 별도 파일로 두는 것이 안전함.

```bash
sudo -l              # 내가 sudo 로 할 수 있는 명령 목록
sudo -u kim cmd      # kim 사용자로 실행
sudo -i              # root 로그인 셸
sudo -s              # root 셸(환경 유지)
visudo               # sudoers 편집
visudo -c            # 문법 검사
visudo -f /etc/sudoers.d/dev
```

**`su` vs `sudo`:**

| 항목 | `su` | `sudo` |
| --- | --- | --- |
| 필요한 암호 | **대상 계정(root)의 암호** | **자기 자신의 암호** |
| 권한 범위 | 전환 후 전부 | **sudoers에 정의된 명령만** |
| 로그 | 적음 | **명령 단위로 `/var/log/secure`에 기록** |
| root 암호 공유 | 필요 | **불필요** ← 이것이 sudo를 쓰는 핵심 이유 |

`su -`(하이픈)는 **로그인 셸**로 전환해 대상 사용자의 환경변수·홈·PATH를 완전히 새로 읽음. `su`만 쓰면 현재 환경이 유지되어 PATH가 달라 명령을 못 찾는 문제가 생김.

#### chage — 64번

**chage** = change age. 패스워드 **만료 정책** 전용 명령임(`/etc/shadow` 3~8 필드를 다룸).

| 옵션 | 의미 |
| --- | --- |
| **`-l`** | **list. 만료 정보 전체 조회** ← 64번 정답 |
| `-m` | **m**in. 최소 사용 일수 |
| `-M` | **M**ax. 최대 사용 일수 |
| `-W` | **W**arn. 만료 경고 시작일 |
| `-I` | **I**nactive. 만료 후 비활성 유예일 |
| `-E` | **E**xpire. 계정 만료일 (YYYY-MM-DD) |
| `-d 0` | 마지막 변경일을 0으로 → **다음 로그인 시 암호 변경 강제** |

```bash
chage -l kim                       # 조회
chage -M 90 -W 7 kim               # 90일마다 변경, 7일 전 경고
chage -E 2026-12-31 kim            # 계정 만료일
chage -d 0 kim                     # 다음 로그인 시 암호 변경 강제
passwd -e kim                      # 위와 동일한 효과
```

64번 선지 ③`id`·④`groups`는 **그룹 소속 조회** 명령이라 만료 정보와 무관함.

### 4-25. SELinux 기초

> 65번 무응답 — 정답 ④(`ls -Z`)

**SELinux** = Security-Enhanced Linux. NSA가 개발해 커널에 통합된 **강제 접근 제어(MAC)** 시스템임.

| 구분 | **DAC** (Discretionary Access Control) | **MAC** (Mandatory Access Control) |
| --- | --- | --- |
| 결정 주체 | **파일 소유자**가 재량으로 권한 부여 | **시스템 정책**이 강제 |
| 구현 | 전통 퍼미션(`rwx`), ACL | **SELinux**, AppArmor |
| 한계 | root나 탈취된 프로세스는 무엇이든 가능 | root라도 정책 밖의 행동 불가 |

**핵심 가치** — 웹 서버가 해킹당해도, httpd 프로세스는 정책상 허용된 파일(`httpd_sys_content_t` 타입)만 만질 수 있어 `/etc/shadow` 탈취가 차단됨.

**보안 컨텍스트(security context)** — 모든 파일·프로세스·포트에 붙는 라벨임.

```
system_u:object_r:httpd_sys_content_t:s0
   ↑         ↑            ↑            ↑
 user      role         type        level(MLS)
                         ↑
                  실제 접근 판정의 핵심
```

```bash
ls -Z /var/www/html/index.html    # -Z 로 파일 컨텍스트 확인  ← 65번 정답 ④
ps -eZ                            # 프로세스 컨텍스트
id -Z                             # 내 컨텍스트
```

**동작 모드 3종:**

| 모드 | 동작 |
| --- | --- |
| **Enforcing** | 정책 **적용 + 차단 + 로그** (운영 권장) |
| **Permissive** | **차단하지 않고 로그만** 남김 (정책 튜닝·문제 진단용) |
| **Disabled** | 완전 비활성 (재부팅 필요) |

```bash
getenforce                        # 현재 모드 (Enforcing/Permissive/Disabled)
sestatus                          # 상세 상태
setenforce 0                      # Permissive 로 (일시적, 재부팅 시 원복)
setenforce 1                      # Enforcing 으로
vi /etc/selinux/config            # SELINUX=enforcing  → 영구 설정
```

**Enforcing ↔ Permissive는 재부팅 없이 전환 가능하지만, Disabled ↔ 나머지는 재부팅이 필요함.** 시험 포인트임.

**컨텍스트·불린 관리:**

```bash
chcon -t httpd_sys_content_t /web/index.html   # 임시 변경(relabel 시 원복)
semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?"   # 영구 규칙 등록
restorecon -Rv /web                # 정책 기준으로 컨텍스트 복원
getsebool -a                       # 불린(on/off 스위치) 전체 조회
setsebool -P httpd_can_network_connect on   # -P = permanent
semanage port -l                   # 포트-타입 매핑
semanage port -a -t http_port_t -p tcp 8080 # 8080 을 웹 포트로 허용
ausearch -m avc -ts recent         # AVC 거부 로그 조회
sealert -a /var/log/audit/audit.log # 해석과 조치 제안
```

거부 로그는 `/var/log/audit/audit.log`에 **AVC**(Access Vector Cache) 메시지로 남음. "설정은 다 맞는데 서비스가 안 된다"면 여기를 먼저 봐야 함.

### 5-1. Apache 웹 서버

> 66번·67번 정답 · 68번·69번 무응답 — 정답 ②(이름 기반 가상호스트), ④(`AllowOverride`)

- 데몬: `httpd` (데비안 계열은 `apache2`)
- 주 설정 파일: **`/etc/httpd/conf/httpd.conf`** (데비안: `/etc/apache2/apache2.conf`)
- 추가 설정: `/etc/httpd/conf.d/*.conf`
- 로그: `/var/log/httpd/access_log`, `error_log`

**주요 지시자(directive) — 이름과 역할을 서로 바꿔 묻는 것이 고정 패턴임:**

| 지시자 | 역할 |
| --- | --- |
| **`ServerRoot`** | **설정 파일·로그·모듈의 기준 디렉터리** (`/etc/httpd`) |
| **`DocumentRoot`** | **웹 콘텐츠(HTML)의 최상위 디렉터리** (`/var/www/html`) ← 66번 정답 |
| **`Listen`** | **수신할 IP·포트** (`Listen 80`, `Listen 192.168.1.10:8080`) ← 67번 정답 |
| `ServerName` | **이 서버의 도메인명**(가상호스트 구분 기준) |
| `ServerAdmin` | 관리자 **이메일 주소** |
| `ServerTokens` | 응답 헤더에 노출할 서버 정보량 (`Prod`가 보안상 권장) |
| `ServerSignature` | 오류 페이지 하단 서명 표시 여부 |
| **`DirectoryIndex`** | **기본 문서** (`index.html index.php`) |
| **`AllowOverride`** | **`.htaccess`로 재정의를 허용할 범위** (`None`/`All`/`AuthConfig`…) ← **69번 정답** |
| **`Options`** | 디렉터리 기능 (`Indexes`=목록 표시, `FollowSymLinks`, `ExecCGI`) |
| **`Require`** | 접근 제어 (`Require all granted` / `denied` / `ip 192.168.1.0/24`) — Apache 2.4 |
| `ErrorLog` | **오류** 로그 경로 |
| `CustomLog` | **접근** 로그 경로 + 형식 |
| `LogLevel` | 로그 상세도 |
| `KeepAlive` | 연결 재사용 여부 (`On`/`Off`) |
| `KeepAliveTimeout` | 재사용 연결 유지 시간 |
| **`MaxKeepAliveRequests`** | **KeepAlive 연결 1개당 처리할 최대 요청 수** (동시 접속 IP 수가 아님 — 67번 ③ 오답 근거) |
| `Timeout` | 요청 타임아웃 |
| `LoadModule` | 모듈 적재 |
| `User` / `Group` | httpd 실행 계정 (보통 `apache`) |
| `Alias` | URL 경로를 다른 디렉터리로 매핑 |
| `Redirect` | URL 리다이렉트 |

**`.htaccess`란?** — 디렉터리 안에 두는 분산 설정 파일임. 주 설정 파일을 못 고치는 사용자(웹호스팅 이용자)가 그 디렉터리의 설정만 바꿀 수 있게 해줌. **`AllowOverride None`이면 `.htaccess`가 있어도 무시됨.** 성능상 운영 서버에서는 `None`을 권장함.

#### 가상호스트(Virtual Host) — 68번

한 대의 서버에서 **여러 도메인의 사이트**를 운영하는 기능임. 두 방식이 있음.

| 방식 | 구분 기준 | IP 필요 수 | 특징 |
| --- | --- | --- | --- |
| **이름 기반**(name-based) | **HTTP `Host` 헤더**(= `ServerName`) | **1개** | 오늘날의 표준. IP 절약 ← **68번 정답 ②** |
| **IP 기반**(IP-based) | **접속한 IP 주소** | 도메인 수만큼 | SSL 초기 방식, 별도 NIC/IP 필요 |

```apache
<VirtualHost *:80>                      # *:80 = 모든 IP의 80포트 → 이름 기반
    ServerName www.example.com          # 이 이름으로 온 요청을 여기서 처리
    ServerAlias example.com
    DocumentRoot /var/www/example
    ErrorLog  logs/example-error_log
    CustomLog logs/example-access_log combined
</VirtualHost>

<VirtualHost 192.168.1.10:80>           # 특정 IP 명시 → IP 기반
    ServerName www.other.com
    DocumentRoot /var/www/other
</VirtualHost>
```

68번에서 `*:80`(IP를 특정하지 않음) + `ServerName`이 있으므로 **이름 기반**임. ④의 "DocumentRoot가 로그 경로"는 명백한 오답(로그는 `ErrorLog`/`CustomLog`)이고, ③은 포트가 80이지 443이 아님.

**이름 기반 가상호스트의 원리** — 브라우저가 요청 헤더에 `Host: www.example.com`을 실어 보냄. Apache는 그 값을 `ServerName`/`ServerAlias`와 대조해 어느 사이트인지 결정함. HTTPS에서는 암호화 전에 도메인을 알려주는 **SNI**(Server Name Indication) 확장이 같은 역할을 함.

```bash
httpd -t                  # 설정 문법 검사 (= apachectl configtest)
httpd -S                  # 가상호스트 구성 확인
httpd -M                  # 적재된 모듈 목록
apachectl restart / graceful
systemctl restart httpd
```

#### Nginx — 70번(정답 ①)

| 항목 | **Apache** | **Nginx** |
| --- | --- | --- |
| 처리 구조 | **프로세스/스레드 기반**(요청마다 할당, prefork·worker·event MPM) | **비동기 이벤트 기반**(적은 프로세스가 다수 연결 처리) |
| 동시 접속 | 많아지면 메모리 급증 | **대량 동시 접속에 강함**(C10K 문제 해결) |
| 강점 | 모듈 생태계, `.htaccess`, 동적 콘텐츠 내장 처리 | **정적 파일**, **리버스 프록시**, **로드밸런서** |
| 설정 파일 | `httpd.conf` | **`nginx.conf`** (`/etc/nginx/nginx.conf`) |
| 동적 처리 | 모듈 내장(mod_php) | 외부로 위임(FastCGI → php-fpm) |

**리버스 프록시(reverse proxy)** — 클라이언트 앞에 서서 요청을 받아 뒤쪽 실제 서버(WAS)로 전달하고 응답을 되돌려주는 역할임. 캐싱·부하 분산·SSL 종료·보안 차단을 한곳에서 처리할 수 있어 웹 서비스의 표준 구조가 됨. **프록시(forward)** 는 클라이언트를 대신하고, **리버스 프록시**는 서버를 대신한다는 점이 다름.

### 5-2. DNS — 이름 해석의 전 과정

> 71번 오답(② 선택, 정답 ③) · 72~74번 무응답

**DNS** = Domain Name System. 도메인 이름을 IP 주소로 변환하는 분산 데이터베이스임. **53번 포트**(질의는 UDP, 존 전송은 TCP)를 씀.

#### 이름 해석 관련 파일 3종 — 71번이 물은 부분

| 파일 | 역할 |
| --- | --- |
| **`/etc/hosts`** | **IP ↔ 호스트명 정적 매핑.** DNS를 거치지 않는 로컬 사전 (71번 ①이 이것) |
| **`/etc/resolv.conf`** | **질의할 DNS 서버 지정.** `nameserver 8.8.8.8` ← **71번 정답 ③** |
| **`/etc/nsswitch.conf`** | **조회 순서 결정.** `hosts: files dns` = hosts 파일 먼저, 그다음 DNS (71번 ②가 이것) |

```
# /etc/hosts
127.0.0.1       localhost
192.168.1.10    srv01.lab.local  srv01

# /etc/resolv.conf
nameserver 192.168.1.1        # 질의할 DNS 서버 (최대 3개)
nameserver 8.8.8.8
search lab.local              # 짧은 이름에 자동으로 붙일 도메인
domain lab.local
options timeout:2 attempts:3

# /etc/nsswitch.conf
hosts:      files dns         # files(=/etc/hosts) → dns 순서
```

`resolv.conf`는 NetworkManager나 DHCP가 자동으로 덮어쓰는 경우가 많음. 고정하려면 NetworkManager 설정에서 DNS를 지정해야 함.

#### DNS 서버 유형

| 유형 | 역할 |
| --- | --- |
| **마스터(주, master/primary)** | **존 데이터의 원본**을 보유. 관리자가 여기서 수정 |
| **슬레이브(부, slave/secondary)** | 마스터로부터 **존 전송(zone transfer)** 으로 복사본을 받음 |
| **캐시 전용(caching-only)** | 자기 존이 없음. 질의를 대신 수행하고 결과를 캐시 |
| **포워딩(forwarding)** | 모든 질의를 다른 서버로 전달 |

#### BIND 설정 — 72번

**BIND** = Berkeley Internet Name Domain. 리눅스 표준 DNS 서버 구현이고 데몬 이름은 **`named`** 임.

- 주 설정: **`/etc/named.conf`**
- 존 파일: `/var/named/*.zone`

```
# /etc/named.conf
options {
    listen-on port 53 { any; };
    directory "/var/named";           # 존 파일 기준 디렉터리
    allow-query { any; };
    recursion yes;
    forwarders { 8.8.8.8; };
};

zone "example.com" IN {
    type master;                      # 이 서버가 원본 보유  ← 72번 정답 ④
    file "example.com.zone";          # 존 데이터 파일명
    allow-transfer { 192.168.1.20; }; # 슬레이브에게만 전송 허용
};

zone "1.168.192.in-addr.arpa" IN {    # 역방향 존
    type master;
    file "192.168.1.rev";
};
```

슬레이브라면 이렇게 됨 — 72번 ①이 틀린 이유:

```
zone "example.com" IN {
    type slave;
    masters { 192.168.1.10; };        # 어디서 받아올지 명시 필요
    file "slaves/example.com.zone";
};
```

#### 존 파일과 레코드 유형 — 73번·74번

```
$TTL 86400
@   IN  SOA  ns1.example.com. admin.example.com. (
            2026090601  ; Serial   (변경 시 반드시 증가시켜야 슬레이브가 갱신함)
            3600        ; Refresh  (슬레이브가 확인하는 주기)
            1800        ; Retry    (실패 시 재시도 간격)
            604800      ; Expire   (연락 안 되면 데이터 폐기)
            86400 )     ; Minimum/Negative TTL

@       IN  NS   ns1.example.com.
@       IN  MX   10  mail.example.com.        ← 73번
ns1     IN  A    192.168.1.10
www     IN  A    192.168.1.20
mail    IN  A    192.168.1.30
ftp     IN  CNAME www.example.com.
@       IN  TXT  "v=spf1 mx -all"
```

| 레코드 | 원어 | 역할 |
| --- | --- | --- |
| **A** | Address | **도메인 → IPv4 주소** |
| **AAAA** | — | 도메인 → **IPv6** 주소 |
| **CNAME** | Canonical Name | **별칭**. 다른 도메인 이름을 가리킴 |
| **MX** | Mail eXchanger | **메일 수신 서버 지정.** 앞의 숫자는 **우선순위 — 작을수록 우선** ← **73번 정답 ②** |
| **NS** | Name Server | 그 존의 **네임서버 지정**(하위 도메인 위임) |
| **PTR** | PoinTeR | **IP → 도메인 (역방향 조회)** ← **74번 정답 ①** |
| **SOA** | Start Of Authority | 존의 **권한 시작**. 시리얼·갱신 주기 등 존 전체 정보 |
| **TXT** | Text | 임의 텍스트 (SPF·DKIM·소유권 확인) |
| **SRV** | Service | 서비스의 호스트·포트 |

**역방향 조회(reverse lookup)** — IP를 도메인으로 바꾸는 것임. IP를 **거꾸로 뒤집고 `in-addr.arpa`를 붙인** 특수 도메인에 PTR 레코드를 등록함.

```
192.168.1.20 의 역방향 이름 →  20.1.168.192.in-addr.arpa
20  IN  PTR  www.example.com.
```

메일 서버는 발신 IP의 PTR이 없으면 스팸으로 취급되는 경우가 많아, 실무에서 역방향 등록이 중요함.

**시리얼 번호는 반드시 증가시켜야 함** — 슬레이브는 시리얼을 비교해 갱신 여부를 판단하므로, 존 파일을 고치고 시리얼을 안 올리면 변경이 전파되지 않음. 관례상 `YYYYMMDDNN` 형식을 씀.

**조회 도구:**

```bash
dig www.example.com                  # 표준 조회 도구
dig @8.8.8.8 example.com MX          # 특정 서버에 MX 질의
dig -x 192.168.1.20                  # -x = 역방향 조회(PTR)
dig example.com AXFR                 # 존 전송 시도(보안상 차단돼야 정상)
nslookup www.example.com             # 대화형/구형 도구
host www.example.com                 # 간단 조회
named-checkconf                      # named.conf 문법 검사
named-checkzone example.com /var/named/example.com.zone   # 존 파일 검사
rndc reload                          # 설정 재적재
```

### 5-3. 메일 시스템 — MTA·MDA·MUA

> 75~78번 전부 무응답 — 정답 ③(IMAP 143), ②(`/etc/mail/access`), ④(`main.cf`), ①(Dovecot=POP3/IMAP)

**메일이 흐르는 경로와 각 구성 요소의 역할을 먼저 잡아야 전부 정리됨.**

```
 보내는 사람                                              받는 사람
  ┌─────┐   SMTP    ┌─────┐   SMTP    ┌─────┐          ┌─────┐
  │ MUA │ ────────▶ │ MTA │ ────────▶ │ MTA │          │ MUA │
  └─────┘  (발송)   └─────┘  (중계)   └──┬──┘          └──▲──┘
  Outlook            postfix            postfix           │
  Thunderbird        sendmail             │ MDA           │ POP3 / IMAP
                                          ▼               │  (수신 조회)
                                     [ 메일함 ] ◀── Dovecot ┘
                                   /var/spool/mail/kim
```

| 약어 | 원어 | 역할 | 소프트웨어 |
| --- | --- | --- | --- |
| **MUA** | Mail User Agent | 사용자가 쓰는 **메일 클라이언트** | Outlook, Thunderbird, `mail`, `mutt` |
| **MTA** | Mail Transfer Agent | **메일 발송·중계**(SMTP) | **sendmail**, **Postfix**, qmail, Exim |
| **MDA** | Mail Delivery Agent | 도착한 메일을 **사용자 메일함에 배달** | procmail, maildrop, dovecot-lda |
| **MRA/MAA** | Mail Retrieval Agent | 사용자가 **메일함을 조회**(POP3/IMAP) | **Dovecot**, Courier |

#### 프로토콜과 포트 — 75번

| 프로토콜 | 원어 | 역할 | **기본 포트** | SSL/TLS 포트 |
| --- | --- | --- | --- | --- |
| **SMTP** | Simple Mail Transfer Protocol | **발송·중계** | **25** | 465(SMTPS), 587(제출용 STARTTLS) |
| **POP3** | Post Office Protocol v3 | **수신 — 서버에서 내려받고 보통 삭제** | **110** | **995**(POP3S) |
| **IMAP** | Internet Message Access Protocol | **수신 — 서버에 두고 동기화** | **143** | **993**(IMAPS) |

**25 / 110 / 143** 세 숫자와 **465 / 995 / 993** 세 숫자를 묶어서 외울 것. 75번은 이 셋을 서로 뒤바꿔 놓은 문제였고 ③(IMAP 143)만 맞음.

**POP3 vs IMAP** — POP3는 내려받고 서버에서 지우는 방식이라 한 기기에서만 볼 수 있음. IMAP은 서버에 원본을 두고 상태(읽음·폴더)를 동기화하므로 **여러 기기에서 같은 메일함**을 봄. 오늘날은 IMAP이 표준임.

#### sendmail — 76번

| 파일 | 역할 |
| --- | --- |
| `/etc/mail/sendmail.cf` | 주 설정 파일(직접 편집 어려움. `sendmail.mc` → `m4`로 생성) |
| `/etc/mail/sendmail.mc` | 사람이 편집하는 매크로 설정 |
| **`/etc/mail/access`** | **호스트·도메인별 접근 정책**(RELAY/OK/REJECT/DISCARD) ← **76번 정답 ②** |
| `/etc/mail/local-host-names` | **이 서버가 수신을 책임지는 도메인 목록** |
| `/etc/mail/virtusertable` | 가상 사용자 매핑 |
| `/etc/aliases` | **메일 별칭**(`postmaster: root`). 수정 후 **`newaliases`** 실행 |
| `/var/spool/mail/<사용자>` | 사용자 메일함 |
| `/var/spool/mqueue` | 발송 대기 큐 |

```
# /etc/mail/access
192.168.1              RELAY      # 이 대역은 릴레이 허용
spam.example.com       REJECT     # 거부(에러 반환)
bad.example.com        DISCARD    # 조용히 폐기
localhost              OK

makemap hash /etc/mail/access < /etc/mail/access   # 텍스트를 db 로 변환 (필수)
```

**릴레이(relay)** — 자기 도메인 소속이 아닌 메일을 대신 전달하는 것임. 아무나 쓰게 열어두면(**open relay**) 스팸 발송에 악용되므로 반드시 `access`로 제한해야 함. 시험에도 "오픈 릴레이 차단"이 자주 나옴.

#### Postfix — 77번

sendmail을 대체한 현대적 MTA임. RHEL 계열의 기본 MTA임.

| 파일 | 역할 |
| --- | --- |
| **`/etc/postfix/main.cf`** | **주 설정 파일.** 호스트명·도메인·네트워크·릴레이 정책 ← **77번 정답 ④** |
| **`/etc/postfix/master.cf`** | **데몬 프로세스 구성** (어떤 서비스를 어떤 방식으로 띄울지) |

```
# main.cf 주요 항목 — 77번 문제에 나온 것들
myhostname = mail.example.com        # 이 서버의 FQDN
mydomain   = example.com             # 도메인
myorigin   = $mydomain               # 발신 주소에 붙일 도메인
inet_interfaces = all                # 수신할 네트워크 인터페이스 (localhost = 로컬만)
mydestination = $myhostname, localhost, $mydomain   # 로컬 배달할 도메인
mynetworks = 127.0.0.0/8, 192.168.1.0/24            # 릴레이 허용 대역
relayhost  = [smtp.isp.com]:587      # 상위 릴레이 서버
home_mailbox = Maildir/              # Maildir 형식 사용
```

```bash
postconf -n            # 기본값과 다른 설정만 출력
postfix check          # 설정 점검
postfix reload
mailq / postqueue -p   # 대기 큐 확인
postsuper -d ALL       # 큐 비우기
```

**mbox vs Maildir:**

| 형식 | 구조 | 특징 |
| --- | --- | --- |
| **mbox** | 메일함 **하나의 파일**에 전부 이어붙임 (`/var/spool/mail/kim`) | 단순하지만 동시 접근 시 잠금 문제 |
| **Maildir** | 메일 **하나당 파일 하나** (`~/Maildir/{new,cur,tmp}`) | 잠금 불필요, 대용량에 유리. 현대 표준 |

#### Dovecot — 78번

**POP3·IMAP 서버**임. 즉 **사용자가 메일함을 읽게 해주는 쪽**이고, 보내는 쪽(MTA)이 아님 — 이것이 78번의 전부임.

- 설정: `/etc/dovecot/dovecot.conf`, `/etc/dovecot/conf.d/*.conf`

```
protocols = imap pop3 lmtp
mail_location = maildir:~/Maildir
ssl = required
disable_plaintext_auth = yes
```

**전형적인 메일 서버 구성** — Postfix(발송·수신) + Dovecot(조회) + SpamAssassin(스팸 필터) + ClamAV(바이러스 검사) 조합임. 78번 선지 ④의 "스팸 필터링 전용"은 SpamAssassin의 설명임.

### 5-4. NFS — 유닉스 파일 공유

> 79번·80번 무응답 — 정답 ②(no_root_squash 설명이 반대), ③(`showmount -e`)

**NFS** = Network File System. 썬 마이크로시스템즈가 만든 **유닉스/리눅스 간 파일 공유** 프로토콜임. 원격 디렉터리를 로컬 디렉터리처럼 마운트해서 씀. **RPC**(Remote Procedure Call)를 기반으로 하며 NFSv4는 **2049 포트**를 씀.

- 서버 설정: **`/etc/exports`**
- 데몬: `nfs-server`, `rpcbind`

```
# /etc/exports  형식:  공유경로  클라이언트(옵션,옵션,...)
/share    192.168.1.0/24(rw,sync,no_root_squash)
/pub      *(ro,sync)
/home     192.168.1.10(rw,sync,root_squash,no_subtree_check)
```

**주요 옵션 — 79번의 핵심:**

| 옵션 | 의미 |
| --- | --- |
| `ro` / `rw` | 읽기 전용 / 읽기·쓰기 |
| **`sync`** | **디스크에 실제로 기록한 뒤 응답**(안전, 느림) |
| `async` | 메모리에 받고 바로 응답(빠름, 정전 시 유실) |
| **`root_squash`** | **기본값.** 클라이언트의 **root를 익명 사용자(nfsnobody)로 강등** |
| **`no_root_squash`** | **클라이언트 root를 서버에서도 root로 인정** ← **79번 ②가 설명을 반대로 한 것** |
| `all_squash` | **모든 사용자**를 익명으로 강등 |
| `anonuid` / `anongid` | 익명 매핑 시 사용할 UID/GID |
| `no_subtree_check` | 하위 트리 검사 생략(성능·안정성) |
| `secure` | 1024 미만 포트에서 온 요청만 허용 |

**squash("짓누르다")의 의미** — 클라이언트에서 root인 사람이 서버 파일까지 root 권한으로 만지면 위험하므로, 기본적으로 권한을 익명 사용자 수준으로 **깔아뭉갬**. `no_root_squash`는 그 보호를 **끄는** 옵션이라 보안상 위험함. 79번은 이 방향을 뒤집어 놓은 문제임.

**명령 — 서버와 클라이언트를 구분할 것(80번의 핵심):**

```bash
# 서버 측
exportfs -r                    # re-export. /etc/exports 변경 반영
exportfs -a                    # all. 전체 export
exportfs -v                    # 현재 공유 목록 확인(서버 로컬)
exportfs -u /share             # unexport
systemctl restart nfs-server

# 클라이언트 측
showmount -e 192.168.1.10      # -e = exports. 서버의 공유 목록 원격 조회 ← 80번 정답 ③
mount -t nfs 192.168.1.10:/share /mnt/share
umount /mnt/share
nfsstat                        # NFS 통계
rpcinfo -p 192.168.1.10        # RPC 서비스 목록
```

`/etc/fstab`에 넣을 때는 **`_netdev`** 옵션이 필요함(네트워크가 올라온 뒤 마운트):

```
192.168.1.10:/share  /mnt/share  nfs  defaults,_netdev  0 0
```

### 5-5. Samba — 윈도 파일 공유

> 81번·82번 무응답 — 정답 ④(kim 전용 쓰기 가능 공유), ①(smbclient 설명이 틀림)

**Samba** = 리눅스에서 **SMB/CIFS** 프로토콜을 구현해 **윈도와 파일·프린터를 공유**하게 해주는 소프트웨어임.

| 약어 | 원어 |
| --- | --- |
| **SMB** | Server Message Block |
| **CIFS** | Common Internet File System (SMB의 확장 명칭) |
| **NetBIOS** | Network Basic Input/Output System |

- 설정: **`/etc/samba/smb.conf`**
- 포트: 445(SMB 직접), 139(NetBIOS over TCP), 137·138(UDP, 이름 서비스)

**데몬 3종 — 82번이 물은 지식:**

| 데몬 | 역할 |
| --- | --- |
| **`smbd`** | **파일·프린터 공유, 인증** (핵심 데몬) |
| **`nmbd`** | **NetBIOS 이름 해석**, 브라우징(네트워크 환경 목록) |
| `winbindd` | 윈도 도메인(AD) 사용자·그룹 연동 |

**설정 파일 구조 — 81번:**

```ini
[global]                              # 전역 설정
   workgroup = WORKGROUP
   server string = Samba Server
   security = user                    # user(계정 인증) / share(구버전)
   map to guest = Bad User

[share]                               # 공유 이름 (클라이언트에 보이는 이름)
   path = /srv/samba/share            # 서버의 "실제" 경로
   writable = yes                     # 쓰기 허용 (= read only = no)
   valid users = kim                  # 접근 허용 사용자
   browseable = yes                   # 목록에 표시
   create mask = 0664
   directory mask = 0775
   guest ok = no                      # 익명 접근 금지
```

**81번 정답 ④ 분해** — `path`=서버 실제 경로(③이 "클라이언트 마운트 지점"이라 한 것이 오답), `writable = yes`=쓰기 가능(②가 "읽기 전용"이라 한 것이 오답), `valid users = kim`=kim만 접근(①이 "익명 공유"라 한 것이 오답).

**주요 명령 — 82번의 핵심:**

| 명령 | 역할 |
| --- | --- |
| **`smbclient`** | **공유 자원에 접속하는 FTP 유사 클라이언트** ← 82번 ①이 이것을 "암호 등록"이라 잘못 설명 |
| **`smbpasswd`** | **삼바 계정 암호 등록·변경** (`smbpasswd -a kim`) |
| `pdbedit` | 삼바 계정 데이터베이스 관리 (`pdbedit -L`) |
| **`testparm`** | **smb.conf 문법 검사** |
| `smbstatus` | 현재 접속·잠금 상태 |
| `nmblookup` | NetBIOS 이름 조회 |
| `mount -t cifs` | 리눅스에서 윈도/삼바 공유 마운트 |

```bash
smbclient -L //192.168.1.10 -U kim        # -L = list. 공유 목록 조회
smbclient //192.168.1.10/share -U kim     # 접속(FTP 처럼 get/put 사용)
smbpasswd -a kim                          # -a = add. 삼바 계정 추가
testparm                                  # 설정 검사
mount -t cifs //192.168.1.10/share /mnt -o username=kim
```

**중요** — 삼바 계정은 리눅스 계정과 **별개의 암호 데이터베이스**를 씀. 리눅스에 `kim`이 있어도 `smbpasswd -a kim`을 해야 삼바로 접속됨. 시험에 자주 나옴.

**NFS vs Samba:**

| 항목 | NFS | Samba |
| --- | --- | --- |
| 프로토콜 | NFS(RPC) | SMB/CIFS |
| 주 용도 | **유닉스 ↔ 유닉스** | **리눅스 ↔ 윈도** |
| 포트 | 2049 | 445, 139 |
| 설정 | `/etc/exports` | `/etc/samba/smb.conf` |
| 권한 모델 | UID/GID 기반 | 계정 인증 기반 |

### 5-6. FTP — vsftpd

> 83번 무응답 — 정답 ②

**FTP** = File Transfer Protocol. **vsftpd** = **v**ery **s**ecure **FTP d**aemon으로 리눅스 표준 FTP 서버임.

- 설정: **`/etc/vsftpd/vsftpd.conf`**
- 포트: **21**(제어), **20**(데이터, 능동 모드)

**주요 설정 — 83번의 세 줄이 그대로 시험 범위임:**

| 항목 | 의미 |
| --- | --- |
| **`anonymous_enable=NO`** | **익명(anonymous) 접속 차단** |
| **`local_enable=YES`** | **로컬 계정 사용자 접속 허용** |
| **`write_enable=YES`** | **쓰기(업로드·삭제·이름변경) 허용** |
| `chroot_local_user=YES` | 사용자를 자기 홈 디렉터리에 **가둠**(상위로 못 올라감) |
| `local_umask=022` | 업로드 파일의 umask |
| `ftpd_banner=` | 접속 배너 |
| `userlist_enable=YES` | `/etc/vsftpd/user_list` 목록 사용 |
| `userlist_deny=YES` | 그 목록을 **거부** 목록으로(NO면 허용 목록) |
| `ssl_enable=YES` | FTPS 활성화 |
| `pasv_enable=YES` | 수동 모드 허용 |

| 파일 | 역할 |
| --- | --- |
| `/etc/vsftpd/ftpusers` | **접속 금지 사용자 목록**(root 등이 기본 등록) |
| `/etc/vsftpd/user_list` | `userlist_deny` 값에 따라 거부/허용 목록 |
| `/var/log/xferlog` | 전송 로그 |

**능동 모드 vs 수동 모드 — 시험 단골:**

| 모드 | 데이터 연결을 여는 쪽 | 포트 | 방화벽 |
| --- | --- | --- | --- |
| **능동(Active)** | **서버 → 클라이언트** | 서버의 **20번**에서 출발 | **클라이언트 방화벽에 막힘** |
| **수동(Passive)** | **클라이언트 → 서버** | 서버가 알려준 임의 고포트 | 오늘날 대부분 이 모드를 씀 |

FTP는 **제어·데이터가 모두 평문**이라 계정 정보가 노출됨. 대안으로 **FTPS**(FTP over SSL/TLS)나 **SFTP**(SSH 기반, 전혀 다른 프로토콜)를 씀. SFTP는 이름만 비슷할 뿐 SSH의 하위 기능임.

### 5-7. DHCP

> 84번 무응답 — 정답 ④(기본 게이트웨이)

**DHCP** = Dynamic Host Configuration Protocol. 클라이언트에게 **IP 주소와 네트워크 설정을 자동 배포**하는 프로토콜임. 서버 **67**/UDP, 클라이언트 **68**/UDP를 씀.

- 설정: **`/etc/dhcp/dhcpd.conf`**
- 임대 정보: `/var/lib/dhcpd/dhcpd.leases`
- 데몬: `dhcpd`

```
# /etc/dhcp/dhcpd.conf
default-lease-time 86400;             # 기본 임대 기간(초)
max-lease-time     172800;            # 최대 임대 기간

subnet 192.168.5.0 netmask 255.255.255.0 {
    range 192.168.5.100 192.168.5.200;          # 배포할 IP 범위(풀)
    option routers 192.168.5.1;                 # 기본 게이트웨이  ← 84번 정답 ④
    option domain-name-servers 8.8.8.8, 1.1.1.1; # DNS 서버
    option domain-name "example.com";
    option subnet-mask 255.255.255.0;
    option broadcast-address 192.168.5.255;
}

host printer {                        # 고정 IP 예약
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 192.168.5.50;
}
```

**옵션 이름과 전달 정보 — 84번이 물은 대응:**

| 옵션 | 전달하는 것 |
| --- | --- |
| **`option routers`** | **기본 게이트웨이 주소** |
| `option domain-name-servers` | **DNS 서버 주소** (84번 ①) |
| `default-lease-time` / `max-lease-time` | **IP 임대 기간** (84번 ②) |
| `option broadcast-address` | 브로드캐스트 주소 (84번 ③) |
| `option subnet-mask` | 서브넷 마스크 |
| `range` | 배포할 IP 범위 |

`routers`가 게이트웨이인 이유 — 라우터가 곧 그 네트워크의 출구(게이트웨이)이기 때문임. 이름과 역할이 미묘하게 어긋나서 함정으로 잘 쓰임.

**DHCP 동작 4단계 — DORA:**

| 단계 | 방향 | 내용 |
| --- | --- | --- |
| **D**iscover | 클라이언트 → 브로드캐스트 | "DHCP 서버 있나요?" |
| **O**ffer | 서버 → 클라이언트 | "이 IP 어때요?" |
| **R**equest | 클라이언트 → 브로드캐스트 | "그 IP 쓸게요" |
| **A**ck | 서버 → 클라이언트 | "승인. 임대 기간은 N초" |

> DHCP 개념과 임대 파일 해석은 [[../../QA#D-1. DHCP 란 무엇인가]], [[../../QA#D-2. `dhcpd_leases` 에 응답 없는 IP 가 보이는 이유]] 참조.

### 5-8. SSH

> 85번·86번 무응답 — 정답 ③(평문 전송이라는 설명이 틀림), ①(`PermitRootLogin no`)

**SSH** = Secure SHell. 원격 접속 통신을 **전 구간 암호화**하는 프로토콜임. 평문으로 전송하던 telnet·rlogin·rsh를 대체함. **포트 22**.

| 항목 | telnet | **SSH** |
| --- | --- | --- |
| 포트 | 23 | **22** |
| 암호화 | **없음(평문)** | **전 구간 암호화** |
| 인증 | 패스워드 | 패스워드 + **공개키** |
| 파일 전송 | 별도(FTP) | `scp`, `sftp` 내장 |

85번 ③의 "평문 전송이라 스니핑에 취약"은 **telnet의 약점**을 SSH 설명으로 옮겨놓은 것임. SSH의 존재 이유 자체가 그것을 없애는 것이므로 명백한 오답임.

**설정 파일 — 서버와 클라이언트를 구분할 것:**

| 파일 | 대상 |
| --- | --- |
| **`/etc/ssh/sshd_config`** | **SSH 서버(sshd)** 설정 ← 86번 |
| `/etc/ssh/ssh_config` | SSH **클라이언트** 설정 |
| `~/.ssh/id_rsa` / `id_ed25519` | **개인키** (권한 600, 절대 유출 금지) |
| `~/.ssh/id_rsa.pub` | **공개키** |
| **`~/.ssh/authorized_keys`** | **접속을 허용할 공개키 목록**(서버 쪽에 둠) |
| `~/.ssh/known_hosts` | 접속했던 서버의 호스트 키 |

**`sshd_config` 보안 설정 — 실기·필기 모두 빈출:**

```
Port 22222                      # 기본 포트 변경(무차별 스캔 회피)
PermitRootLogin no              # root 원격 로그인 금지        ← 86번 정답 ①
PasswordAuthentication no       # 패스워드 인증 끄기(키만 허용)
PubkeyAuthentication yes        # 공개키 인증 허용
PermitEmptyPasswords no         # 빈 암호 금지
MaxAuthTries 3                  # 인증 시도 횟수 제한
AllowUsers kim lee              # 허용 사용자 목록
DenyUsers guest                 # 거부 사용자 목록
AllowGroups sshusers            # 허용 그룹
Protocol 2                      # SSHv1 금지(구버전)
X11Forwarding yes               # X11 포워딩
ClientAliveInterval 300         # 유휴 세션 정리
```

86번 ②`RootLogin deny`·③`DenyRoot yes`는 **존재하지 않는 지시자**이고, ④`PermitEmptyPasswords`는 빈 암호 허용 여부라 root와 무관함.

**공개키 인증 절차 — 원리를 알면 명령이 외워짐:**

```bash
ssh-keygen -t ed25519 -C "kim@laptop"     # 1. 키 쌍 생성 (-t 알고리즘, -C 주석)
ssh-copy-id kim@192.168.1.10              # 2. 공개키를 서버 authorized_keys 에 등록
ssh kim@192.168.1.10                      # 3. 암호 없이 접속
```

개인키는 내 손에만 두고, 공개키를 서버에 등록함. 서버가 공개키로 암호화한 문제를 개인키로 풀 수 있는지 검증하는 방식이므로 **암호가 네트워크를 오가지 않음**.

**부가 명령:**

```bash
scp file.txt kim@host:/tmp/               # 파일 복사
scp -r dir/ kim@host:/tmp/                # 디렉터리
scp -P 22222 file.txt kim@host:/tmp/      # 포트 지정은 대문자 -P (ssh 는 소문자 -p)
sftp kim@host                             # 대화형 파일 전송
ssh -p 22222 kim@host
ssh -L 8080:localhost:80 kim@host         # 로컬 포워딩(터널링)
ssh -X kim@host                           # X11 포워딩
```

### 5-9. LDAP·Squid

> 87번·88번 무응답 — 정답 ②(389 포트, DN 식별), ③(내부망에 3128 프록시 허용)

#### LDAP — 87번

**LDAP** = Lightweight Directory Access Protocol. 사용자·그룹·조직 정보를 **트리 구조의 디렉터리**에 저장하고 조회하는 프로토콜임. 여러 서버가 계정 정보를 공유하는 **중앙 인증**에 씀. 리눅스 구현은 **OpenLDAP**(데몬 `slapd`)임.

| 항목 | 값 |
| --- | --- |
| **포트** | **389** (LDAP), **636** (LDAPS, SSL) |
| 데몬 | `slapd` |
| 설정 | `/etc/openldap/slapd.conf` 또는 `slapd.d/` |
| 데이터 교환 형식 | **LDIF** (LDAP Data Interchange Format) |

**디렉터리 구조와 DN:**

```
dc=example,dc=com                      ← 최상위 (Base DN)
├── ou=People
│   ├── uid=kim,ou=People,dc=example,dc=com    ← 이 전체 경로가 DN
│   └── uid=lee,ou=People,dc=example,dc=com
└── ou=Groups
    └── cn=dev,ou=Groups,dc=example,dc=com
```

| 약어 | 원어 | 의미 |
| --- | --- | --- |
| **DN** | Distinguished Name | **항목을 고유하게 식별하는 전체 경로** |
| RDN | Relative DN | 한 단계의 이름(`uid=kim`) |
| **dc** | domain component | 도메인 구성요소 (`dc=example,dc=com`) |
| **ou** | organizational unit | 조직 단위(부서) |
| **cn** | common name | 일반 이름 |
| **uid** | user id | 사용자 ID |
| o | organization | 조직 |

87번 ①의 443은 **HTTPS** 포트이고, ③은 SQL, ④는 SMB의 설명임. **"389 = LDAP, DN으로 식별"** 만 잡으면 됨.

```bash
ldapsearch -x -b "dc=example,dc=com"      # -x 단순 인증, -b 검색 기준 DN
ldapadd -x -D "cn=admin,dc=example,dc=com" -W -f user.ldif
ldapmodify / ldapdelete
slaptest                                  # 설정 검사
```

#### Squid — 88번

**Squid** = 리눅스 표준 **프록시(캐시) 서버**임. 클라이언트 대신 웹 요청을 수행하고 결과를 캐시해 대역폭을 절약하며, 접근 제어·로깅에도 씀.

| 항목 | 값 |
| --- | --- |
| **기본 포트** | **3128** (대안 8080) |
| 설정 | **`/etc/squid/squid.conf`** |
| 로그 | `/var/log/squid/access.log` |
| 캐시 | `/var/spool/squid` |

```
acl allowed_net src 192.168.1.0/24    # acl 이름 유형 값  — src = 출발지 IP
acl SSL_ports port 443
acl Safe_ports port 80 21 443

http_access allow allowed_net         # 위에서 정의한 acl 을 허용
http_access deny  all                 # 나머지는 모두 거부 (마지막에 둘 것)

http_port 3128                        # 프록시 대기 포트
cache_dir ufs /var/spool/squid 100 16 256
visible_hostname proxy.example.com
```

**88번 정답 ③ 분해** — `acl`로 정의한 192.168.1.0/24 대역에 `http_access allow`를 적용하고 `http_port 3128`로 대기하므로, **내부망 클라이언트에게 3128 포트로 프록시를 제공**하는 설정임. ①(모든 외부에 개방)·②(그 대역을 차단)·④(전부 폐기)는 모두 반대 해석임.

**`http_access` 규칙은 위에서부터 순서대로 평가되고 처음 일치한 규칙에서 결정됨** — iptables와 같은 원리임. 그래서 `deny all`은 항상 맨 마지막에 둠.

**정방향 프록시 vs 리버스 프록시:**

| 구분 | 대신하는 대상 | 용도 | 예 |
| --- | --- | --- | --- |
| **정방향 프록시**(forward) | **클라이언트** | 캐시, 접근 제어, 익명화 | **Squid** |
| **리버스 프록시**(reverse) | **서버** | 부하 분산, SSL 종료, 보안 | **Nginx**, HAProxy |

### 5-10. 가상화와 컨테이너

> 89번 무응답 — 정답 ①(KVM) · 90번 정답(④) — "②는 정확히 왜 오답인지?" 요청

#### 가상화 방식 분류 — 89번

| 방식 | 원리 | 격리 수준 | 예 |
| --- | --- | --- | --- |
| **전가상화**(full virtualization) | 하드웨어를 완전히 흉내내 **수정 없는 게스트 OS** 실행 | 높음(별도 커널) | **KVM**, VMware, VirtualBox, QEMU |
| **반가상화**(para-virtualization) | 게스트 OS를 **수정**해 하이퍼바이저와 협력 | 높음 | **Xen**(전통 방식) |
| **컨테이너**(OS 수준 가상화) | **호스트 커널을 공유**하고 프로세스 공간만 격리 | 낮음(커널 공유) | **Docker**, LXC, **OpenVZ**, Podman |
| chroot | 루트 디렉터리만 바꿈 | 매우 낮음 | `chroot` |

**하이퍼바이저(hypervisor)** 유형:

| 유형 | 위치 | 예 |
| --- | --- | --- |
| **Type 1 (베어메탈)** | **하드웨어 위에 직접** | **KVM**, Xen, VMware ESXi, Hyper-V |
| **Type 2 (호스트형)** | **호스트 OS 위에서 앱처럼** | VirtualBox, VMware Workstation, UTM/QEMU |

**KVM** = Kernel-based Virtual Machine. **리눅스 커널에 모듈(`kvm.ko`, `kvm_intel.ko`/`kvm_amd.ko`)로 내장된 하이퍼바이저**임. CPU의 하드웨어 가상화 확장(**Intel VT-x / AMD-V**)이 반드시 필요하고, 장치 에뮬레이션은 **QEMU**가 맡음. 관리 도구로 `libvirt`/`virsh`/`virt-manager`를 씀.

89번 선지 분석 — **OpenVZ와 Docker는 컨테이너**(커널 공유)이므로 "하이퍼바이저"가 아니고, **chroot는 디렉터리 격리 기법**일 뿐 가상화가 아님. 문제의 "커널 모듈 + VT-x/AMD-V + QEMU 연동" 세 조건이 전부 KVM만 가리킴.

```bash
lsmod | grep kvm                    # KVM 모듈 적재 확인
egrep -c '(vmx|svm)' /proc/cpuinfo  # 하드웨어 가상화 지원 여부 (0이면 미지원)
virsh list --all                    # VM 목록
virsh start/shutdown/destroy vm1
virt-install ...                    # VM 생성
```

#### Docker 명령 — 90번

**90번에서 "②가 왜 오답인지"** — `docker rm`은 **컨테이너**를 삭제함. **이미지** 삭제는 **`docker rmi`**(rm image)임. 선지 ②는 이 둘을 바꿔놓은 것임.

| 명령 | 실제 역할 | 90번 선지가 잘못 붙인 설명 |
| --- | --- | --- |
| **`docker ps`** | **실행 중인 컨테이너 목록** (`-a`면 종료된 것까지) | — (**정답 ④**) |
| `docker images` | **이미지 목록** | ① "새 컨테이너를 생성"이라 함 (실제 생성은 `docker create`/`run`) |
| **`docker rm`** | **컨테이너 삭제** | ② "이미지를 삭제"라 함 (**이미지 삭제는 `docker rmi`**) |
| `docker pull` | 레지스트리에서 **다운로드** | ③ "업로드"라 함 (**업로드는 `docker push`**) |

**이미지와 컨테이너의 관계 — 이 구분이 모든 선지의 기반임:**

```
이미지(image)      = 실행에 필요한 파일시스템 스냅샷. 읽기 전용 "설계도"
    │  docker run / create
    ▼
컨테이너(container) = 이미지를 실행한 "인스턴스". 쓰기 계층이 추가됨
```

한 이미지에서 컨테이너를 여러 개 만들 수 있음. 그래서 **삭제 명령도 두 종류**(`rm` / `rmi`)로 나뉨.

| 명령 | 역할 |
| --- | --- |
| `docker run -d -p 8080:80 --name web nginx` | 이미지로 컨테이너 생성 + 실행 (`-d` 백그라운드, `-p` 포트 매핑) |
| `docker ps` / `docker ps -a` | 실행 중 / 전체 컨테이너 목록 |
| `docker images` | 이미지 목록 |
| `docker pull nginx` / `docker push myrepo/app` | 다운로드 / 업로드 |
| `docker start` / `stop` / `restart` | 컨테이너 시작 / 중지 / 재시작 |
| **`docker rm web`** | **컨테이너 삭제** |
| **`docker rmi nginx`** | **이미지 삭제** |
| `docker exec -it web bash` | 실행 중 컨테이너에서 명령 실행(`-it` 대화형 터미널) |
| `docker logs -f web` | 컨테이너 로그 |
| `docker build -t myapp .` | Dockerfile로 이미지 빌드 |
| `docker inspect web` | 상세 정보 |
| `docker volume` / `docker network` | 볼륨 / 네트워크 관리 |

**가상 머신 vs 컨테이너:**

| 항목 | 가상 머신 | 컨테이너 |
| --- | --- | --- |
| 커널 | **게스트마다 별도 커널** | **호스트 커널 공유** |
| 크기 | GB 단위 | MB 단위 |
| 부팅 시간 | 수십 초 | **1초 미만** |
| 격리 수준 | **강함** | 상대적으로 약함 |
| 다른 OS 실행 | 가능(리눅스 위에 윈도) | **불가**(리눅스 커널만) |

### 5-11. 네트워크 공격 기법 분류

> 91번 정답(② SYN Flooding) — "공격기법 정리 필요" · 92번 오답(② DNS 스푸핑 선택, 정답 ④ ARP 스푸핑)

**공격을 세 갈래로 나누면 선지 구분이 쉬워짐 — ①자원 고갈(DoS) ②위조(스푸핑) ③가로채기.**

#### 서비스 거부(DoS/DDoS) 계열

| 공격 | 원리 | 핵심 키워드 |
| --- | --- | --- |
| **SYN Flooding** | TCP **3-way handshake**를 악용. SYN만 대량 전송하고 ACK를 보내지 않아 서버의 **백로그 큐(연결 대기 큐)를 고갈**시킴 | **SYN 패킷 폭주**, 백로그 큐 ← **91번 정답** |
| **Smurf Attack** | **출발지를 피해자로 위조한 ICMP** echo 요청을 **브로드캐스트**로 발송 → 네트워크 전체가 피해자에게 응답 | **ICMP 증폭**, 브로드캐스트 |
| **Ping of Death** | **규격을 넘는 초대형 ICMP 패킷**을 조각내 전송, 재조립 시 버퍼 오버플로 | 초대형 ICMP |
| **Land Attack** | **출발지 IP = 목적지 IP**로 위조해 자기 자신에게 응답하는 무한 루프 유발 | **출발지=목적지** |
| **Teardrop** | IP 조각(fragment) **오프셋을 조작**해 재조립 오류 유발 | 조각 오프셋 조작 |
| **DDoS** | 다수의 좀비 PC(봇넷)로 분산 공격 | 분산·봇넷 |

**91번은 "3-way handshake + SYN만 + 백로그 큐 고갈" 세 키워드가 SYN Flooding의 정의 그대로임.** 방어책은 SYN 쿠키, 백로그 큐 확대, `net.ipv4.tcp_syncookies=1`임.

#### 위조(스푸핑, spoofing) 계열 — 92번의 핵심

| 공격 | **무엇을 위조하는가** | 발생 범위 |
| --- | --- | --- |
| **IP 스푸핑** | **출발지 IP 주소** | 어디서나 |
| **ARP 스푸핑**(ARP cache poisoning) | **MAC 주소** — "이 IP의 MAC은 나다"라고 거짓 ARP 응답을 반복 전송 | **동일 LAN 구간 내부에서만** ← **92번 정답 ④** |
| **DNS 스푸핑** | **DNS 응답** — 잘못된 IP를 알려줘 가짜 사이트로 유도 | DNS 질의 경로 |
| **이메일 스푸핑** | 발신자 주소 | 메일 |

**92번을 DNS 스푸핑으로 오답한 이유를 짚으면** — 문제의 키워드 세 개가 전부 ARP를 가리킴:
1. **"동일 LAN 구간"** — ARP는 **2계층(데이터링크)** 프로토콜이라 라우터를 넘지 못함. LAN 내부에서만 성립함
2. **"위조된 MAC 주소 응답"** — MAC을 다루는 것은 **ARP**임. DNS는 도메인↔IP(3계층 이상)를 다루므로 MAC이 등장할 수 없음
3. **"트래픽이 공격자를 거쳐 가도록"** — 중간자(MITM) 위치 선점

**ARP** = Address Resolution Protocol. **IP 주소로 MAC 주소를 알아내는** 프로토콜임. "192.168.1.1 쓰는 사람 누구?"를 브로드캐스트로 묻고 해당 호스트가 자기 MAC으로 응답함. **응답에 인증이 없어서** 공격자가 먼저·자주 거짓 응답을 보내면 피해자의 ARP 캐시가 오염됨.

```bash
arp -a                        # ARP 캐시 조회 (같은 MAC이 여러 IP에 붙어 있으면 의심)
ip neigh                      # 최신 명령
arp -s 192.168.1.1 00:11:22:33:44:55   # 정적 등록(방어책)
```

**방어** — 정적 ARP 등록, 스위치의 **DAI**(Dynamic ARP Inspection)·포트 보안, arpwatch 감시.

#### 가로채기 계열

| 공격 | 원리 |
| --- | --- |
| **스니핑**(sniffing) | 네트워크를 지나는 패킷을 **수동적으로 훔쳐봄**. 랜카드를 **무차별 모드**(promiscuous)로 전환. 평문 프로토콜(telnet·FTP·HTTP)에 치명적 |
| **세션 하이재킹** | 인증이 끝난 **세션을 탈취**해 정당한 사용자인 척함(세션 ID·쿠키 탈취) |
| **중간자 공격**(MITM) | 통신 양단 사이에 끼어들어 도청·변조. ARP 스푸핑이 대표적 진입 수단 |

#### 애플리케이션 계층 공격

| 공격 | 원리 |
| --- | --- |
| **SQL 인젝션** | 입력값에 SQL 구문을 주입해 DB 조작 |
| **XSS**(Cross-Site Scripting) | 웹 페이지에 악성 스크립트를 삽입해 다른 사용자 브라우저에서 실행 |
| **CSRF**(Cross-Site Request Forgery) | 로그인 상태를 악용해 사용자 몰래 요청 전송 |
| **버퍼 오버플로** | 할당 범위를 넘는 데이터로 메모리를 덮어써 코드 실행 |
| **무차별 대입**(brute force) | 가능한 모든 조합을 시도. `lastb`로 흔적 확인 |

### 5-12. iptables — 규칙 구조와 평가 순서

> 93번·94번 무응답 — 정답 ③(내부망만 SSH 허용), ①(`-P`가 기본 정책)

**iptables**는 리눅스 커널의 **netfilter** 프레임워크를 제어하는 방화벽 도구임. RHEL 7부터는 `firewalld`가 이것을 감싸는 상위 도구로 쓰이지만 시험은 iptables 문법을 그대로 물음.

#### 구조 — 테이블 / 체인 / 규칙

| 테이블 | 용도 |
| --- | --- |
| **filter** | **패킷 허용·차단** (기본 테이블) |
| **nat** | 주소 변환 (**SNAT/MASQUERADE**, **DNAT**/포트 포워딩) |
| mangle | 패킷 헤더 변경(TOS·TTL) |
| raw | 연결 추적 제외 |

| 체인 | 언제 통과하는가 |
| --- | --- |
| **INPUT** | **이 서버로 들어오는** 패킷 |
| **OUTPUT** | **이 서버에서 나가는** 패킷 |
| **FORWARD** | **이 서버를 거쳐 지나가는** 패킷(라우터 역할) |
| PREROUTING | 라우팅 결정 **전** (nat: DNAT) |
| POSTROUTING | 라우팅 결정 **후** (nat: SNAT) |

#### 옵션 — 94번의 전부

| 옵션 | 원어 | 의미 |
| --- | --- | --- |
| **`-P`** | **P**olicy | **체인의 기본 정책 설정** (`-P INPUT DROP`) ← **94번 정답 ①** |
| **`-A`** | **A**ppend | 체인 **끝에 규칙 추가** (94번 ④가 "맨 앞 삽입"이라 해서 오답) |
| **`-I`** | **I**nsert | **맨 앞(또는 지정 위치)에 삽입** (`-I INPUT 1 ...`) |
| **`-D`** | **D**elete | 규칙 삭제 |
| **`-L`** | **L**ist | **규칙 목록 출력** (94번 ②가 "전부 삭제"라 해서 오답) |
| **`-F`** | **F**lush | **규칙 전부 비우기** (94번 ③이 "목록 출력"이라 해서 오답) |
| `-R` | **R**eplace | 규칙 교체 |
| `-N` / `-X` | New / delete chain | 사용자 정의 체인 생성 / 삭제 |
| `-Z` | **Z**ero | 카운터 초기화 |
| `-t` | **t**able | 테이블 지정 (기본 filter) |
| `-p` | **p**rotocol | 프로토콜 (`tcp`, `udp`, `icmp`, `all`) |
| `-s` | **s**ource | **출발지** IP/대역 |
| `-d` | **d**estination | **목적지** IP/대역 |
| `--sport` | source port | 출발지 포트 |
| **`--dport`** | destination port | **목적지 포트** |
| `-i` | **i**n-interface | 입력 인터페이스 |
| `-o` | **o**ut-interface | 출력 인터페이스 |
| **`-j`** | **j**ump | **처리 방식**(타깃) 지정 |
| `-m` | **m**atch | 확장 모듈 (`-m state`, `-m multiport`) |
| `-n` / `-v` | numeric / verbose | 이름 해석 안 함 / 상세 |

**타깃(`-j` 뒤에 오는 값):**

| 타깃 | 동작 |
| --- | --- |
| **ACCEPT** | **허용** |
| **DROP** | **조용히 폐기**(응답 없음 → 공격자가 존재 여부를 모름) |
| **REJECT** | **거부 + 오류 응답 전송**(빠른 실패, 내부망에 적합) |
| LOG | 로그 기록 후 **다음 규칙으로 계속** |
| SNAT / MASQUERADE | 출발지 주소 변환(내부→외부) |
| DNAT / REDIRECT | 목적지 주소 변환(포트 포워딩) |

#### 규칙 평가 순서 — 93번의 핵심

**규칙은 위에서부터 순서대로 검사하고, 처음 일치하는 규칙에서 처리가 끝남(first match wins).** 그 뒤 규칙은 보지 않음. 어느 것도 일치하지 않으면 **체인의 기본 정책(`-P`)** 이 적용됨.

```bash
iptables -A INPUT -p tcp --dport 22 -s 192.168.1.0/24 -j ACCEPT   # 규칙 1
iptables -A INPUT -p tcp --dport 22 -j DROP                        # 규칙 2
```

| 접속 시도 | 규칙 1 일치? | 결과 |
| --- | --- | --- |
| 192.168.1.50 → 22번 | **일치** | **ACCEPT** (규칙 2를 보지 않음) |
| 10.0.0.5 → 22번 | 불일치(출발지 다름) | 규칙 2에 일치 → **DROP** |

즉 **내부망(192.168.1.0/24)의 SSH만 허용하고 나머지 SSH는 전부 차단** — 93번 정답 ③임.

**순서를 뒤집으면 정반대가 됨** — DROP 규칙을 먼저 쓰면 모든 SSH가 차단되고 ACCEPT 규칙은 영원히 도달하지 못함. 이것이 iptables에서 가장 흔한 실수임.

#### 실무 예시

```bash
# 기본 정책 — 들어오는 것은 막고 나가는 것은 허용(화이트리스트 방식)
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# 루프백은 항상 허용
iptables -A INPUT -i lo -j ACCEPT

# 이미 맺어진 연결의 응답은 허용 (이것이 없으면 아무 통신도 안 됨)
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# 서비스별 허용
iptables -A INPUT -p tcp --dport 22 -s 192.168.1.0/24 -j ACCEPT
iptables -A INPUT -p tcp -m multiport --dports 80,443 -j ACCEPT
iptables -A INPUT -p icmp --icmp-type echo-request -j ACCEPT

# 확인·저장
iptables -L -n -v --line-numbers      # 줄 번호까지 확인
iptables -D INPUT 3                   # 3번 규칙 삭제
iptables-save > /etc/sysconfig/iptables
iptables-restore < /etc/sysconfig/iptables
```

**`-P INPUT DROP`을 원격에서 먼저 실행하면 자기 SSH가 끊김.** 반드시 SSH 허용 규칙을 먼저 넣고 정책을 바꿔야 함.

**firewalld (RHEL 7+ 기본):**

```bash
firewall-cmd --state
firewall-cmd --get-active-zones
firewall-cmd --permanent --add-service=http     # --permanent 는 영구
firewall-cmd --permanent --add-port=8080/tcp
firewall-cmd --reload                           # permanent 변경 반영
firewall-cmd --list-all
```

### 5-13. 보안 솔루션과 암호화

> 95~97번 무응답 — 정답 ④(Snort=NIDS), ②(VPN), ③(TLS 하이브리드) · 98번 정답(① AES)

#### 보안 도구 분류 — 95번

| 도구 | 분류 | 역할 |
| --- | --- | --- |
| **Snort** | **NIDS** | **시그니처(규칙) 기반 네트워크 침입 탐지.** 스니퍼·패킷 로거·NIDS **3가지 모드** 지원 ← 95번 정답 ④ |
| Suricata | NIDS/NIPS | Snort 호환, 멀티스레드 |
| **Tripwire** | **HIDS** | **파일 무결성 검사**(해시 비교로 변조 탐지) — 95번 ①이 이것 |
| AIDE | HIDS | Tripwire의 오픈소스 대안 |
| **Nessus / OpenVAS** | **취약점 스캐너** | 시스템 취약점 점검 — 95번 ②가 이것 |
| **John the Ripper / hydra** | 패스워드 크래커 | 암호 강도 점검 — 95번 ③이 이것 |
| Nmap | 포트 스캐너 | 열린 포트·서비스·OS 탐지 |
| Wireshark / tcpdump | 패킷 분석기 | 트래픽 캡처·분석 |
| fail2ban | 침입 차단 | 로그를 보고 공격 IP를 자동 차단 |

**IDS vs IPS, HIDS vs NIDS — 개념 문제로 자주 나옴:**

| 구분 | 원어 | 차이 |
| --- | --- | --- |
| **IDS** | Intrusion **Detection** System | **탐지·경고만** (통로 옆에서 관찰) |
| **IPS** | Intrusion **Prevention** System | **탐지 + 차단** (통로 위에 위치) |
| **HIDS** | **Host**-based IDS | **개별 호스트**의 로그·파일 변조 감시 (Tripwire, AIDE) |
| **NIDS** | **Network**-based IDS | **네트워크 구간**의 패킷 감시 (**Snort**) |

**탐지 방식:**

| 방식 | 원리 | 장단점 |
| --- | --- | --- |
| **시그니처(오용) 탐지** | 알려진 공격 패턴과 대조 | 정확하지만 **신종 공격 탐지 불가** |
| **이상(anomaly) 탐지** | 정상 행위와의 편차 측정 | 신종 탐지 가능하지만 **오탐 많음** |

#### VPN — 96번

**VPN** = Virtual Private Network. **공중망(인터넷) 위에 터널링과 암호화를 적용해 전용선처럼 안전한 통신로를 만드는 기술**임. **물리적 전용 회선이 필요 없다는 것이 핵심 가치**임(96번 ①이 이걸 뒤집은 선지).

| 방식 | 계층 | 특징 |
| --- | --- | --- |
| **IPsec VPN** | 3계층(네트워크) | 사이트 간(site-to-site) 연결에 주로 사용. AH(인증)·ESP(암호화) 프로토콜 |
| **SSL/TLS VPN** | 4~7계층 | 브라우저만 있으면 접속 가능. 원격 사용자 접속에 유리 |
| PPTP / L2TP | 2계층 | 구형. PPTP는 보안 취약으로 사용 지양 |
| WireGuard / OpenVPN | — | 현대적 구현 |

**터널링(tunneling)** — 원래의 패킷을 통째로 다른 패킷 안에 캡슐화해 전송하는 기법임. 공중망을 지나는 동안 내부 내용이 감춰짐.

#### SSL/TLS 동작 — 97번

**SSL** = Secure Sockets Layer, **TLS** = Transport Layer Security(SSL의 후속 표준명). 오늘날 쓰이는 것은 전부 TLS이지만 관행적으로 SSL이라 부름.

**하이브리드 구조 — 97번의 정답 근거:**

```
1. 핸드셰이크 단계
   서버가 인증서(공개키 포함) 제시  →  클라이언트가 CA 서명 검증
   비대칭키(공개키)로 세션키를 안전하게 합의        ← 느리지만 안전한 키 교환
2. 데이터 전송 단계
   합의된 세션키(대칭키)로 실제 데이터 암호화       ← 빠름
```

**왜 나누는가** — 비대칭키는 안전하지만 **매우 느림**. 대칭키는 빠르지만 **키를 어떻게 안전하게 전달하느냐**가 문제임. 그래서 **느린 비대칭키로 키만 주고받고, 실제 데이터는 빠른 대칭키로** 처리함. 97번 ①("모든 데이터를 비대칭키로")이 틀린 이유가 이것임.

**포트** — HTTPS 443, IMAPS 993, POP3S 995, SMTPS 465, LDAPS 636, FTPS 990.

#### 대칭키 vs 비대칭키 — 98번

| 구분 | **대칭키**(비밀키) | **비대칭키**(공개키) |
| --- | --- | --- |
| 키 | **암호화·복호화에 같은 키** | **공개키로 암호화 → 개인키로 복호화** |
| 속도 | **빠름** | **느림**(수백~수천 배) |
| 키 관리 | n명이면 **n(n-1)/2개** 필요 | 각자 키 쌍 1개 |
| 문제 | **키 배송 문제** | 속도 |
| **알고리즘** | **AES**, DES, 3DES, SEED, ARIA, IDEA, RC4, Blowfish | **RSA**, **ECC**, **DSA**, ElGamal, Diffie-Hellman |

**98번 정답 ①** — AES(Advanced Encryption Standard)만 대칭키이고 RSA·ECC·DSA는 전부 공개키 계열임. **"S로 끝나는 표준(AES/DES)은 대칭, RSA·ECC·DSA는 비대칭"** 정도로 묶어두면 됨(SEED·ARIA는 한국 표준 대칭키임).

**해시 함수** — 암호화가 아니라 **단방향 요약**임. 무결성 검증·패스워드 저장에 씀. 복호화가 불가능하다는 점이 암호와 다름.

| 알고리즘 | 출력 길이 | 상태 |
| --- | --- | --- |
| MD5 | 128비트 | **충돌 발견, 사용 금지** |
| SHA-1 | 160비트 | **취약, 폐기 권고** |
| **SHA-256 / SHA-512** | 256 / 512비트 | **현재 표준** |

```bash
sha256sum file.iso            # 무결성 검증
md5sum file.iso
gpg --gen-key                 # 키 쌍 생성
openssl enc -aes-256-cbc -in a.txt -out a.enc   # 대칭키 암호화
```

**전자서명** — 비대칭키를 **반대로** 씀. **개인키로 서명 → 공개키로 검증**. 보낸 사람이 본인임을 증명(부인 방지)함. 암호화(공개키로 잠금)와 방향이 반대라는 것이 시험 포인트임.

### 5-14. 점검 도구 — nmap·tcpdump

> 99번·100번 무응답 — 정답 ④(`-sS`), ③(캡처 후 파일 저장)

#### nmap — 포트 스캐너 (99번)

**nmap** = Network Mapper. 열린 포트·서비스·OS를 탐지하는 도구임.

| 옵션 | 스캔 방식 |
| --- | --- |
| **`-sS`** | **TCP SYN 스캔(half-open).** SYN만 보내고 **SYN/ACK를 받으면 RST로 끊음** — **3-way handshake를 완성하지 않음.** 빠르고 로그에 덜 남아 기본값 ← **99번 정답 ④** |
| **`-sT`** | **TCP Connect 스캔.** **연결을 완전히 맺음.** 권한 불필요하지만 로그에 남음 |
| **`-sU`** | **UDP 스캔.** 느림 |
| `-sA` | ACK 스캔(방화벽 규칙 탐지) |
| `-sn` / `-sP` | 포트 스캔 없이 **호스트 생존만** 확인(핑 스윕) |
| **`-O`** | **OS 탐지** |
| `-sV` | 서비스 버전 탐지 |
| `-p 1-1000` | 포트 범위 지정 |
| `-A` | 공격적 스캔(OS+버전+스크립트+traceroute) |
| `-T0`~`-T5` | 속도 조절(낮을수록 은밀) |

```bash
nmap -sS -p 1-1000 192.168.1.10
nmap -sV -O 192.168.1.10
nmap -sn 192.168.1.0/24              # 살아 있는 호스트 목록
```

**`-sS`가 "half-open"인 이유** — 정상 연결은 SYN → SYN/ACK → ACK 세 단계인데, `-sS`는 SYN/ACK를 받은 시점에 포트가 열려 있음을 알았으므로 **ACK 대신 RST를 보내 연결을 끊음**. 연결이 성립되지 않아 애플리케이션 로그에 남지 않음. **root 권한이 필요함**(원시 패킷 생성).

**허가 없는 스캔은 불법임.** 자신이 관리하는 시스템이나 명시적 승인을 받은 대상에만 사용해야 함.

#### tcpdump — 패킷 캡처 (100번)

명령행 패킷 분석기임. **스캔 도구가 아니라 캡처 도구**라는 것이 100번의 함정임(②가 그 오해를 노림).

| 옵션 | 의미 |
| --- | --- |
| **`-i eth0`** | **i**nterface. **캡처할 인터페이스** (`-i any`면 전체) |
| **`-w file.pcap`** | **w**rite. **캡처를 파일로 저장**(화면 출력 안 함) |
| **`-r file.pcap`** | **r**ead. 저장된 파일을 읽어 분석 |
| `-n` | 이름 해석 안 함(IP를 그대로 표시, 빠름) |
| `-nn` | 포트 번호도 이름 해석 안 함 |
| `-c 100` | count. 100개만 캡처 후 종료 |
| `-v` / `-vv` | 상세도 |
| `-A` | ASCII로 페이로드 출력 |
| `-X` | 16진수 + ASCII |
| `-s 0` | snaplen. 패킷 전체 캡처 |

**필터 표현식(BPF):**

```bash
tcpdump -i eth0 tcp port 80 -w web.pcap    # 100번 문제 — eth0에서 TCP 80 캡처 → 파일 저장
tcpdump -i eth0 host 192.168.1.10          # 특정 호스트
tcpdump -i eth0 src 192.168.1.10           # 출발지 지정
tcpdump -i eth0 dst port 443               # 목적지 포트
tcpdump -i eth0 net 192.168.1.0/24         # 대역
tcpdump -i eth0 'tcp and port 80 and host 192.168.1.10'   # 논리 결합
tcpdump -r web.pcap -nn -A                 # 저장 파일 분석
```

`-w`로 저장한 `.pcap` 파일은 **Wireshark**로 열어 GUI 분석할 수 있음. 서버에서 `tcpdump -w`로 뜨고 로컬에서 Wireshark로 보는 것이 표준 작업 흐름임.

**도구 성격 구분 — 시험에서 서로 바꿔 물음:**

| 도구 | 성격 |
| --- | --- |
| **nmap** | **능동적** — 패킷을 **보내서** 응답으로 상태를 알아냄 |
| **tcpdump / Wireshark** | **수동적** — 지나가는 패킷을 **관찰만** 함 |
| netstat / ss | 로컬 시스템의 연결 상태 조회 |

```bash
ss -tulpn        # -t TCP -u UDP -l LISTEN -p 프로세스 -n 숫자 (netstat 후속)
netstat -tulpn   # 동일한 의미(구형)
lsof -i :80      # 80번 포트를 쓰는 프로세스
```
